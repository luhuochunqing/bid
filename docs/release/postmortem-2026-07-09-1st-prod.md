## 三、为什么准备充分还是出问题

### 3.1 根因一：测试环境与生产环境的隐性差异

**问题**：V1092 collation 冲突

- 测试环境数据库默认 collation 是 `utf8mb4_unicode_ci`
- 生产环境数据库默认 collation 是 `utf8mb4_0900_ai_ci`（MySQL 8.0 新默认）
- V1092 迁移中的临时表用数据库默认 collation，与 `roles`/`users` 表的 `utf8mb4_unicode_ci` 冲突
- 测试环境因为默认 collation 恰好一致，从未暴露此问题

**教训**：**测试环境通过 ≠ 生产环境通过**。collation、字符集、时区、SQL mode 这些隐性配置差异，只有在生产环境才会暴露。

**改进**：新增教训"临时表必须显式指定 COLLATE 与关联表对齐"，已写入部署报告 §12。

### 3.2 根因二：配置项声明但代码未使用（最严重）

**问题**：`skipUnmappedUsers` 配置项在 `OrganizationIntegrationProperties` 中声明（默认 true），但 `OrganizationUserSyncWriter.upsert()` line 68 硬编码 `LoginRoleWhitelist.isAllowed()` 检查，**完全忽略** `skipUnmappedUsers` 配置。

**为什么测试环境没发现**：
- 测试环境历史上有 8438 个 NULL 角色用户（旧版代码创建的历史遗留）
- 这些用户登录时由 `OssPermissionCache` 实时从 OSS 抓取角色
- 测试环境的日常使用从未触发"首次全量同步"场景
- 配置项声明了但未使用，单元测试只测了声明层，没测行为层

**为什么准备阶段没发现**：
- 准备阶段关注的是"配置是否正确"
- 没人想到去验证"配置项是否真的被代码使用"
- 这属于**配置-代码契约断裂**，不是配置错误

**教训**：**配置项声明 ≠ 配置生效**。新增配置项时必须验证代码确实使用了该配置，最好有集成测试覆盖。

**改进**：建议后续添加集成测试，验证 `skipUnmappedUsers=false` 时未匹配角色用户能被创建。

### 3.3 根因三：同步结果的"假成功"掩盖问题

**问题**：首次全量同步返回 `status=SUCCESS`，8572 条记录全部标记成功，但 users 表只有 168 条。

**根因**：`OrganizationSyncRunAppService.processUser()` 中，当 `userWriter.upsert()` 返回 `Optional.empty()` 时，仍然记录为 `successItem`：

```java
// 实际代码
userWriter.upsert(sourceApp, eventKey, snapshot, jobRoleLookupMap);
itemRepository.save(successItem(...));  // 即使 upsert 返回 empty 也算成功
return RunCounters.success();
```

**教训**：**"跳过"不等于"成功"**。同步框架应该区分"成功创建/更新"和"跳过未处理"两种状态，否则统计数字会误导排障。

**改进**：建议后续重构同步统计，增加 `skippedCount` 字段。

### 3.4 根因四：端口认知混乱导致排障绕弯

**问题**：排查 admin 403 时，误以为后端在 8080 端口，实际两个环境后端内部端口都是 18080。

**实际端口架构**（测试和生产一致）：

| 层 | 端口 | 说明 |
|----|------|------|
| Nginx 对外 | 80 / 8080 | 浏览器和外部 curl 访问入口 |
| 后端内部 | 18080 | `SERVER_PORT=18080`，通过 `/etc/xiyu-bid/backend.env` 注入 |
| application-prod.yml 默认 | 8080 | 仅是 fallback 默认值，**从未实际使用** |

**根因**：
- `application-prod.yml` 中 `server.port: ${SERVER_PORT:8080}` 默认 8080，容易让人误读
- `LIVE_SERVER_DEPLOYMENT_RUNBOOK.md` 同时出现 `127.0.0.1:8080` 和 `127.0.0.1:18080` 两种健康检查地址（8080 经 Nginx 代理可达，但容易误导）
- 排障时混淆了"Nginx 对外端口"和"后端内部端口"

**教训**：**部署文档必须明确区分 Nginx 对外端口和后端内部端口**，不能混用。

**改进**：已在部署报告 §2 明确记录 `后端端口 18080（Nginx 80/8080 反代）`；本次复盘已补充端口对照表。

### 3.5 根因五：本地开发环境干扰生产排障

**问题**：本地 Mac 设置了 `HTTP_PROXY=127.0.0.1:7897`（Clash/V2Ray），导致 `curl http://172.16.10.149:18080` 走代理隧道超时。

**教训**：**本地代理是排障隐形杀手**。这条经验在部署技能 §16 已经记录过（第 19/23 次复发），但本次又踩了一次。

**改进**：所有 curl 命令必须加 `--noproxy '*'`，或排障时直接 ssh 到服务器内部执行。

## 七、总结

本次首次生产部署最终成功上线，但过程中暴露了 5 个问题，其中 2 个（collation 冲突 + skipUnmappedUsers 未使用）是**测试环境无法暴露的系统性问题**。

**核心教训**：

1. **测试环境通过 ≠ 生产环境通过** — 隐性配置差异（collation、端口、数据量）是首次部署的最大风险
2. **配置项声明 ≠ 配置生效** — 必须验证代码确实使用了配置
3. **"跳过"不等于"成功"** — 同步统计口径必须严谨
4. **准备再充分也要预留 2 小时排障窗口** — 首次部署一定会遇到生产环境特有问题

**改进方向**：建立"首次部署预检清单"，专门针对测试环境无法暴露的差异（collation、端口、生产数据量、OSS 数据质量），在首次部署前主动验证。
