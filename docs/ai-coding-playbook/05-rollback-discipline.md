# 第 5 章 回退与恢复纪律：36 次回退教我们的

> 读者：准备开启下一个 AI Coding 项目的工程团队。
> 本章数据源：对西域数智化投标管理平台 2000+ PR 的全量挖掘（`.runtime/pr-mining/findings/reverts.json`），覆盖 36 个 revert/回退类 PR、6 大聚类、13 个深度案例。所有 PR 号、commit hash、数字均来自该数据源。

## 5.1 TL;DR：先把 36 起回退拆开看

看到"36 次回退"这个数字，先别急着得出"质量失控"的结论。拆开看，结构完全不同：

- **真·事故性 revert：约 10 起，占 2000+ 总 PR 的 0.5%**。修复方向错、改错对象、过度修复、同步覆盖他人代码、生产部署失败——只有这些才是经典意义上的"出了事故要回滚"。
- **回滚基础设施合规债：12 起**。不是事故，而是回滚机制本身反复欠费——Flyway U 脚本缺失、source header 缺失、版本号引用错误、脚本放错目录，被 `FlywayRollbackScriptCoverageTest` 门禁反复拦下后补丁式补齐。
- **fallback（降级/回退）设计补全：11 起**。主路径假设过强，生产环境缺字段、缺权限、服务不可用时崩溃，事后补 fallback。

质量信号在哪里？三个：

1. **0.5% 的真事故率**，说明"真实 API 唯一源 + 门禁体系"的组合拳大体是有效的——事故没有灭绝，但被压到了很低的绝对水平。
2. **同日 revert 是主流**：!1230→!1232、!1952→!1955、!2066→!2067、!2091→!2095、!1453→!1471 全部当天完成。发现错误→整单回退的响应链路是通的，没有把错误留在主干上发酵。
3. **恢复方式在演化**：从"手工重写丢 author"到"cherry-pick 优先纪律"再到"revert PR 规范化 + 守护测试"，团队把每次事故都转化成了纪律资产（详见 5.4）。

真正需要警惕的不是 revert 的数量，而是两类"看不见"的回退（详见 5.5）：隔 9 天才发现的权限回退（!1385→!1921）和无用户感知的覆盖事故（3dcc30097）。它们的共同点是——**测试环境根本测不出**。

一个口径说明：本章把"回退"分成三个层次统计——

- **revert**：用 `git revert` 或等价手段撤销已合入的提交（真事故性回滚）；
- **回滚能力建设**：让"将来能回滚"成为可能的基础设施投入（Flyway U 脚本、门禁）；
- **fallback 设计**：运行时的降级路径（服务不可用、字段为空时的备选行为）。

三层共用同一个词是中文语境的巧合，但背后的纪律是相通的：**无论是代码态的回滚、迁移态的回滚还是运行态的降级，"出错了怎么退"都必须在设计时被显式回答，而不是出事后临时回答。** 36 起里 23 起是后两层欠费，说明这个项目的短板从来不是"revert 不果断"，而是"交付时没把退路算进 Done"。

对读者的使用建议：5.2 和 5.3 是案例库，可以跳读；5.6 是行动清单，建议整段抄进下个项目的第一周基建任务里。

## 5.2 回退聚类全景：6 类，每类的模式、代表 PR 与预防

先给一张全景表，再逐类展开。注意每一类的"预防"列——它们最终汇总成 5.6 的五条门禁级纪律。

| 聚类 | 数量 | 性质 | 一句话模式 |
|---|---|---|---|
| 回滚基础设施合规债（Flyway U 脚本 / 门禁） | 12 | 非事故，合规欠费 | U 脚本缺失/放错目录，被门禁反复拦下后补丁式补齐 |
| 降级/回退（fallback）设计修复 | 11 | 非事故，设计欠费 | 第一版只考虑理想路径，生产缺字段/缺权限/服务不可用就崩 |
| 真·revert：方向错 / 改错对象 / 过度修复 | 8 | 真事故 | AI 没核实真相就动手：错文档、错组件、没做依赖展开 |
| 同步覆盖他人代码（多仓集成事故） | 2 | 真事故 | 滞后镜像当真源，一个 commit 覆盖当天 9 个修复 |
| 生产部署失败回滚 | 1 | 真事故 | prod-only 装配的 Bean 从未在测试环境实例化过 |
| 传递依赖引发测试环境回退 | 2 | 非事故，基建回归 | SDK 传递依赖静默改变框架默认行为（XML 内容协商） |

三个结构性观察：

- **64% 的回退类 PR（23/36）不是事故，而是两类"欠费"**——回滚机制欠费和 fallback 设计欠费。它们暴露的不是"AI 写错代码"，而是"交付标准里没把回滚能力和降级路径算进 Done 的定义"。
- **真事故集中在"核实真相"环节**：8 起真 revert 里，没有一起是"不会写代码"，全部是"没核实就动手"——没读真实定义、没复现定位、没列消费方、没验证双轨。
- **多仓集成和 prod-only 路径是最危险的两类**：数量少（3 起），但发现延迟最长、影响面最大，且都绕过了全部门禁。

### 5.2.1 回滚基础设施合规债（Flyway U 脚本 / 门禁）——12 起

- **代表 PR**：!4、!17、!32、!42、!166、!316、!402、!413、!1156、!1589、!1780、!1811
- **模式**：不是事故回滚，而是回滚机制本身反复欠费：U 脚本缺失、source header 缺失、版本号引用错误、脚本放错目录，被 `FlywayRollbackScriptCoverageTest` 门禁反复拦下后补丁式补齐。
- **最刺眼的一例**：!413 在补 U1064–U1069 六个 U 脚本的同时，挖出 `scripts/pre-push-gate.sh` 第 35 行的默认值 bug——`PRE_PUSH_GATE:-0` 把"跳过检查"写成了默认。结果是 **14 道门禁上线后从未真正生效**，P0 编译错误一路放行。
- **预防**：
  - 回滚能力与迁移同 PR 强制交付（V+U 成对门禁），写迁移脚本时由机器人自动生成 U 脚本骨架；
  - 门禁自身要纳入审计——对 gate 脚本做"自检测试"：故意制造一个必失败的提交，验证 gate 真的会红；
  - skip 开关的默认值必须 **fail-close**（默认开启检查）。这是下个项目第一天的基础设施决策。

### 5.2.2 降级/回退（fallback）设计修复——11 起

- **代表 PR**：!187、!257、!434、!605、!888、!972、!1076、!1086、!1119、!1287、!1471
- **模式**：主路径假设过强导致事故，事后补 fallback：OSS 认证不可用回退本地密码（!888）、menuPermissions 为空回退角色白名单（!1471）、employeeNumber 为空回退 username（!1076/!1119）、结项查不到保证金回退立项表（!187）、事务污染改用独立事务（!1287）。共同点是第一版实现只考虑了"理想路径"，生产数据/环境缺字段、缺权限、服务不可用时就崩。
- **根因**：AI 生成代码默认走 happy path。
- **预防**：在 review 清单加一条硬问——**这个调用的外部依赖（OSS/权限点/字段）为空或不可用时，行为是什么？** fallback 必须和主路径同 PR 交付并配测试，而不是等用户在 Linear 上报后再返工（!1076→!1119 隔日返工，!1453→!1471 同日 rework）。

### 5.2.3 真·revert：修复方向错 / 改错对象 / 过度修复——8 起

- **代表 PR**：!578、!1232、!1238、!1244、!1921、!1955、!2067、!2095
- **模式**：AI 在没核实真相的情况下动手——
  - 拿错误文档当依据批量改 70 个文件（!1230→!1232）；
  - 改错组件和阶段（!2066→!2067）；
  - 改全局锁定信号没查 7 处依赖（!2091→!2095）；
  - 权限注解改细没考虑 OSS 用户权限来源（!1385→!1921）；
  - 按猜测调整 OBS URL 模式（!1952→!1955）；
  - 前端猜后端契约两次改回（!1238/!1244）。
- **预防**（三条，条条对应血案）：
  1. **真相唯一源是代码和数据库，不是文档**——改之前先读 RoleProfileCatalog 式的真实定义（!1232）；
  2. 改共享信号/全局变量前必须做 **Dependency Expansion**，列出全部消费方（!2095 的 locked 有 7 处依赖）；
  3. **定位再动手**——用户报的 bug 在哪个组件，先复现确认，不要凭关键词相似就改（!2067 改了 DraftingStage，真 bug 在 InitiationStage）。

### 5.2.4 同步覆盖他人代码（多仓集成事故）——2 起

- **代表 PR**：!1133、!1135
- **模式**：commit `3dcc30097` 名为"同步 GitHub main 重构"，实际 GitHub main 滞后于 Gitee，一个 commit 把当天 9 个 Gitee 修复整体覆盖（74 文件改、18 文件删、净删 1236 行）。用户隔天报"任务卡片点不开、三列宽度又不一致"才发现；最深的一处回退（投标专员标讯可见性 `a048a0cfd`）无任何用户感知，靠系统排查才挖出。
- **预防**：多 remote（Gitee/GitHub）镜像环境里，"同步"和"重构"是最危险的两类 commit——**巨量 diff + 模糊说明 = 必须逐文件核对净删除**。同步类 PR 设行数上限和强制文件级说明；净删超阈值自动要求人工确认；覆盖他人 commit 后恢复一律 cherry-pick 保 author。

### 5.2.5 生产部署失败回滚——1 起

- **代表 PR**：!1532（第 34 次部署报告）
- **模式**：!1519 的 Sentry Logback 集成在 prod profile 下 SentryAppender 实例化失败，后端 crash-loop 约 10 分钟（13:20–13:30），nginx 502；`remote-deploy.sh` 的健康检查还把 502 误判为成功。手动恢复旧 jar（`057612930-api8080`）+ 重启，约 3 分钟回滚成功，Smoke 全绿。
- **预防**：监控/日志类集成恰恰最常在 prod profile 才激活（本地和 staging 不挂 SentryAppender），属于"只在生产执行的路径"。凡 profile 条件装配的 Bean，部署前必须用 prod profile 本地启动一次；健康检查脚本对 502 必须 fail 而不是 pass。回滚 SOP（旧 jar + 重启 + Smoke）这次 3 分钟跑通，证明有效，直接沿用。

### 5.2.6 传递依赖引发测试环境回退——2 起

- **代表 PR**：!1974、!2053
- **模式**：`huaweicloud-sdk-iam:3.1.28` 传递引入 `jackson-dataformat-xml`，`standaloneSetup` 的 MockMvc 默认注册 XML 转换器，请求不带 `Accept: application/json` 时内容协商回退到 XML，`$.success` 等 JSON path 断言批量失败。!1974 修了 17 个文件，漏了 10 个，!2053 两天后再补一批，合计修 51 个 Failure。
- **预防**：第三方 SDK 的传递依赖能静默改变框架默认行为（内容协商、序列化）。`dependency:tree` 变更纳入 PR diff 审查；测试基建类修复先全局 grep 同一模式（`standaloneSetup`）一次性修完，不要修一批漏一批。

## 5.3 深度案例：10 个最有教学价值的现场

从 13 个深度案例中选出 10 个，取舍标准有三条：根因要有代表性（覆盖"错文档、错对象、错真相源、错恢复方式"四类典型错误）、教训要可转化为下个项目的第一周动作、过程要有完整证据链（PR 号、commit hash、行数可核对）。未入选的 3 个（!1532 部署失败、!413 门禁默认值、!1974 传递依赖）并非不重要，而是已在 5.2 聚类中完整展开，此处不再重复。

### 案例 1：!1230→!1232——错误真相源引发的 70 文件同日互 revert

- **经过**：!1230 依据 CLAUDE.md 角色清单，把 70 个 E2E 文件 215 处角色名从 `/bidAdmin` 等改成 `bid_admin`/`bid_lead`（merge `185eb4045`，70 files +215/-215）；当天 !1232 用 `git revert 5b09c3a21` 全部还原（merge `582a9c6b9`，70 files +215/-215）。
- **根因**：CLAUDE.md 的角色清单是错误文档。后端 `RoleProfileCatalog.java` 第 56–58 行和数据库 RoleProfile 表存的是 `/bidAdmin`（OSS 格式带斜杠），改完后端 `findByCodeIgnoreCase('bid_admin')` 查不到，注册 400，E2E 批量跳登录页失败。
- **教训**：**代码与数据库是唯一真相，文档（包括 CLAUDE.md）会撒谎。** 批量改动前先拿一条用例验证假设；发现方向错了就整单 revert，不要在错误基础上叠加修复。

### 案例 2：3dcc30097——"同步 GitHub main"净删 1236 行覆盖 9 个 commit

- **经过**：`3dcc30097`（2026-06-25 16:15）标题是"同步 GitHub main 重构"，实际 GitHub main 滞后于 Gitee，agent 把滞后镜像当真源执行"同步"，等价于用旧快照覆盖新代码：74 文件改、18 文件删、净删 1236 行，当天 9 个 Gitee 修复 commit 被整体覆盖。
- **暴露路径**：用户隔天报"任务卡片点不开、三列宽度又不一致"；最深的一处——`TenderProjectAccessGuard` 投标专员标讯可见性（原修复 `a048a0cfd`）——无任何用户报障，靠系统排查才挖出。
- **恢复**：!1133（merge `dc2ab1ffc`，8 files +578/-16）恢复两部分：CO-338 任务看板抽屉/三列等宽（原修复 `90563f6a1`）和投标专员可见性。
- **教训**：识别信号已经写进 playbook——**标题含"同步 main/重构" + 净删千行 = 红色警报**。多 remote 镜像环境下，任何"同步"动作前必须确认方向：哪边是真源，哪边是滞后镜像。
- **补充**：这起事故同时暴露了"恢复"和"发现"两个短板——发现靠用户报障（隔天），恢复靠手工重写（丢 author）。它一个事故催生了 playbook 的两条核心规则（识别信号 + cherry-pick 优先），是全书引用密度最高的事故现场。

### 案例 3：!1135——恢复方式本身犯了第二个错误

- **经过**：!1133 恢复时跳过 cherry-pick 直接手工重写，`90563f6a1` / `a048a0cfd` 的原 author 在 git blame 中丢失。!1135（merge `e51a673bc`，4 文件）把"回退恢复默认 cherry-pick、冲突不豁免、仅三种例外允许手工、手工也必须双重记录原 hash"写入 RELIABILITY.md 关键硬约束第 7 条，并新建 `docs/references/rollback-recovery-playbook.md`。
- **教训**：**git blame 可追溯性是团队资产。** 案例对照表写得很清楚：标讯可见性恢复本可纯 cherry-pick + 解决 2 个小冲突，实际全盘手工，代价最高。下个项目从第一天就把这条纪律写进 agent 合约。

### 案例 4：!1385→!1921——隔 9 天生产才爆的权限回退

- **经过**：!1385（merge `e832aa111`，2026-06-30，16 files +545/-49）把权限统一下沉到 Policy 层并改用 `hasAuthority('tender.view')`；9 天后 !1921（merge `d4a8e5ad7`，2 files +19/-10）把 `TenderController.java:135` 紧急回退为 `hasAnyRole(...)`。
- **根因**：OSS 同步用户的权限唯一来源是 OSS 菜单映射，OSS 端从未定义 `tender.view` 权限点，本地 DB 的 V1118 迁移对 OSS 用户完全无效——**所有 OSS 用户（含 admin）进标讯详情页 403**。更糟的是 `AccessDeniedException` 被 Sentry 过滤不上报，靠服务器日志 + git 追溯才定位。
- **教训**：权限模型有双轨（本地 DB / OSS 映射）时，任何 `hasAuthority` 细化都必须验证两条轨的权限点覆盖。**测试环境全是本地用户，测不出 OSS 用户路径**——权限改动需要一条"OSS 用户冒烟用例"进 e2e。

### 案例 5：!2091→!2095——revert 规范化的标杆："撤销什么/保留什么" + 守护测试

- **经过**：!2091 的 commit `153053011`（2026-07-16 11:43）把 `locked` 定义从 `PENDING_REVIEW||APPROVED` 收窄，想让待审状态字段可编辑；当天 !2095（merge `5976bca82`，2 files +66/-2）revert 该 commit 恢复 `locked` 原定义，**保留无关的 region cascader 修复**，并补 5 个 `locked` 语义守护测试。期间 !2094 试图在错误基础上分离 `fieldLocked`/`operationLocked`，被识别为"错误上叠加错误"直接关闭。
- **根因**：`locked` 是全局锁定信号，被 7 处依赖（字段编辑 + 删除/上传/AI 评估操作权限），改定义连带解锁了危险操作。AI 推荐方案时未做 Dependency Expansion。
- **教训**：改共享信号前列出全部消费方；发现根因是自己上一手造成的，正确动作是 **revert 回原点重新设计，而不是打补丁**（!2094 被关）。revert 同时沉淀守护测试，把"回退"升级为"回退 + 防再犯"。

### 案例 6：!1952→!1955——OBS 三连："revert ≠ 修复原始问题"

- **经过**：!1952（merge `83ef63c1d`，1 file +10/-5）为修自定义域名 SSL 证书不匹配启用 OBS path-style；当天 !1955（commit `7f988157f`，1 file +7/-10）revert 回 virtual-hosted-style。但随后 `a0107997d` 发现 virtual-hosted 仍 `SignatureDoesNotMatch`，真正根因是 SDK 需要 `setCname(true)`，**第三次改动才修对**。
- **根因**：path-style 把 bucket 拼进路径参与签名，与 OBS 自定义域名格式不符，CRM 打开文件报 `SignatureDoesNotMatch`。但 revert 只消除了新引入的问题，SSL 证书问题在 revert 后依然存在——两次都是按猜测调 URL 模式。
- **教训**：**revert 只消除新引入的问题，不代表解决了原始问题。** 对外部服务（OBS SDK）的签名/URL 语义，先读官方文档再动配置，一次改对胜过 revert 循环。

### 案例 7：!1076→!1119——"声明式修复"：PR 描述写了，代码没写

- **经过**：!1076（merge `10b1973bd`，2026-06-25）声称修复 `formatOperatorName` 在 `employeeNumber` 为空时回退 username；次日用户反馈仍是纯姓名，!1119（merge `909408c91`，2 files +31/-3）发现 !1076 实际代码在 employeeId 为空时仍 `return fullName` 未回退，改用 User 实体已有的 `getDisplayEmployeeNumber()`。
- **教训**：**PR 描述不等于代码行为**，review 要对照 diff 验证声明；修复前先搜实体/工具类是否已有封装方法（`getXxx`/`displayXxx`），不要重复造轮子。同一 bug 修两次的成本远高于第一次就改对。

### 案例 8：!1453→!1471——修一类用户，回归另一类用户

- **经过**：!1453（merge `7a1f4518d`，11 files +149/-41）把业绩/仓库/人员证书三模块的可见性从 `isBidManager(roleCode)` 改为 `hasAnyPermission` 权限点，修投标专员缺失问题；同日用户反馈"投标组长和投标管理员账号功能也出现缺失"，!1471（merge `83f5ceca8`，2 files +58/-11）加 menuPermissions 为空时回退 `isBidManager` 白名单的 fallback。
- **根因**：session restore / OSS fallback 等登录路径可能返回空 menuPermissions，`hasAnyPermission` 对空数组返回 false，管理员角色被误伤。
- **教训**：权限/可见性改动的影响面是 **全部角色 × 全部登录路径**。改动后验证矩阵必须覆盖：每个角色 × 每条登录路径（正常 / session restore / OSS fallback）。

### 案例 9：!2066→!2067——改错对象：组件名相似是 AI 的高发诱因

- **经过**：!2066（merge `f55e81131`，3 files +145/-3）给 `DraftingStage.vue` 的 `ProjectDocumentTable` 加 `isCurrentUserReviewer` 下载权限；当天 !2067（merge `49d06e227`，3 files +3/-145）用 `git revert -m 1` 完整撤销，测试 30/30 绿。
- **根因**：用户报的 bug 在 `InitiationStage.vue:82-155` 的独立「招标文件」卡片（立项阶段），与 !2066 改的 DraftingStage（标书制作阶段）是**不同阶段、不同组件、不同页面**——修复对用户的 bug 完全无效，+145 行全是白费。
- **教训**：先复现定位再动手。组件名/业务阶段相似是 AI 改错对象的高发诱因；revert PR 里附带真实 bug 的疑点链路（`handleDownloadBidDoc → GetDownloadUrlUseCase → DownloadPolicy`），为后续正确修复铺路，这个写法值得固化成 revert PR 模板（见 5.6 纪律 5）。

### 案例 10：!1238 / !1244——前端猜后端契约，同日两次改回

- **经过**：CO-329 CRM 集成中前端按猜测实现：!1238（merge `91ab9cadf`，2 files +4/-4）revert 无效的 `c.position` 字段映射并修 POSITION 下拉；!1244（merge `1cee1fa69`，2 files +4/-4）把联系人 API 从 GET 改回 POST 以匹配后端真实接口。两个 revert 同日（2026-06-27）。
- **根因**：前端对后端契约（字段名、HTTP 方法）的实现基于猜测而非真实接口定义，联调时才发现不匹配。
- **教训**：**跨端契约是唯一不能猜的东西。** 项目已有 `docs/references/crm-field-mapping` 类文档，下个项目把契约做成机器可校验的（OpenAPI / 契约测试），前端生成代码而非手写 guess-and-check。

## 5.4 恢复方式的三级进化

36 起回退里藏着一条清晰的能力演化曲线，值得下个项目直接跳到最后一级：

| 级别 | 时期 | 代表 PR | 做法 | 代价 / 收益 |
|---|---|---|---|---|
| 第一级：手工重写 | 2026-06-25 前后 | !1133 | 跳过 cherry-pick，照着记忆重写代码 | 原 author 在 blame 中永久丢失；review 无法对照原 diff；易引入二次偏差 |
| 第二级：cherry-pick 优先 | 同日沉淀 | !1135 | 纪律写入 RELIABILITY.md 硬约束第 7 条 + rollback-recovery-playbook | 保 author、保可追溯性；冲突不豁免 |
| 第三级：revert PR 规范化 | 2026 年 7 月 | !2067 / !2095 | 明确"撤销什么/保留什么" + 附疑点链路 + 补守护测试 | 回退升级为"回退 + 防再犯"，事故转化率最大化 |

**第一级：手工重写，丢 author（2026-06-25 前后）**
!1133 恢复 3dcc30097 覆盖事故时，agent 跳过 cherry-pick 直接手工重写，`90563f6a1` / `a048a0cfd` 的原 author 在 blame 中永久丢失。手工重写看似"快"，实际代价最高：丢失可追溯性、容易引入二次偏差、review 无法对照原 diff。

**第二级：cherry-pick 优先纪律（同日 !1135 沉淀）**
事故当天即复盘，把"回退恢复默认 cherry-pick、冲突不豁免、仅三种例外允许手工、手工也必须双重记录原 hash"写入 RELIABILITY.md 关键硬约束第 7 条，并产出 `docs/references/rollback-recovery-playbook.md`。纪律要点：git blame 是团队资产；cherry-pick 有冲突不是绕开它的理由。

**第三级：revert PR 规范化（2026 年 7 月，!2067 / !2095）**
- !2067 用 `git revert -m 1` 完整撤销 !2066，测试 30/30 绿，且 revert PR 里附带真实 bug 的疑点链路（`handleDownloadBidDoc → GetDownloadUrlUseCase → DownloadPolicy`），为后续正确修复铺路——这个写法值得固化成 revert PR 模板。
- !2095 revert 时明确"撤销什么 / 保留什么"（撤销 locked 修改、保留 region cascader 修复），并补 5 个守护测试，把"回退"升级为"回退 + 防再犯"。

注意第三级其实已经**超越了 playbook**——!1135 写的纪律只覆盖恢复方式，!2095 增加了防再犯测试维度。这说明纪律本身是活的，每次事故都应该回头加固它。

## 5.5 为什么"同日 revert 是主流"，但有两类例外

同日 revert 是主流不是偶然：!1230→!1232、!1952→!1955、!2066→!2067、!2091→!2095、!1453→!1471 全部当天完成。原因是这些 bug 在测试环境**可复现、可观察**——E2E 一跑就红，用户一报就能定位。

两个例外都有"看不见"的特性，值得单独设防：

**例外一：prod-only 装配路径（!1519→第 34 次部署失败）**
SentryAppender 只在 prod/staging profile 装配，本地和门禁环境从未实例化过它。这类"只在生产执行的路径"靠测试环境覆盖不到，必须靠部署纪律补：profile 条件装配的 Bean，部署前用 prod profile 本地起一次。好消息是回滚 SOP（旧 jar + 重启 + Smoke）3 分钟跑通，证明"回滚能力"本身是合格的——问题从来不在回滚，在于发现太晚。

**例外二：OSS 菜单映射权限源（!1385→!1921，隔 9 天）**
测试环境全是本地用户，OSS 用户的权限来自菜单映射这条轨永远测不到；`AccessDeniedException` 又被 Sentry 过滤，连告警都没有。同类还有 3dcc30097 里最深的那处可见性回退——无用户感知，靠系统排查才挖出。这类问题的防御只能靠**验证矩阵显式覆盖双轨**：权限改动必须带一条 OSS 用户冒烟用例进 e2e；监控过滤规则本身要纳入审计（被过滤的异常 = 静默的事故）。

给下个项目的推论：**凡是"测试环境测不出"的路径，都要在门禁或部署 SOP 里给它配一条专门的验证通道**，否则它就是下一个 9 天潜伏期。

### 5.5.1 发现延迟的代价分级

把 36 起回退按"从引入到发现"的延迟排开，是一条非常清晰的代价曲线：

- **当日级（主流）**：!1230→!1232、!1952→!1955、!2066→!2067、!2091→!2095、!1453→!1471。错误在主干上存活不到一天，代价 ≈ 一个 revert PR + 少量返工。这一级靠的是 E2E 红、用户即时报障——**可观察性在测试环境内**。
- **隔日级**：!1076→!1119（次日用户反馈）、3dcc30097（隔天用户报"任务卡片点不开"）。代价开始包含用户信任损耗，以及"到底还有多少处没被发现"的排查成本——3dcc30097 最深的一处可见性回退没有任何用户感知，靠系统排查才挖出。
- **多日级**：!1385→!1921（9 天）、!1974→!2053（2 天补漏）。9 天里所有 OSS 用户（含 admin）进标讯详情页 403；2 天里测试套件带着 10 个文件的已知失败运行。这一级的共同点是**观察通道本身有洞**：Sentry 过滤了 AccessDeniedException，第一批修复没做全局模式搜索。

结论：回退纪律的真正分水岭不在"会不会 revert"，而在**发现延迟被压在哪一级**。把隔日级、多日级的案例逐个拆解，补的都不是 revert 技术，而是观察通道——e2e 冒烟矩阵、监控过滤审计、全局模式搜索。这是 5.6 五条纪律共同指向的目标。

## 5.6 下个项目的回退纪律清单（5 条门禁级建议）

这 5 条全部来自真实事故，建议从项目第一天就写进 agent 合约和门禁体系。排序有意为之：前两条防"发现太晚"（门禁失效、双轨盲区），第三条防"改出事故"（共享信号），后两条管"事故发生后的动作"（恢复方式、revert 规范）。它们覆盖了一条事故从孕育、爆发到善后完整生命周期的每一个环节。

**纪律 1：门禁 fail-close，且门禁自身要被审计**
来源：!413——`PRE_PUSH_GATE:-0` 默认值写反，14 道门禁上线后从未真正生效，P0 编译错误一路放行。执行项：所有 skip 开关默认开启检查；对 gate 脚本做"元测试"（故意制造必失败提交，验证 gate 真的会红）；迁移脚本 V+U 成对交付，机器人自动生成 U 脚本骨架。

**纪律 2：权限改动验证双轨**
来源：!1385→!1921——本地 DB 轨有 `tender.view` 权限点，OSS 菜单映射轨没有，所有 OSS 用户 403，隔 9 天才发现。执行项：权限模型有双轨（本地 DB / OSS 映射）时，任何 `hasAuthority` 细化必须验证两条轨的权限点覆盖；e2e 必须有一条"OSS 用户冒烟用例"；被监控系统过滤的异常类型要定期审计。

**纪律 3：共享信号改前做依赖展开（Dependency Expansion）**
来源：!2091→!2095——`locked` 一个全局信号被 7 处依赖（字段编辑 + 删除/上传/AI 评估），收窄定义连带解锁危险操作。执行项：改任何共享信号/全局变量/公共组件前，先列出全部消费方并写进 PR 描述；发现根因是自己上一手造成的，revert 回原点重新设计，禁止在错误基础上打补丁（!2094 被关是先例）。

**纪律 4：恢复一律 cherry-pick 保 author**
来源：3dcc30097 覆盖事故 + !1133 手工重写丢 blame + !1135 沉淀纪律。执行项：回退恢复默认 cherry-pick，冲突不豁免；仅 playbook 规定的三种例外允许手工重写，且手工也必须双重记录原 hash；同步类 PR（多 remote 镜像环境）设行数上限、强制文件级说明、净删超阈值自动要求人工确认。

**纪律 5：revert PR 必须带守护测试**
来源：!2095——revert 同时补 5 个 locked 语义守护测试，把"回退"升级为"回退 + 防再犯"。执行项：revert PR 模板固化三要素——明确"撤销什么 / 保留什么"、附带真实 bug 的疑点链路（!2067 的 `handleDownloadBidDoc → GetDownloadUrlUseCase → DownloadPolicy` 是范本）、补守护测试防再犯。没有守护测试的 revert 不允许合入。

### 5.6.1 落地检查表（第一周可直接抄）

| # | 纪律 | 落点 | 第一周验收标准 |
|---|---|---|---|
| 1 | 门禁 fail-close | gate 脚本默认值 + 元测试 | 故意提交一个必失败 commit，gate 真的红 |
| 2 | 权限双轨验证 | e2e 冒烟套件 | 存在一条 OSS 用户角色的冒烟用例并接入 CI |
| 3 | 依赖展开 | PR 模板必填字段 | PR 描述含"本改动全部消费方清单"一栏 |
| 4 | cherry-pick 优先 | agent 合约 / RELIABILITY 类文档 | 硬约束写明"恢复默认 cherry-pick，仅三种例外允许手工" |
| 5 | revert PR 规范化 | revert PR 模板 | 模板含"撤销什么/保留什么/疑点链路/守护测试"四栏 |

五条纪律的共同指向，其实是同一个原则：**把"出错了怎么办"从事后反应变成事前设计**。回滚能力随迁移同 PR 交付、fallback 随主路径同 PR 交付、守护测试随 revert 同 PR 交付——形式不同，逻辑一致。
