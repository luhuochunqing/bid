# 第 4 章 AI Coding 门禁体系：事故驱动的进化

> 本章面向准备开启下一个 AI Coding 项目的工程团队。
> 素材来自本项目（西域数智化投标管理平台）的完整考古：git 历史 2026-05-29 ~ 2026-07-17、PR 编号至 !2115+、lessons-learned 61 条、Gitee 已合并 PR 2059 个（其中 fix+hotfix 占 59%）。

## 1. TL;DR

门禁体系是 AI Coding 项目的基础设施，但它的真实面貌和大多数人的想象相反：

- **门禁最大的敌人不是被绕过，而是自己的假绿。** 本项目最著名的门禁事故不是谁绕过了门禁，而是 `pre-push-gate.sh` 第 35 行把默认值写成了 `${PRE_PUSH_GATE:-0}`——一个字符的 `:-0`，让 14 道门禁从建成（2026-06-03）到被发现（2026-06-09，PR !413）整整一周从未真正生效，期间所有 push 都在裸奔，且无人察觉。类似的还有 macOS BSD sed 不支持 `\+` 导致 Flyway 撞号检测长期空循环假绿，直到第 18 次部署事故（main 上同时存在两个 V1110）才暴露。**没有阴性对照的门禁，约等于没有门禁，但它会给你虚假的安全感。**

- **14 道门几乎全是事故税，没有一道是提前预言出来的。** 复盘全部 17 道门禁的引入原因：除了 ArchUnit 基线和文件锁来自单 Agent 时代的工程直觉，其余每一道都能指认出一个具体的事故 PR、一次具体的部署失败、一个具体的 CO-XXX 编号。Flyway 系列六道门（撞号/目录/不可变/配置/语法/DB 同步）全部由部署事故直接催生，集中在第 4 周（2026-06-24 ~ 06-30）一周内装上。**不要试图在第一天设计出完备的门禁体系，你设计不出来；要建立的是「事故 → RCA → 门禁 → 防复发验证」的闭环机制。**

- **门禁自身会成为新的故障源，必须有元治理。** 门禁脚本会假绿（fail-open 默认值、跨平台语法不兼容）、会误伤（hook 误判正常迁移）、会自锁（main 被污染时连修复 PR 都被拦）、会爆炸（hook 调用链成环导致进程风暴，用户侧记录 127 个进程）、会拖垮吞吐（全量跑一遍 7-10 分钟）。本项目为门禁本身修了至少 7 次 bug，并最终催生了「元门禁」——检查门禁的门禁。

一句话：**门禁值得装，但要按「事故驱动 + fail-closed + 阴性对照 + 成本治理」四条纪律装，而不是按教科书装。**

阅读本章时请带着三个问题：①你现在的门禁里，有哪几道从未做过阴性对照？②如果门禁默认值写错了，你的团队会在第几天发现？③你的门禁跑一次要几分钟，乘以你预期的 PR 总量是多少小时？这三个问题的答案，决定了你的门禁体系是在保护吞吐，还是在消耗吞吐。

本章只讲门禁本身。门禁所依赖的多 Agent 工作区策略（持久 worktree、单一开发环境）见 [02 多 Agent 协作体系](02-multi-agent-collaboration.md)；事故驱动的 RCA 方法与逐案案例库见 [01 Bug 根因模式全景](01-bug-root-causes.md) 与仓库 `docs/lessons/`；回退恢复的门禁级纪律见 [05 回退与恢复纪律](05-rollback-discipline.md)。

## 2. 演进时间线：六个阶段

「14 道门禁」是 2026-06-09 PR !413 修复时的口径；到快照时点，pre-push-gate.sh 已膨胀到约 24 个检查段，pre-commit 另有约 25 项检查，scripts/ 下 check-* 脚本 56 个。这个体系不是设计出来的，是长出来的：

## 4. 门禁自身失效的 7 个案例

这是本章最有价值的部分。门禁是代码，代码就有 bug；门禁的 bug 比普通 bug 更阴险，因为它的失效方式是**静默放行**。

### 案例 1：!413——一个字符让 14 道门裸奔一周

`pre-push-gate.sh` 第 35 行写成 `${PRE_PUSH_GATE:-0}`：未设环境变量时**默认跳过全部检查**。从 2026-06-03 建成到 06-09 修复（merge 018ec30ed / fix 832cf3990），14 道门禁从未真正生效，期间所有 push 都是裸奔，且无人察觉——因为「门禁存在」和「门禁生效」在外观上完全一样。

**教训：门禁默认值必须 fail-closed。** 未配置、配置错误、环境异常时，门禁应该拒绝放行，而不是放行。fail-open 的门禁比没有门禁更糟糕——它占用了你的信任预算。

### 案例 2：!606——hook 调用链成环，进程指数爆炸

session-gate.sh 的自动 push 触发 pre-push-gate → gate 跑 vitest（start-env-detection.spec.js）→ vitest 经 dev-env.sh:141 又触发 session-gate → 远端分支不存在再次自动 push。push→gate→vitest→session-gate→push 无限递归，进程指数级爆炸耗尽 CPU，用户侧记录达 127 个进程。修复（94e1c258b / 2a07554f6）：自动化脚本的辅助 push 一律显式带 `PRE_PUSH_GATE=0` 断环。

**教训：门禁/hook 调用链必须是无环图。** 自动化脚本（自动 push、环境同步）显式跳过门禁；hook 内禁止执行会再触发 hook 的命令。上双防线这类环境层复杂机制之前，先把调用链画出来评审。

### 案例 3：BSD sed 假绿——撞号检测从未检测

`check-flyway-versions.sh` 用 GNU sed 语法 `s/.*V\([0-9]\+\).*/\1/` 提取版本号，macOS BSD sed 不支持 `\+` → 提取永远为空 → 空循环 → 撞号检测**一直假绿**，直到第 18 次部署事故（main 两个 V1110）才暴露。脚本第 227 行注释自述：「之前一直假绿是因为 sed 用了 \+」。更糟的是第二层 bug（ece7ce90a，07-07）：main 已被污染时，连修复 PR 本身都被门禁阻断，必须 `--no-verify`——**门禁自锁死循环**。

**教训：** ①假绿比没门更危险，它提供虚假安全感；②跨平台脚本禁用 GNU/BSD 特定扩展（用 `grep -oE` / `sed -E`），关键提取逻辑加非空断言；③门禁必须防自锁——不能阻断「修复门禁所发现问题的 PR」。

### 案例 4：`|| true` 隐性 fail-open

surefire 报告路径误判 + `mvn test || true`：编译失败被静默吞掉，无 XML 报告时结果判定不可靠（463813d72，06-15）。残余缺陷一直潜伏到 !2012 事故（07-11）证明 main 编译断裂仍能漏过，!2014 才补上独立的 `mvn compile` 检查。

**教训：门禁脚本里 `|| true` 是隐性 fail-open，每一处都是定时炸弹。** 结果判定要分层：编译失败立即阻断，不依赖下游报告文件的间接推断。

### 案例 5：hook 误伤正常迁移

V1118 把表名 role_profile 改为 roles 的正常迁移被守卫误拦（2848446dd，06-30「修复 hook 误判」）。

**教训：阻断式门禁的误伤成本是真实的。** 每道门都要预留准确的豁免通道（`// SAFE:` 注释 / `SAFE:` 行尾标记），否则团队会学会讨厌门禁——而讨厌门禁的团队会绕过门禁。

### 案例 6：门禁自身的腐化——元门禁的诞生

守卫脚本注释声明的逃生阀与代码实现不一致；pre-push-gate 的 `mvn -Dtest` 列表与 `backend/src/test` 实际测试文件漂移——文件不存在时 push 静默失败、门禁假绿。PR !1657（07-04）催生 check-guard-consistency.sh 与 check-test-entry-coverage.sh 两道元门禁。

**教训：门禁代码本身是被测对象。** 门禁数量超过 ~10 道后，「防护机制需要阴性对照」必须从单门纪律升级为体系纪律——用元门禁 CI 化地检查门禁。

### 案例 7：运行成本失控——push 一次 7-10 分钟

14 道门全量跑含 3-4 次 mvn JVM 启动 + 前端测试 + build，push 一次约 7-10 分钟，前端测试进程还会挂起。治理（均发生在 06-15）：mvn 按变更检测 + 4 个测试合并一次调用（41e3dc636）、agent/* 分支跳过前端测试与 E2E-UI 检查（3fc05687d）、diff 基准统一 `GATE_BASE..HEAD`（8f6f44491）。

**教训：门禁耗时就是项目吞吐。** 2059 个 PR 的规模下，每道门省 1 分钟等于救回数百小时。按变更范围执行、合并同进程调用、分支分级执行，应该在第一天就设计进去，而不是等拖垮了再治理。

### 元规则汇总

从 7 个案例提炼四条元规则，按重要性排序：

1. **每道门必须有阴性对照测试。** 上线当天故意制造一次违规，确认门禁会红。不红的门不上线。这一条能防住案例 1/3/4/6 的全部假绿。
2. **门禁代码本身是被测对象。** 门禁脚本进代码评审、进测试覆盖、进元门禁扫描，和业务代码同一标准。
3. **默认值一律 fail-closed。** 未配置 = 拒绝放行；脚本异常 = 拒绝放行；结果不可判 = 拒绝放行。任何 `|| true`、`:-0`、空结果静默通过都是 bug。
4. **装门当天故意违规验证，并防自锁。** 门禁不能阻断「修复门禁所发现问题的 PR」；逃生阀要显式命名（`FLYWAY_ALLOW_*` / `JSON_*_SKIP`）+ bypass 日志留痕 + PR 审查检查日志。

## 5. 二阶成本治理

门禁装多了之后，矛盾会从「防不住」变成「跑不动、绕不过、管不了」。本项目的二阶治理有四块，都是花钱买的经验：

### 5.1 按变更范围执行

- **mvn 变更检测**（41e3dc636）：ArchUnit 等 Java 测试不再每次全量跑，按 `GATE_BASE..HEAD` 的 diff 决定是否触发，且 4 个架构测试合并为一次 mvn 调用——JVM 启动是固定大头，能合并就合并。
- **分支跳过策略**（3fc05687d）：agent/* 日常开发分支默认跳过前端测试与 E2E-UI 检查，完整执行让位给 PR/CI 阶段。代价是问题发现点后移，收益是本地 push 吞吐恢复——在 10 个 Agent 高频 push 的场景下这是正确取舍。
- 原则：**重测试门禁第一天就该放 CI 而不是本地 push**。本地门禁只留快（秒级）且零误伤的检查。

### 5.2 P0 逃生阀 + 留痕

2026-07-03 标讯中心宕机事故的教训：P0 时完整 14 道门 + Spec Kit 流程耗时不可接受，如果没有合规通道，团队就会用 `--no-verify` 无纪律绕行，事后无迹可查。对策（RELIABILITY.md §紧急修复通道）：

- hotfix 有明确 SLA 和合规边界，`PRE_PUSH_GATE=0` 是**显式、留痕、事后补审**的动作，不是偷偷摸摸的绕过。
- **不可跳项写死**：ArchUnit 和 Flyway 检查永不可跳——这两类事故（架构腐蚀、迁移炸部署）恰恰是 hotfix 最容易引入的。
- 制度化逃生阀反而降低了门禁被整体丢弃的风险：有合规出口的体系，团队才不会砸门。

### 5.3 棘轮口径：白名单只减不增

处理存量债务唯一可持续的口径：

- 历史违规文件进白名单，**白名单只减不增**；文件达标即从白名单摘除；新代码零容忍。
- 反例是 ArchUnit RULE 13：因存量违规太多被迫整体 DISABLED——**DISABLED 的门等于没门**，还占着编号给人错觉。
- 棘轮类门禁越早装越便宜：第一天装，存量为零，白名单为空，此后每一行新代码都在约束之下。

### 5.4 逃生阀与绕过通道的治理

- 逃生阀显式命名（`FORCE_PUSH_OK=1`、`FLYWAY_ALLOW_*`、`JSON_FIELD_SERIALIZATION_SKIP`、`[skip e2e-scope]`），每个阀门配 bypass 日志留痕，PR 审查时检查日志。
- 逃逸阀注释与实现不一致本身就是事故源（!1657），由元门禁兜底。
- 绕过通道收窄到一个合规口，优于「静默 `--no-verify` + 双防线拦截」的军备竞赛——后者正是 !606 风暴的温床。

## 6. 下个项目第一天只装 5 道门

不要复制本项目的 17 道门——那是 6 周事故税的存量。第一天只装 5 道，其余让事故驱动：

1. **编译门禁（mvn compile + 前端 build + 冲突标记扫描）。** 全部门禁中投入产出比最高的一道：成本极低、零误伤，防的是 main 直接断掉阻断全员部署（!2012 证明缺它真会断）。本项目直到第 6 周才装上，是复盘时公认「最该第一天就有」的门。
2. **分支历史保护（force-push 拦截 + root ratchet）。** 防 filter-repo/orphan/force push 改写历史导致的**不可恢复**损失（#224 静默丢企微登录入口）。日常零成本，只在受保护分支触发。
3. **Flyway 迁移三合一（集中取号 + 撞号拦截 + 已发布不可变）。** 数据库迁移是本项目 P0 事故最密集的来源，多 Agent 并行撞号是必然事件不是概率事件。注意只装简单版：取号集中化（fetch main 取 max+1）+ worktree 内撞号拦截 + diff 检查已发布文件不可变，不要第一天就上全量守卫——本项目那道高维护成本的撞号检测（假绿、误判、自锁三连）就是反例。
4. **架构分层 + 300 行棘轮（ArchUnit 核心 RULE 子集）。** 10 个 Agent 并行时架构腐蚀以天为单位发生；棘轮第一天装 = 零存量成本。**但从第一版就要按变更范围执行**，否则 push 耗时会拖垮吞吐。
5. **agent-locks 冲突检查。** 多 Agent 并行前提下，把文件冲突从 PR 阶段提前到开工登记时暴露，纯文本比对几乎零成本。定位要清楚：锁只提前暴露冲突，不解决冲突；高频撞锁文件按职责拆分（Split-First）才是方案，靠锁排队是技术债。

**配套纪律（不算门，但必须有）：** 每道门上线前做一次阴性对照——故意制造违规确认它会红；所有默认值 fail-closed。这是 !413 用一周假绿换来的，成本为零，不做没有借口。

**明确不装（第一天）：**

- 前端 test:unit 放本地 push——进程挂起/超时频发，本项目第 2 周就被迫对 agent 分支跳过；第一天就该直接放 CI。
- 双防线 alias/包装器——一层 hook + 团队公约足够；双防线是发现绕行成规模后的对策，且是 !606 递归风暴的温床。
- 业务事故税门禁群（RoleCode/toMap/JSON/429/枚举直渲等）——事故后必加、事故前不必预言；预言式的门往往防错地方。
- 元门禁——门禁数量超过 ~10 道再加，第一天没有腐化可守。
- TDD 阻断式 pre-commit——第 2-3 周团队适应门禁存在后再上；第一天就上阻断只会教会大家绕行。

最后强调一次第 6 节的使用方式：这 5 道门是**起点不是终点**。装完之后，你的门禁清单会而且应该随着事故增长——每出一次 P0/P1，走完「RCA → 加门 → 阴性对照验证」的闭环，清单自然长到适合你这个项目的样子。本项目 6 周长到 14 道，你的项目会长出自己的形状；唯一不该长出来的是假绿。

## 7. 常见疑问（FAQ）

**问：门禁这么多，会不会拖慢 AI Agent 的交付速度？**

恰好相反。本项目 fix+hotfix 占全部 2059 个已合并 PR 的 59%（1223 个），绝大多数返工都能追溯到某次「当时没有门」。门禁的真实成本不在执行耗时（已治理到可接受），而在假绿和误伤——这两项靠第 4 章的四条元规则治理。真正拖慢速度的是事故：一次 main 编译断裂阻断的是全部 10 个 Agent 的部署（!2012 阻断第 77 次部署）。

**问：能不能抄一份成熟项目的门禁清单直接用？**

可以抄「结构」，抄不了「内容」。本项目的门禁内容几乎全部由本项目的事故催生——CO-373 的 RoleCode 直调、CO-469 的 JSON 序列化、spec-024/033 的 hasAnyRole 双轨，换个项目一个都不会中。能直接抄走的是元规则：fail-closed、阴性对照、棘轮口径、逃生阀留痕、按变更范围执行，以及第 6 节的 5 道 Day-1 门禁。

**问：多 Agent 并行才需要这套东西吗？单 Agent 呢？**

多 Agent 把事故频率放大了（撞号、工作区污染、并行冲突是 10 个 Agent 并行下的必然事件），但门禁的价值不依赖 Agent 数量：编译门、分支历史保护、迁移不可变、棘轮这四道在单 Agent 项目同样是投入产出比最高的。单 Agent 可以省掉的是 agent-locks 和撞号检测，其余照装。

**问：团队抵触门禁怎么办？**

本项目的经验是三条：①误伤要快修——hook 误判（2848446dd）当天修，并给出 `// SAFE:` 豁免通道，误伤不修团队就会学会讨厌门禁；②阻断要有合规出口——P0 通道制度化之后，没有人需要砸门；③门禁争议最大的 TDD 阻断门（37a717b77）是在体系运行约 10 天后才从警告升级为阻断的——先警告后阻断，让团队先适应门禁存在，比第一天硬拦有效。

**问：门禁失效怎么发现？靠巡检吗？**

靠阴性对照 CI 化，不靠人。本项目发现门禁失效的方式全部是事故（!413 是周末复盘时发现，BSD sed 假绿是第 18 次部署事故发现）——这本身就是「没有阴性对照」的代价。正确做法：每道门装的时候写一对用例（正例放行、反例拦截），门禁超过 ~10 道后加元门禁定期检查门禁脚本自身的声明与实现是否一致（check-guard-consistency.sh 模式）。

## 8. 十条经验速查

1. 门禁默认值必须 fail-closed，每道门配阴性对照测试——一个 `:-0` 让 14 道门装了一周从未生效（!413）。
2. 假绿比没门更危险：跨平台脚本禁用 GNU/BSD 特定扩展，关键提取逻辑加非空断言（BSD sed 撞号假绿）。
3. 门禁/hook 调用链必须无环，自动化辅助 push 显式跳过门禁；防自锁——门禁不能阻断修复它所发现问题的 PR（!606、ece7ce90a）。
4. 事故 → RCA → 门禁 → 防复发验证的闭环，是 fix 占 59% 的项目的不二解法；lessons-learned 61 条逐条对应门禁，同一事故绝不再犯第二次。
5. 棘轮式门禁是处理存量债务唯一可持续口径：白名单只减不增、达标摘除、新代码零容忍；反例 RULE 13 被迫 DISABLED，等于没门。
6. 门禁耗时就是项目吞吐：按变更范围执行、合并 mvn 调用、分支分级跳过；重测试门禁第一天就该放 CI。
7. 绕过通道收窄到一个合规口：显式命名逃生阀 + bypass 日志留痕 + PR 审查检查日志。
8. P0 紧急通道与日常门禁分离：hotfix SLA + 不可跳项写死（ArchUnit/Flyway 永不跳），避免第一次 P0 就是门禁体系的第一次崩塌。
9. 门禁超过 ~10 道必须加元门禁（守卫一致性 / 测试入口覆盖），防体系性假绿。
10. 文件锁只提前暴露冲突，不解决冲突：高频撞锁文件按职责拆分（Split-First），靠锁排队是技术债。
