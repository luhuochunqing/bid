# 06｜下一个 AI Coding 项目的行动清单

> 本章是全书各章 Day-1 清单的汇总与排期。细节与证据请回到对应章节。
> 原则：**第一天少装、装对、验证生效；其余交给事故驱动生长。**

## 阶段 0：开工第一天（必装）

### 协作底盘（详见 [02](02-multi-agent-collaboration.md) §2.6）

- [ ] 分支协议：`agent/<name>/<task>` 命名 + 每 agent 一个持久 worktree + 主工作区只做集成
- [ ] 早操 SOP：开工强制 `git fetch && git rebase origin/main`（冲突成本左移）
- [ ] 收尾 SOP：一键脚本（合入检查 + 锁清理 + 切回锚点），内置 janitor
- [ ] per-task 文件锁（不要共享单文件锁——每次 rebase 必撞，会被集体无视）
- [ ] 每日 push WIP 纪律 + `who-touches` 式查询（协调信号用 git 事实，不用静态所有权表）
- [ ] 一套统一开发环境（端口/DB 唯一），禁止 per-agent 端口和数据库
- [ ] Flyway 版本号集中取号（预约 + 撞号检测 + 已发布不可变三合一）

### 最小门禁 5 道（详见 [04](04-quality-gates.md) §6）

- [ ] 编译门禁（pre-push 必过；投入产出比最高，!2012 证明缺它 main 会断）
- [ ] 分支历史保护（防 force-push 覆盖；#224 类损失不可恢复）
- [ ] Flyway 三合一简单版（本项目 P0 最密集来源）
- [ ] 架构分层 ArchUnit 核心子集 + Service 行数棘轮（棘轮第一天装 = 零存量）
- [ ] agent-locks 冲突检查
- [ ] **装门当天做一次故意违规验证**（阴性对照），默认值一律 fail-closed——!413 的 `:-0` 让 14 道门建成一周从未生效

### 透传范式组件（详见 [03](03-passthrough-pattern.md) §3.7）

- [ ] 后端：`BusinessException.userMessage` + `GlobalExceptionHandler`（只路由不加工）+ 纯核心消息安全判定（五道检查：长度/SQL 关键字/包路径/堆栈痕迹/CRLF）+ 统一 `ApiResponse.msg`
- [ ] 前端：axios 拦截器 `response.data?.msg` 优先弹窗 + blob 下载错误先转 JSON + `skipGlobalErrorMessage` 逃生口
- [ ] TraceID：入站 Filter + 出站注入器 + 异步 MDC 装饰器 + CORS 白名单同步
- [ ] 用集成测试锁死透传链——透传的退化都是静默吞消息，没有测试必然回潮

### 纪律条文（详见 [05](05-rollback-discipline.md)）

- [ ] 恢复被回退代码一律 cherry-pick，禁止手工重写（保 author、保 blame）
- [ ] revert PR 必须写清"撤销什么/保留什么" + 附守护测试
- [ ] 修 bug 先取证（日志/traceId/DB），禁止无铁证改代码
- [ ] 同根因二次复发 = 强制根因分析 + 强制抽象/强制 lint 规则（详见 [01](01-bug-root-causes.md) §3）

## 阶段 1：第一周（防已知高发模式）

针对 [01](01-bug-root-causes.md) 频次 Top 5 模式各装一道防线：

- [ ] **权限语义分散（177 例）**：权限点常量化 + 所有 Controller 类级 `@PreAuthorize` + ArchUnit 强制 + 安全默认拒绝（禁止 `default→STAFF` 式宽容 fallback）+ 权限矩阵文档化
- [ ] **文件链路断裂（125 例）**：统一上传/下载封装（禁各页面自写 XHR/Blob）+ 文件类型 magic number 校验 E2E
- [ ] **外部系统契约靠猜（113 例）**：外部 API 契约机器化（OpenAPI/黄金样本契约测试）+ "code:0 不代表成功"验收铁律 + 联调不止步于"本地测试绿"
- [ ] **前后端契约无单源（108 例）**：枚举/字典以后端为唯一源 + 字段级 round-trip 契约测试（防"假保存"）
- [ ] **并行合并病（89 例）**：阶段 0 的左移纪律 + 同步远端改动一律 cherry-pick，禁止 merge/覆盖

## 阶段 2：持续运转（闭环与预算）

- [ ] 事故闭环：事故 → RCA → 门禁 → 防复发验证（门禁这样长出来，不预言式设计）
- [ ] 修复预算：产能规划按"fix 占六成"预留；设 integrator 角色专司集成与发布
- [ ] 门禁性能预算：按变更范围执行、分支分级跳过、重测试放 CI——2059 个 PR 规模下每道门省 1 分钟 = 救回数百小时
- [ ] 棘轮口径处理存量债：白名单只减不增、新代码零容忍（反例：RULE 13 因存量违规整体 DISABLED = 没门）
- [ ] 元门禁：门禁超过约 10 道后，给门禁本身加自检（逃生阀留痕、hook 无回环、脚本跨平台——macOS BSD sed 不兼容 GNU 语法曾让撞号检测长期假绿）
- [ ] PR 元数据纪律：正文必填根因/证据——本项目约半数 PR 正文是空模板，严重削弱事后归因
- [ ] P0 逃生阀：显式命名 + bypass 留痕；ArchUnit/Flyway 划为永不可跳

## 明确别做（交过学费的）

- 别搞 per-agent 端口/数据库（环境撕裂，联调地狱）
- 别搞一任务一 worktree（管理成本爆炸）
- 别搞共享单文件锁（摩擦成本定律，必被无视）
- 别搞静态任务所有权表（会腐烂，用 git 事实）
- 别预言式装业务门禁（等事故来，装得快就行）
- 别让 AI 用 Mock 兜底当"修复"（假数据会污染生产库，!1350）

---

**一句话总纲**：事实单源化、信号透传化、冲突左移、门禁最小化但必验证、修复先取证、回退留证据。
