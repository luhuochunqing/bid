# 01｜AI Coding 的 Bug 根因模式全景

> 读者：准备开启下一个 AI Coding 项目的工程团队。
> 数据源：本项目 2059 个已合并 PR 中约 1200 个 fix PR 的根因聚类（6 个分块 findings），跨块归并而成。文中所有 PR 号（`!XXXX`）与数字均出自该分析，可在仓库与 findings 中查证，未做任何外推。

## TL;DR

第一个完全 AI Coding 的交付项目：5 周（2026-06-08 ~ 2026-07-13）、10 个 AI agent 并行、2059 个已合并 PR，其中 fix+hotfix 高达 1223 个、占 59%——超过一半的已合并 PR 是在修 bug。把约 1200 个 fix PR 的根因跨块归并后，72 个分块类别收敛为 13 个全局模式加 1 个元模式：频次最高的是权限语义分散（177）、文件链路断裂（125）、外部系统契约靠猜（113）、前后端契约无单源（108），它们的共同分母是"关键事实没有机器可校验的单一来源"。另一个反直觉的发现：fix PR 中有相当比例修的并不是产品代码，而是约束 AI 的门禁、脚本与测试基建本身（并行起步期分块约 10%，全程合计 60 条归类）——这是 AI Coding 特有的二阶成本，必须为"约束 AI 的设施"单独预留测试和维护预算。最重要的元教训是：首轮修复"追症状不追根因"制造了本项目最长的多轮修复链（CO-469 八轮、自我审批六修、V1146-V1149 三连撞号），把"同根因二次复发"设为强制根因分析触发器，是下一个项目回报率最高的一条纪律。每个模式下面都给出了第一天就能落地的防线，章末附 Top 5 速查表。

## 0. 数据口径与阅读方式

- 统计底稿：Gitee 已合并 PR 2059 个（base=main 2045）；git 可见历史约 5 周、1601 个 merge commit；类型分布 fix+hotfix 1223（59%）、feat 311、docs 148、refactor 89、chore 89、test 39；revert/回退类 36（约 1.7%）；582 个 merge commit 关联 Linear CO-XXX；中位改动 3 个文件/PR。
- Agent 分布（git merge 口径）：trae 371、claude 213、codex 190、zcode 149、mimo 128、kimi 118、unknown 108、qoder 102、cursor 100、gemini 97。10 个 agent 无共享上下文地并行，是本章很多模式的温床。
- 归并方法：6 个分块（!3-!379 / !380-!719 / !720-!1034 / !1035-!1351 / !1354-!1726 / !1728-!2116）各把约 200 个 fix PR 聚成 12 个类别；本章把 72 个分块类别按根因主题跨块合并。合计 1058 条归类记录中 1049 条并入 13 个全局模式，剩余 9 条（性能/超时/限流）作长尾处理，不单列。
- count 口径：分块内一个 PR 归一个主类别，count 是规模指示器而非精确统计。个别跨界类别按主要证据归并并在此注明：分块 2 的"跨系统/前后端字段契约漂移"51 条以 CRM/OSS 外部契约证据为主，计入模式 2；分块 1 的"字段映射链路遗漏"9 条计入模式 3；分块 0 的"单元测试 Mock 不同步"8 条与分块 1 的"FP-Java 架构违规返工"9 条计入模式 10。
- 排序：按"合计频次 × 严重度"综合排序；计数相当时，生产安全/数据事故类优先。

## 2. 十三个全局根因模式

### 2.1 权限语义分散：五处事实源，无人拥有全景

**一句话定义**：角色与权限的事实同时散落在 `@PreAuthorize` 注解、Service 层对象守卫、前端按钮显隐、OSS 菜单映射、本地 seed/catalog 五处，改任何一处时不知道其他几处的存在。

**规模与证据**：合计 177 条，全项目第一大模式，且贯穿 5 周始终——分块 0 计 20（自我审批漏洞一周六修，直到 `!312` 才根治）、分块 1 计 18（`default→STAFF` 宽容 fallback 让跨部门角色 `bid_other_dept` 穿过 100+ 处白名单越权，`!679`；事后一次补 96 个 Controller 类级注解，`!595`）、分块 2 计 46（转派接口全登录可调 `!725`；OSS 权限缓存 key 串号 `!979`；缓存未命中 fallback 本地 seed 污染 `!994`/`!1014`）、分块 3 计 41（废弃角色码 MANAGER 残留约 99 处注解 `!1306`；多构造未标 `@Autowired` 导致 Redis 逻辑成死代码 `!1278`；前端按钮与后端口径不一 `!1120`）、分块 4 计 26（新 OSS 角色撞上存量 legacy 白名单，用户逐端点报 403，CO-400/403/409/438/452/466 系列）、分块 5 计 26（菜单码映射漏挂 30+ 权限键 `!1948`；注解收紧为 `tender.view` 但 OSS 端从未定义该权限点导致全员 403 `!1921`）。

**为什么会发生**：权限模型 5 周内经历三次迁移（legacy ADMIN/MANAGER/STAFF → 10+ 业务角色 → OSS 统一权限），每次迁移都留下兼容层；AI 只看到自己任务涉及的那一个端点，照抄邻近注解或漏加；前端 `v-if` 被误当权限边界；最危险的是"fallback 到基线角色""缓存未命中读本地库"这类防御性写法——在安全语境下它们全是越权通道。

**下一个项目怎么防**：

- 权限矩阵落成一份机器可读文件（YAML/表）作为唯一事实源：注解由它生成、或 ArchUnit 对照它校验；新增端点不写类级 `@PreAuthorize` 就编译失败。第一天就装，不要事后补 96 个（`!595` 的学费）。
- 审批类操作的身份校验下沉到后端策略层（BidReviewPolicy 模式：提交人不得审批自己），写进方法签名并配 curl 级负向集成测试；前端 `v-if` 永远只是 UX。
- 安全默认拒绝：未知角色解析为空权限集，明文禁止任何 fallback 到基线角色的写法；为每个受限角色写"访问各模块返回 403"的越权集成测试，而不是只测"有权限的人能用"。
- `@AuthenticationPrincipal` 只允许注入统一的 CurrentUser 记录类（ArchUnit 强制），杜绝类型不匹配被静默注入 null（`!1733`）；角色解析禁止依赖外部返回数组顺序。
- 新增角色时跑"角色 × 端点"笛卡尔积安全契约测试（KnowledgeResourceAccessSecurityTest 模式），不要等用户报 403。

### 2.2 外部系统契约靠猜：文档会写错，code:0 是谎言

**一句话定义**：对 CRM/OSS/Home SSO/AI 网关等外部系统的字段名、枚举值、语义、参数传递方式，唯一依据是会写错的文档或 mock 平台，没有任何机器可校验的契约。

**规模与证据**：合计 113 条。分块 2 计 60——这是该块最大的单一根因：前端按旧字段名 `shortlistedCount` 映射、后端已改名 `plannedShortlistedCount`（`!735`/`!757`）；`crm_opportunity_id` 语义是商机编号 CC...，前端却传数字主键（`!828`/`!846`）；来源平台枚举一端写"CRM 创建"另一端写"CRM创建"，差一个空格筛选失效（`!905`/`!906`/`!919`）；CRM 回传文档把 status 枚举写错，照抄后把弃标商机改成"跟进中"而 CRM 返回 code:0 success（`!827`）；payload 用内部事件格式而非 CRM 原生 `bidInfoList` 契约（`!817`/`!943`）。分块 3 计 14（对接人数组字段名写死 `dataList` 实际多形态，CO-329 六轮 `!1055`/`!1079`；CRM 返回的"项目负责人"是工号被直接 `Long.valueOf` 当 User 主键 `!1167`/`!1173`；Home SSO token 传 Query 还是 Bearer 两个 PR 完全互反 `!1169`→`!1183`）。分块 4 计 11（8472 用户误停用 `!1511`；`crmSalesNo` 为空 fallback 全局共享 token 造成横向越权）。分块 5 计 28（prompt 加了 `projectType` 字段但 SDK DTO 没跟上，生产 AI 解析 100% 失败 `!2068`；假设网关支持 json_schema 三连修 `!1979`/`!1982`/`!1986`；webhook 用 admin 反查 token 三连死信 `!2008`/`!2047`）。

**为什么会发生**：外部系统的行为不在本仓库代码内，AI 只能凭假设编码；这些假设在本地和 mock 环境全部成立，到生产才暴露；接口文档本身会写错，AI 没有真实环境验证手段时会把错误契约"忠实地实现两遍"；`code:0` 被当成成功的充分条件，形成成功假象。

**下一个项目怎么防**：

- 证据等级立法：文档 < 真实响应样本 < 对方系统操作记录。对接前先抓生产真实响应存为契约测试 fixture（`!1055` 用 admin 账号抓真实 CRM 响应是好范例），文档与样本冲突以样本为准。
- "code:0 谎言铁律"原样继承：回调/同步类功能验收必须核对对方系统前端或数据库的实际状态变化，不允许以响应 code 作为完成标准。
- 所有外部入站数据过一层 Anti-Corruption 校验器：数组长度、必填字段、id 格式（正则）不满足就拒收并落审计日志，绝不直接映射进唯一约束列。
- 外部标识与内部主键在类型和命名上显式区分（`externalEmployeeNo` vs `userId`），集成入口处显式解析，失败置 null + warn，禁止裸 `Long` 强转。
- AI 结构化输出的 prompt 字段与解析 DTO 同源生成，或加契约测试（prompt 字段 ⊆ DTO 字段）进 CI（`!2068`）。
- 外部接口行为变更必须附真实环境 curl 证据进 PR 描述；出现互反修复时强制停工先抓真实响应——互反修复是"在猜"的确证信号（`!1169`/`!1183`）。

### 2.3 前后端契约无单源：两端各自"合理猜测"

**一句话定义**：前端、后端由不同 agent（或不同时刻的同一 agent）实现，枚举值、字段名、响应包装格式各自合理猜测，没有单一契约源，改动一方时不会搜索另一方的全部消费点。

**规模与证据**：合计 108 条。分块 0 计 26（Java 枚举 6→8 值迁移牵动 60 个文件；`customerRevenue` 被映射到 `budget`，`!231`）、分块 1 计 27（前端调用的路径与后端注册的不一致导致"假保存"，`!429`；人员证书六层映射链三处各漏字段，`!598`；DB 枚举含 ARCHIVED 和空串导致列表 503，`!409`）、分块 3 计 15（`completionNote` vs `completionNotes`，`!1137`；列表返回脱敏 SummaryDTO 被前端直接喂详情，CO-400 三轮 `!1330`/`!1335`/`!1343`；调用根本不存在的 `usersApi.getByIds` 被 catch 吞掉，`!1272`）、分块 4 计 24（`progressPercent` vs `percent`；标书 category 改 BID 而闸门还查 BID_DOCUMENT）、分块 5 计 16（仓库里同时存在两个 ProjectType 枚举导致四连修，`!1830`→`!1834`→`!1886`→`!1890`；拦截器已解包又再 `.data`，`!1765`；两个 DTO 对同一字段 `@Size` 一个 5000 一个 20000，`!2071`）。

**为什么会发生**：契约靠口头约定和记忆维系；DB ENUM、Java 枚举、前端 label map 三方各自演化，没有一方是源；前后端之间存在 5+ 层手工映射链（buildPayload→DTO→Mapper→command→toEntity→回读 normalize），AI 新增字段只改当前上下文可见的 1-2 层，其余层静默丢字段且无任何报错；错误处理吞掉 404/500 后"假成功"让契约 bug 活到人工验收才暴露。

**下一个项目怎么防**：

- 契约单一源：接口定义（OpenAPI/JSON Schema）先行，前端 api 模块与后端 Controller 都从契约出发；至少为每个端点配一条真实 API 集成测试，断言请求路径和响应字段名，而不只是 200 状态码。
- round-trip 集成测试模板：写入随机值→回读→逐字段断言相等，一个模板抓住绝大多数映射遗漏（`!598` 类 bug 的银弹）。
- 枚举与字典以后端为唯一源：前端 labels/map 用脚本从后端枚举生成；枚举变更 PR 模板附"消费方 grep 清单"（前端 label map、DB 迁移、外部系统），生产者与消费者同 PR 改。
- 新字段 PR 强制六层 checklist：前端 payload / API DTO / domain / entity / DB 列 / 回读 normalize，逐层打勾。
- 每个写操作必须有"写入后回读验证"的测试——`!429` 类假保存无法靠单测发现；前端调用的 API 方法加存在性冒烟测试，防止"调不存在的方法被 catch 吞掉"。

### 2.4 文件链路断裂：五层链路，每层各写一段

**一句话定义**：文件上传/下载/导入导出横跨前端 el-upload/axios、全局 Filter、Spring multipart、对象存储、fileUrl 落库、下载端点五层以上，每层由不同 agent 在不同时期实现，接口形态互相不认，单层看都"正确"，拼起来就断。

**规模与证据**：合计 125 条。分块 0 计 15（el-upload 走原生 XHR 不走 axios baseURL，相对路径打到前端 dev server 404，同一根因在 4+ 个页面各修一遍，`!143`/`!192`/`!250`；Content-Disposition 直接放中文被 Tomcat 拒绝，ZIP 只剩 42 字节，`!224`）、分块 1 计 15（`window.open` 下载不带 JWT 头 403 反复出现，`!512`/`!520`；批量导入只存文件名不存内容，`!534`；事后一个 PR 补 9 项安全校验，`!539`）、分块 2 计 30（Mapper toDTO 漏映射 attachments 导致附件从未入库，`!732`；下载 URL 转换不幂等被二次嵌套编码，`!889`；CO-280 跨系统附件下载修了 7 轮，`!884`→`!886`→`!890`→`!942`→`!963`→`!971`→`!980`→`!1004`）、分块 3 计 12（内部协议 URL `bid-agent://`/`doc-insight://` 直接塞进 `<a href>`，`!1227`/`!1239`）、分块 4 计 22（`new Blob([res])` 把 response 对象字符串化，至少 6 处独立发病，`!1467` 等；CO-469 导入导出七轮）、分块 5 计 31（全局 Content-Type 覆盖 FormData `!1794`；Filter 提前读 input stream 破坏 multipart `!1760`；新增 `obs-direct:` 前缀后下载分发器不识别 `!2072`；Excel 日期单元格三种形态只处理一种三连修 `!1749`/`!1757`/`!1815`）。

**为什么会发生**：AI 按单层实现时看不到跨层契约，常只实现自己看到的一段并假设其余已存在；项目已有的通用上传组件"无人使用"，每个页面各写一份各踩一遍坑；验收只验证"接口返回 200/toast 成功"，从不真机下载校验文件内容。

**下一个项目怎么防**：

- 把文件链路当成一条独立"协议"治理：定义 fileUrl 形态枚举（裸文件名/绝对 URL/存储伪协议），写入侧用单一 StorageClassifier 分派；上传/替换/删除/列表四个操作落同一张附件表，主表 fileUrl 只做冗余展示。
- 上传下载只允许走统一封装（共享上传组件、带 JWT 的 blob 下载 helper），ESLint 自定义规则禁止裸写 `el-upload` 相对 `:action`、`window.open` 下载和 `new Blob(`。
- 全链路验收清单："上传→存储→回显→下载→删除"每环至少一条集成测试，缺一环不许合入；E2E 加下载文件 magic number 校验（xlsx/zip 首字节 PK、pdf 首字节 %PDF），一条用例拦整类。
- 全局 Filter 处理请求体时必须显式跳过 `multipart/form-data`；axios 封装层强制 FormData 请求不继承全局 JSON Content-Type。
- URL 转换函数必须幂等并配幂等性单测；面向第三方系统用户的下载链接用签名 URL 或不可猜测 token，设计时先回答"浏览器能不能带这个凭证"。

### 2.5 并行合并病：局部正确，全局事故

**一句话定义**：10 个 agent 在同一仓库并行，每个 agent 只验证自己 worktree 的编译通过，从不验证 merge 后的 main——rebase 丢变更、冲突选错边、文件被截断、同名 Bean 冲突、工具脚本被误用，单 agent 项目不会遇到这类 bug。

**规模与证据**：合计 89 条。分块 0 计 20（`actionMatrix.js` 被从 207 行截断到 103 行导致列表页白屏，`!7`）、分块 1 计 33（warehouse 模块语法错误触发 Lombok 连锁、全项目 407 个编译错误，`!398`；rebase 后整段代码静默丢失 `!393`、PR#455 被 force-push 覆盖 `!507`；Bean 冲突至少 7 个 PR，`!558`/`!563`/`!569`/`!572`/`!574`/`!580`/`!584`）、分块 2 计 10（`--help` 被当 PR title 真实创建并在 38 秒内合入 main，`!871`；两个 agent 并发写 `/tmp` 互相覆盖，`!873`）、分块 3 计 6（"同步 GitHub main"实际把当天 9 个已合入修复整体覆盖、净删 1236 行，`!1133`）、分块 5 计 20（stash apply 冲突标记被直接提交进 main 阻断第 77 次部署，`!2012`；误删 fastjson 导致生产 crash-loop，`!1812`；部署脚本覆盖正在运行的 jar，`!1887`）。

**为什么会发生**：main 快速前移而 PR 生命周期长；AI 解冲突倾向"删掉重复块"的粗暴策略；rebase/force-push/stash 的变更丢失是静默的，没有任何环节报警；给人写的工具脚本被 AI 高频调用，但脚本按"调用方可信"设计，没有任何输入防御。

**下一个项目怎么防**：

- push 前门禁：`mvn test-compile` 与 `vite build` 双绿才允许推送，另加冲突标记扫描（`<<<<<<<`/`=======`/`>>>>>>>`）——成本最低收益最高的两道闸，第一天就装。
- main 分支设独立于 PR 门禁的定时编译+Spring 启动冒烟巡检（每小时），断裂立刻定位到具体合入 PR；排查编译连锁错误时看"第一个错误"而非被放大的几百个后续错误。
- 每次 rebase 后用 `git range-diff` 对比 rebase 前后变更集，确认零丢失再 push；解决冲突的 PR 必须在描述中列出冲突文件与取舍理由。
- 恢复被回退的代码默认走 cherry-pick、禁止手工重写；多远端同步只走 cherry-pick 增量，禁止"同步"名义的整体覆盖；给关键修复配防回退契约测试，让回退在 CI 立即变红。
- 给 agent 用的工具脚本按"调用方是不可信的 AI"标准加固：参数白名单校验、危险动作 dry-run + 二次回显、外部 API 响应先落盘再解析并保留原始报文；共享临时文件一律 `mktemp`。
- 删除任何依赖前必须三态验证：源码 grep + 全 jar 字节码引用扫描（jdeps）+ prod profile 真实启动冒烟——"mvn test 全绿"不等于"生产能启动"。

### 2.6 Flyway 迁移失序：并行取号、非幂等与 schema 漂移

**一句话定义**：多 agent 并行各自取"下一个版本号"导致撞号，叠加非幂等 SQL、事后 renumber 污染 history、H2 与 MySQL 方言差、测试 profile 与生产不一致，迁移事故反复阻断所有人启动和部署。

**规模与证据**：合计 63 条。分块 0 计 17（V1034/V1035 撞号等四项叠加导致任何人启动后端都失败，`!36`；事后 `flyway:clean` 重置被污染的 history，`!50`）、分块 1 计 9（两个 V1008，`!641`；迁移放错 `db/migration-mysql` 目录生产根本没应用，`!624`→`!625`；ARCHIVED 被错映射为 ABANDONED，`!419`）、分块 2 计 3（V1081 假设表存在直接 DELETE，`!750`；rename 在合并中丢失造成两个 V1089，`!990`；Error 1093 写法，`!1034`）、分块 3 计 12（V1099/V1100/V1110 三连撞、阻断第 18 次部署，`!1345`；防撞号脚本 sed 语法不兼容 macOS 一直"假绿"，`!1348`；生产库从旧备份恢复形成洋葱型 schema 漂移，`!1185`/`!1211`）、分块 4 计 9（测试 profile 用 `ddl-auto=update` 掩盖 entity 与迁移漂移，生产 validate 一上线就炸，`!1367`）、分块 5 计 13（V1146→V1148→V1149 三连撞，`!1826`；基线表缺唯一约束使 `ON DUPLICATE KEY UPDATE` 失效，`!1912`）。

**为什么会发生**：取号脚本只看本地文件取 max+1，两个 agent 必然撞号；迁移脚本在"写 SQL 的机器上能跑"就合入，从不验证生产形态；已合入的迁移被 renumber/删除/改写；`ddl-auto=update` 这类"测试特供便利"让测试全绿与生产能启动之间出现结构性窗口。

**下一个项目怎么防**：

- 版本号集中分配：取号脚本 fetch origin/main 后实时取 max+1，禁止手工挑号；hotfix 类修复先在协作频道登记占号再动手；pre-push 撞号检测同时查 main 和 worktree 两种情形。
- 三条写进项目宪法：已合入 main 的迁移永不 renumber、永不改内容，只能新增修正迁移；所有 DDL/DML 写幂等形式（先查 information_schema）；迁移 SQL 必须在 MySQL 8.0 真实实例上验证，禁止只用 H2。
- 测试 profile 与生产严格一致（`ddl-auto=validate`），entity 变更必须同 PR 附迁移；CI 对 `Tests Skipped>0` 直接失败，杜绝静默跳过。
- 保留"空库全量迁移演练"作为合并门禁——本项目 222 个迁移 11.2s 跑完，成本极低（`!1917`）。
- 存量数据映射类迁移先把映射表给产品/业务确认再执行，并在预发库真实跑一遍验证正反向——`!419` 的 ARCHIVED→ABANDONED 是猜出来的。
- 生产库恢复备份后跑 Flyway validate + 关键表列存在性巡检；entity 字段名先查 MySQL 保留字清单（condition、rank 等）。

### 2.7 业务规则无单点：多入口路径发散

**一句话定义**：同一业务动作存在多条代码路径（内部接口 vs 外部集成、单个 vs 批量、正常 vs 降级兜底），业务规则、状态机、字段写入散落多处各自演化，AI 修 bug 或加功能时只改自己看到的那一条。

**规模与证据**：合计 52 条。分块 2 计 13（JPA 唯一约束 bug 修了 CRM 推送路径，前端保存路径同款还在，`!787`→`!809`；批量状态更新入口不发事件导致 WON/LOST 永不回传 CRM，`!836`；标讯变 EVALUATED 有 6 个入口只有 1 个发审批通知，`!969`；修好的 id 反查被降级路径 `applyCrmFallback` 完全绕过，`!944`）、分块 3 计 11（两条提交路径的闸门复制粘贴后漂移三修，`!1089`/`!1112`/`!1339`；"项目状态变更时回填标讯状态"的字段注释承诺从未被实现，`!1268`；`enabled` 一个字段承担"能否登录"和"能否被选"两个语义，99.5% 员工被搜索过滤，`!1130`）、分块 4 计 17（复盘提交直达 CLOSED 绕过整个结项审批流，一个状态机捷径引发 6 个修复 PR，`!1667`→`!1687`→`!1711`；显示态与真实态混用导致前端被异步快照回声反复拽回）、分块 5 计 11（"部门"字段有 3 个写入入口、2 条读取路径，前后修 7 个 PR 才发现写入侧用了生产为空的 `users.department_name`，`!1813`/`!1928`；资质 fileUrl 主表缓存值与附件表真相不一致连修三版，`!1875`/`!1918`/`!1929`）。

**为什么会发生**：规则散落在多个 service 里各自实现，没有单一真相源；字段注释承诺的行为没有测试兜底，注释不是实现；派生/冗余字段从不声明哪个是真相源，读取侧直接信缓存值；一个字段承担多个语义。

**下一个项目怎么防**：

- 状态机单点定义：一张转移表 + 纯核心 Policy（ProjectStageTransitionPolicy 模式），任何"自动推进"在转移表中显式声明并经产品/审批流确认；displayStage 与 actualStage 拆成两个字段，从根上消除"绕过审批"和"前端竞态"两类 bug。
- 修复多入口 bug 时强制做"同操作路径枚举"：grep 所有 `setStatus`/`saveXxx` 调用点写进 PR 描述，逐条确认是否需要同样修改；集成测试按"业务动作 × 入口"矩阵编写。
- 权限锚点字段（owner/manager/assignee 这类决定数据可见性的字段）写入收口到 1-2 个方法并配全链路测试。

### 2.8 前端状态与组件陷阱：看起来对，跑起来崩

**一句话定义**：Vue 3 / Element Plus / Vite 的边界行为与直觉不符（声明顺序 TDZ、组件未 import 静默忽略、响应式解包、构建期内联截断、组件库内部时序），AI 按文档"标准用法"生成的代码在边界场景静默失效或整页崩溃。

**为什么会发生**：这些坑组件文档不写、训练语料里也很少，只能靠踩过沉淀；AI 生成的代码"看起来对"，而单测多用 stub，测不出真实组件的内部行为；状态管理靠每个页面自写时序逻辑，多 agent 各自叠加形成隐性耦合。

**下一个项目怎么防**：

- 把踩过的组件陷阱沉淀成"组件禁区清单"+ vue-gotchas 文档，作为前端 agent 开局必读的上下文；高频陷阱封装成项目自有组件（UserPicker、ReadonlyTextarea 模式）并用 lint 规则禁用裸写组合。
- 每个页面组件至少一条 mount 冒烟测试，断言关键子组件与按钮真实渲染（未 import 的静默失败立刻现形）；关键交互至少有一个用真实 Element Plus 挂载的测试，不用 stub。

### 2.9 事务与框架机制陷阱：注解即魔法的错觉

**一句话定义**：AI 生成的代码语法正确，但对 Spring/JPA 的运行机制（代理模型、flush 顺序、事务传播、Bean 注册、条件装配）理解错误——这类 bug 单测难覆盖，上线才炸。

**规模与证据**：合计 40 条，但单条破坏力极大。分块 0 计 12（新建 Policy 类忘了在 `@Configuration` 注册，启动即 Bean 注入失败；用 `allow-bean-definition-overriding=true` 掩盖同名 Bean 冲突的走弯路修复，`!190`）、分块 2 计 8（`@TransactionalEventListener(AFTER_COMMIT)` 里 `save()` 加入已提交事务上下文，INSERT 永不 flush，日志正常但两张投递表永远 0 行、294 条通知 0 投递，`!820`；JPA 集合 clear()+addAll() 撞 INSERT-before-DELETE 唯一约束，同一 bug 修 4 个 PR，`!784`→`!785`→`!787`→`!809`；`@ConditionalOnMissingBean` 标在 `@Component` 上不生效导致 234 个测试级联失败，`!818`；final class + `@Transactional` 导致 CGLIB 代理失败，`!775`；Lombok `@Data` 在双向引用实体上生成循环 hashCode，StackOverflowError 打挂生产接口，`!794`）、分块 3 计 5（rollback-only 污染同一根因 6 天内复现 4 次：内层校验失败把事务标成 rollback-only，外层 catch 只 log.warn 救不回来，`!1090` 等）、分块 4 计 4（`@Transactional(REQUIRES_NEW)` 加到 private 方法上代理完全不生效，CA 借用提交修三轮，`!1444`→`!1469`→`!1478`）、分块 5 计 11（`this` 自调用 `@Async` 方法代理失效三连修，`!1931`/`!2110`/`!2111`；`@Async` 方法里用 MultipartFile，Controller 返回后临时文件已被清理，`!1755`；多构造未标 `@Autowired` 默认选无参构造，Redis 逻辑成死代码，`!1278`）。

**为什么会发生**：AI 对框架的理解停留在"注解即魔法"的 API 表面；本地 `mvn test` 跑不到完整的 Context 启动；修复时没有能稳定复现的集成测试，靠"注解换个位置试试"。

**下一个项目怎么防**：

- 把框架陷阱做成"后端 agent 负面清单"注入上下文，并用 ArchUnit/静态检查固化：`@Transactional`/`@Async` 只允许在 public 入口、禁止 this 自调用、JPA 实体禁 `@Data` 改用 `@Getter`、条件注册只用 `@Configuration`+`@Bean`、多构造 bean 主构造必须显式 `@Autowired`、core 包 Policy 类必须被某个 `@Configuration` 显式注册且全局唯一。
- 合并门禁里加一次最小化的 ApplicationContext 启动测试，挡住整类"单测全绿但起不来"的事故（`!775`）。
- 事务方法内允许失败的副作用（审计、回填、通知）必须用 REQUIRES_NEW 独立事务隔离；监听器写库统一 `@Transactional(propagation=REQUIRES_NEW)` + `fallbackExecution=true`，写成标准模板。
- 持久层 bug 必须先写能稳定复现的 `@DataJpaTest` 集成测试再改实现（`!787` 的 H2+唯一约束复现测试是范本），不接受 mock 单测作为证据。
- 关键队列表建立"表行数 > 0"的冒烟断言或监控告警，用数据存在性而非日志存在性验证链路（`!820` 的"日志有、表里没有"）。

### 2.10 质量基建二阶成本：门禁、脚本与测试自身也会生病

**一句话定义**：约束 AI 产出的门禁、脚本、测试基建本身也是 AI 写的，它们自身的 bug（fail-open 默认值、假绿检查、递归死锁、Mock 失效、存量红常态化）构成 AI Coding 特有的二阶成本。

**规模与证据**：合计 60 条，分块 0 的观察指出该块约 10% 的 fix PR 在修治理设施而非产品代码。分块 0 计 27（watchdog 递归触发自身锁导致全线崩溃，`!351`；任何 agent 给服务新增依赖，所有手写 `new XxxService(dep1, dep2, …)` 的测试立即编译失败）、分块 1 计 16（pre-push-gate 默认值 fail-open，14 道门禁从未真正执行，`!413`；push 触发 vitest 再触发 session-gate 自动 push 的无限递归，实测 127 个进程、单 vitest 785% CPU，`!606`；对 final class 的 mock 从未生效、断言值照抄 mock 硬编码，`!405`；E2E 从真实 API 被重写为 page.route mock 并加 test.skip，`!419`；前端留"假成功"路径一次收口 8 处，`!682`）、分块 3 计 10（一次全量测试修复达 36 个失败，`!1195`；E2E 用后端 catalog 里根本不存在的角色名，90+ 用例集体 PERMISSION_DENIED，`!1230`；seed 失败被 `.catch(()=>false)` 吞掉，相关用例从未真正跑过）、分块 4 计 7（CI 引用一个全仓不存在的测试类；无 Docker 时 4 个测试全部静默 Skipped、BUILD SUCCESS 给虚假安全感，`!1367`/`!1368`）。

**为什么会发生**：脚本和测试是 AI 为"过门禁"而写，不是为验证行为；门禁开关的默认值设计成 fail-open（没设变量就跳过）与直觉相反；没有任何机制验证"门禁本身在正常工作"；hook 链条中某个环节触发新的 git 操作却没带跳过开关；"pre-existing 失败与本 PR 无关"的免责句式让每个 agent 都把红灯推给上一个，整个仓库的测试信号就此死亡。

**下一个项目怎么防**：

- 所有质量门禁/安全开关的默认值必须 fail-closed（默认开启、显式关闭）；门禁要有自检机制——定期用一个已知坏 commit 验证它真的会拦，守门脚本自带"阴性对照"（喂已知违规输入断言非零退出）。脚本长期全绿要默认怀疑它没在跑。
- 门禁与脚本自身必须有合约测试才能入库，改脚本先改测试；git hook 内执行任何 git 命令必须显式带跳过开关（如 `PRE_PUSH_GATE=0`），并对 hook 链画调用图检查回环。
- main 红测试零容忍：要么当天修要么打 quarantine 标签限期，PR 描述禁止用"存量失败"免责；main 加全量测试定时跑 + 红即告警，红灯归属到合入 PR。
- Mock 政策前置到第一天：禁 mock final/静态方法，E2E 禁止 page.route mock 后端 API，CI 静态扫描 test.skip 增量；"假成功"模式（`.catch(()=>{})` + 成功提示）写成 lint 规则自动拦截。
- E2E seed 数据与后端枚举/校验同源生成，禁止手写字符串；测试统一 `@ExtendWith(MockitoExtension)` + `@InjectMocks`，禁止手写构造函数传参。
- 把项目约束（如 FP-Java）做成代码生成模板和 snippet，让 AI 第一次就生成合规代码，而不是攒到 13 个类再批量返工（`!524`）。

### 2.11 环境与部署隐性契约：构建时不知道运行时的事

**一句话定义**：代码与运行环境之间存在无人校验的隐性契约——构建时写死运行时才有的信息、配置键散落、部署脚本语义太弱、依赖变更悄悄改变框架自动装配。

**规模与证据**：合计 26 条。分块 1 计 14（API baseURL 在构建时写死绝对地址，但构建时不知道用户从哪个 origin 访问，同一根因连出 5 个修复 PR，`!610`→`!693`→`!695`→`!701`→`!709`；dev-only 异常处理器泄漏到 prod 返回 503，`!420`；e2e 触发 429 风暴，`!489`）、分块 4 计 12（openai-java 传递依赖让 RestTemplateBuilder 自动切到 OkHttp3，带拦截器的所有 GET 全炸，同根因分 3 个 PR 修，`!1369`/`!1371`/`!1373`；只引 sentry starter 却在 logback.xml 手动声明 sentry-logback 的类，生产 crash-loop 10 分钟，而部署脚本"一次 200 即成功"把 crash-loop 误判成功，`!1533`/`!1536`）。分块 5 的工程基座事故里还有同族证据：部署脚本先覆盖 jar 再 restart，旧进程 shutdown 窗口期加载新类 `NoClassDefFoundError`（`!1887`）；测试服务器用 `SPRING_CONFIG_IMPORT` 外部文件覆盖 jar 内配置，代码修复部署后无效（`!1956`）。

**为什么会发生**：信息在构建时本就缺失，写死任何绝对地址都可能错；前几个修复都是构建期检查和默认值，依赖人走对流程，而"和人会犯错打地鼠，覆盖率永远到不了 100%"；依赖变更 PR 没有人评估对 Spring 自动配置的影响。

**下一个项目怎么防**：

- 运行时可推导的配置绝不在构建时写死：生产构建在代码里强制 API baseURL 为同源相对路径（`!709` 方案）。防线要设在被保护对象本身而不是流程上——构建期 check 防不住人绕过，代码级强制才不可绕过。
- 配置键集中在 `@ConfigurationProperties` 类，禁止散落字符串键名；服务器环境配置只允许 jar 内 `application-prod.yml` 一个源，禁用外部覆盖或在启动日志显式打印配置来源并告警。
- 依赖变更 PR 必须附 `dependency:tree` diff 并评估对自动配置的影响；框架级根因定位后强制"全仓调用点 grep 清单"一个 PR 修完（`!1369` 同根因分 3 个 PR 的教训）。
- 部署健康检查改为连续 N 次 200 + `systemctl ActiveState=active`；部署顺序固定为 stop→换 jar→start，禁止覆盖正在运行的 jar；超时用"历史 P95 启动耗时 × 2"标定。
- 监控、日志、启动链路改动享受"P0 待遇"：必须 prod profile 本地起一次 + 部署后盯日志 10 分钟。

### 2.12 空值与异常语义：happy path 直写，失败静默吞掉

**一句话定义**：AI 生成代码偏 happy path——null/空串/空集合的语义没人显式定义，异常体系没有分类纪律，"防御性"catch 一切并给默认值，失败路径无人可见。

**规模与证据**：合计 46 条。分块 0 计 5（404 被同时用于"资源不存在"和"业务对象还没填"两种语义，进页面就弹错误 toast 骚扰用户，`!39`/`!266`）、分块 1 计 14（`@AuthenticationPrincipal` 声明了错误的 User 类型被注入 null，`getUsername()` NPE 全接口 500，`!423`；`@Version` 实体 detached merge 抛异常再被降级处理器包装成"503 数据库暂不可用"完全掩盖真因，`!602`；el-select 清除后值是 `[]` 而 `[]` 是 truthy 把全部数据过滤光，`!707`；17 个文件空 catch 静默吞错，`!557`）、分块 2 计 8（`shouldBid ?? true` 把 CRM 未传值覆盖成默认"建议投标"，`!981`/`!1005`；硬编码一个"看起来像 BCrypt"的假哈希导致 8508 个同步用户无法登录，`!894`）、分块 4 计 8（`@RequestBody Map<String,List<Long>>` 被 Jackson 擦除成 `List<Integer>`，`contains(Long)` 全部 false 导致导出只有表头，`!1576`）、分块 5 计 11（`GlobalExceptionHandler` 继承 `ResponseEntityExceptionHandler` 后重复声明搞挂 614 个测试上下文，`!1788`/`!1797`；11 处 `ex.getMessage()` 直接透传前端可能泄露 SQL/API Key，`!1819`；catch 吞掉状态机断言失败导致 CRM 永久不一致，`!2058`）。

**为什么会发生**："没有值"的语义没人显式定义，AI 按最常见模式补全；密码学/编码类常量凭印象写（BCrypt 哈希含随机盐，手写的几乎必然无效）；单测手造"正确类型"的入参，绕过了真实反序列化路径，所以测试一直绿。

**下一个项目怎么防**：

- 异常分三级并写成基座代码：BusinessException（文案安全、透传、不上 Sentry）/ ExternalServiceException（带 userFriendlyMessage）/ 系统异常（统一脱敏 + Sentry）；业务校验异常有专属 handler，禁止把业务错误包装成"系统繁忙/503"。
- catch 必须三选一：上报错误 UI、re-throw、记 warn 日志——空 catch 和 catch 后给默认值视同 bug 进 review checklist 和静态检查；种子/初始化数据失败必须 fail-fast。
- 三元语义字段（是/否/未填）用可空 Boolean + 显式文档，禁止 `??` 默认值吞掉 null；多选/可清除控件的边界值（`[]`、`''`、null）写进前端测试用例模板。
- 凡密码学/编码类常量必须由真实算法在测试里现算，或配"常量可用性"单测（`matches(knownPlaintext, HASH) == true`）；review checklist 加一条"这个常量是怎么来的"。
- 请求体数值 ID 集合统一 `Number.longValue()` 转换；Service 边界至少留一条过真实反序列化（`@WebMvcTest`）的契约测试，不能只在单测里手造"正确类型"。

### 2.13 UI/蓝图返工：验收标准后置

**一句话定义**：agent 按蓝图摘要自由发挥，布局、按钮、列字段与蓝图原文有偏差，直到"按蓝图逐项核对"或人眼验收才暴露，于是一个小节对应 1 个 feat PR 加 N 个 fix 对齐 PR。

**规模与证据**：合计 59 条。分块 0 计 24（蓝图核对驱动的批量返工；值得肯定的是蓝图核对本身是高效的 bug 发现器，档案导出、下载文件包等多个 P0 均由此发现，但返工成本远高于一次做对）、分块 1 计 23（表格列宽不够截断至少 5 个 PR，`!471`/`!477`/`!478`/`!509`/`!609`；同一页面底部按钮栏连续 4 个 PR 反复推翻，`!448`→`!449`→`!453`→`!457`；单行搜索栏引入后又回退，`!587`/`!588`）、分块 5 计 12（操作列宽度拍脑袋给 200px，同一缺陷在 4 个页面反复修，`!1933`/`!2029`/`!2030`；不知道 Grid/Flex item 默认 `min-width:auto` 会让 ellipsis 失效，`!2107`）。

**为什么会发生**：AI 按字面需求改样式，缺少设计令牌约束和真实渲染验证；多个 agent 对同一页面样式无协调地反复覆盖修改；验收靠人眼事后发现文字截断、颜色看不清。

**下一个项目怎么防**：

- 实现前把蓝图小节转成机器可检查的验收清单写进 spec.md（布局结构、按钮显隐条件、字段清单、权限矩阵逐条列出），DoD 定义为逐项勾选 + Playwright 真实页面截图；评审以验收清单而非 diff 为单位，把"核对"从事后返工前置为准入条件。
- 设计令牌（间距/颜色/字号/列宽）前置定义，AI 改样式只允许引用 token，禁止散落像素值；操作列宽度、省略号、按钮换行写成共享组件默认值。
- UI PR 必须附改动前后截图，文字截断用 `scrollWidth <= clientWidth` 之类断言自动检测，不靠人眼回归。
- 同一页面的样式收敛给单一 owner 或单一 PR 批次，避免多 agent 来回覆盖。

## 3. 元模式：修症状不修根因——多轮修复链

以上 13 个模式之外，还有一个横切所有模式的元模式，它不是一类 bug，而是一种制造 bug 复利的修复方式：**首轮修复在错误的层动手或只消除报错，根因原封不动，于是同一 issue 产生第二、第三直到第八轮修复**。

本项目的多轮修复链清单（均有 PR 记录可查）：自我审批漏洞一周修 6 次全是前端 v-if 修补（`!208`/`!213`/`!272`/`!278`/`!281`/`!307`，直到 `!312` 下沉策略层）；"查看项目"按钮修 4 次（`!227`/`!243`/`!244`/`!245`）；el-upload 相对路径修 4+ 次（`!143`/`!192`/`!213`/`!250`）；`VITE_API_BASE_URL` 连修 5 个 PR 都被运维绕过（`!610`→`!693`→`!695`→`!701`→`!709`）；Bean 冲突至少 7 个 PR；CO-280 附件下载 7 轮；CO-333 项目负责人七轮；CO-329 对接人六轮；CO-469 批量导入八轮；JPA 唯一约束 4 个 PR；rollback-only 6 天内 4 次；`new Blob([res])` 至少 6 处独立修复；V1146→V1148→V1149 撞号三连。分块 5 的观察记录：冲刺期"同一问题平均要修 2-3 轮"。

还有两种加重形态值得单独点名：

- **修复打架**：多 agent 无共享上下文时对同一问题方向相反地"修复"且各自"验证通过"——`!405` 删无效 mock 走真实调用（断言值从 mock 的 84 改回真实的 90）对照 `!416` 直接移除 final 让 Mockito 能 mock；Home SSO token 传 Query 还是 Bearer 两个 PR 完全互反（`!1169`→`!1183`）；同一权限闸门 cursor 当越权漏洞加上（CO-474）、gemini 当 403 bug 拆掉（CO-481）。
- **修复被回退**："同步 GitHub main"名义整体覆盖 9 个当天已合入的修复（`!1133`），rebase 用旧版本覆盖已合入修复（`!1915`），同一 issue 被迫修第二遍。

**为什么会这样**：AI 修复的强化信号是"本地测试绿/报错消失"，而不是"根因消除"；没有复现就直接猜，猜错的修复还配套写测试，测试通过反而强化"已修复"的错觉（`!886` 复盘：为错误修复写的 9 个测试是负资产）；每个 agent 没有"同类问题全景"，不知道同根因在仓库别处还存在；PR 描述根因写不清楚的，大概率也没修到根因（分块 3 的观察：body 只剩模板注释的 PR 恰好是多轮修复高发区）。

**下一个项目的四条纪律**：

1. **"同根因二次复发"= 强制根因分析触发器**：同一根因第二次出现时必须停下来做零号病人分析和全仓 grep，一次性肃清，禁止在同层打第三个补丁。
2. **证据先行**：线上问题先拿日志/DB 铁证再动代码（zcode/trae 后期带生产证据的 PR 一次到位率明显更高）；证据不足时优先加观测而不是改逻辑。
3. **修复即配防回退测试**：让回退在 CI 立即变红，而不是让用户再报一遍；错误修复要完整回滚（代码+测试+配置），不要残留成新的混乱源。
4. **互反修复 = 停工信号**：出现方向相反的修复时强制仲裁，先抓真实证据再继续；涉及架构约束的测试修复，AGENTS.md 明写"禁止通过放松架构约束来修"。

## 4. 十五个经典案例

从 6 个分块的 notable_cases 中精选，优先选择跨块印证过、教学价值最高的。每个案例按"发生了什么 → 根因 → 教训"给出。

**案例 1｜`!979` OSS 权限缓存 key 串号越权（模式 1/2，生产安全事故）**。OSS 权限缓存用 JWT token 前 20 字符做 key，但所有用户的 JWT header base64 前缀完全相同（`eyJhbGciOiJSUzI1NiIs`），后登录用户命中第一个登录者（bid_admin）的缓存，全员获得管理员权限——跨部门协同人员实际只有 2 个权限码却拿到 35 个。根因：把"截一段凭证前缀"当用户标识，没意识到 JWT 结构化前缀对所有用户同质；review 和单测都只用单用户场景。教训：缓存/会话 key 必须用完整凭证的强哈希（SHA-256），所有权限缓存强制配"用户 A 登录→用户 B 登录→B 不得看到 A 的权限"的交替场景测试；这类 bug 应列入安全评审必查项。

**案例 2｜`!312` 自我审批漏洞一周六修（模式 1/元模式）**。投标负责人提交标书后自己仍能 curl 调驳回/审核通过端点完成自我审批；一周内被修了 6 次（`!208`/`!213`/`!272`/`!278`/`!281`/`!307`），全部是前端 v-if 表达式修补，甚至出现不同 worktree 的反向修复（`!213` 加 OR、`!272` 删 OR）。根因：`approveBid` 接收了 `currentUserId` 但从未与 `submittedBy` 比较，`BidReviewPolicy.canApprove` 的签名里根本没有"操作者身份"维度——后端策略层零防御，前端按钮显隐是唯一的"权限"。教训：审批类操作的身份校验必须下沉到后端策略层并写进方法签名；同一块前端权限代码被反复反向修改时，应停止修补 UI、转而检查后端是否有真实校验。

**案例 3｜`!405` 与 `!416` 修复打架（模式 5/10/元模式）**。同一个"mock final class 从未生效"的测试问题被两个 agent 反向修复：`!405` 删掉无意义 stubbing 让测试走真实静态调用（断言值从 mock 的 84 改为真实的 90），`!416` 则直接移除类的 final 修饰符让 Mockito 能 mock——一个加固架构，一个破坏架构，且都"通过了验证"。同类互反修复还有 Home SSO 的 `!1169`→`!1183`、权限闸门的 CO-474 vs CO-481。根因：多 agent 无共享上下文时，对"测试为什么红"的归因不同。教训：涉及架构约束（final/纯核心）的测试修复要有仲裁机制；断言值与 mock 返回值雷同是危险信号，review 必查；互反修复出现时强制停工抓真实证据。

**案例 4｜V1146→V1148→V1149 撞号三连（`!1826`，模式 5/6）**。V1146 撞号刚修完，V1148 又撞；更典型的是两个 hotfix PR（`!1823` 和 `!1824`）各自独立把 V1148 重命名为 V1149，互不知情，造成第三次撞号。这不是孤例：此前有 V1034/V1035（`!36`）、V1099/V1100/V1110 三连撞阻断第 18 次部署（`!1345`），而防撞号检查脚本曾因 sed GNU/BSD 语法差异一直"假绿"（`!1348`）。根因：取号脚本只看本地文件取 max+1，撞号检测只在 push 时对比 main，两个修复分支基于同一个撞号的 main 先后合入必然互撞。教训：迁移取号集中化（脚本实时查询 origin/main 最大号）、hotfix 先登记占号再动手、撞号检测同时校验 main 与 worktree——以及守门脚本自身要有阴性对照。

**案例 5｜CO-469 批量导入卡 5%，八轮修复（`!1736`，模式 4/9/元模式）**。人员批量导入"进度卡住"一个症状背后是 5 个独立根因，前七轮依次修了字段名→状态机→NPE→`@ConditionalOnBean` 失效→NOT NULL 约束→字段名（again）→blob；第八轮才彻底：JSON 序列化非法、`failImportTask` 自身二次异常被 `SimpleAsyncUncaughtExceptionHandler` 静默吞掉、`@Async` 里 MultipartFile 临时文件已被清理，三重叠加。根因：每轮只修当前看到的那条 stacktrace；异步线程的异常被吞不留痕迹；任务状态机没有"必达终态"的兜底，前端永远轮询不到结局。教训：异步任务骨架强制 catch Throwable + finally 落终态进度（失败也要写 FAILED）；排查异步 bug 先检查异常是否被吞再谈修复；同一 issue 修到第三轮还没好，强制停下来做全链路日志审计，不再允许"再试一个猜测"。

**案例 6｜`!413` 门禁 fail-open：14 道门禁从未生效（模式 10）**。`pre-push-gate.sh` 第 35 行 `PRE_PUSH_GATE` 默认值写成 `:-0`（没设变量就跳过检查），14 道质量门禁从未真正执行，P0 编译错误长驱直入 main——`!398` 的 407 个编译错误正是在此窗口期合入的。同族事故：防撞号脚本 sed 语法不兼容 macOS 一直假绿（`!1348`）；pre-push 的 `mvn test` 带 `|| true` 吞掉编译失败，冲突标记被提交进 main 阻断第 77 次部署（`!2012`）。教训：所有门禁默认值必须 fail-closed；定期用已知坏 commit 做门禁自检，确认它真的会拦——门禁本身也需要被测试；"一直绿"要默认怀疑"一直没跑"。

**案例 7｜`!827` code:0 谎言：文档写错枚举，CRM 把弃标改成"跟进中"（模式 2）**。CRM 接口文档把 projectStatus 枚举误写为 1=弃标，照抄实现后 CRM 把弃标商机改成"跟进中"，而 CRM 返回 code:0 success 掩盖了错误；同时发现服务器上跑的修复版 jar 与 main 代码不一致，下次从 main 部署会回退修复。最终靠 CRM 商机操作记录原文才确认真枚举是 6=弃标。根因：外部契约的唯一依据是一份会写错的文档，没有任何真实响应校验。教训：证据等级"文档 < 真实响应样本 < 对方系统操作记录"；回调类功能验收必须核对对方系统实际状态（code:0 是谎言）；每次 hotfix 后验证服务器运行 jar 与 main 的 class 级一致性。

**案例 8｜`!820` AFTER_COMMIT 里的 save 永不 flush：294 条通知 0 投递（模式 9）**。弃标事件发生、入队日志正常打印，但 `webhook_delivery_tasks` 和 `notification_delivery_task` 两表始终 0 行——`@TransactionalEventListener(AFTER_COMMIT)` 里的 `save()` 加入已提交的事务上下文，INSERT 注册后永不 flush。日志先于 SQL 打印，造成"代码执行了"的假象，问题潜伏到客户报障。同族：rollback-only 污染 6 天 4 次（`!1090` 等）、private 方法上的 `@Transactional` 三轮（`!1444`/`!1469`/`!1478`）、`this` 自调用 `@Async` 三连（`!1931`/`!2110`/`!2111`）。教训：监听器写库统一 REQUIRES_NEW + `fallbackExecution=true` 写成规范条目；关键队列表用"行数 > 0"的数据存在性验证链路，而不是日志存在性。

**案例 9｜`!1133` "同步 GitHub main"覆盖 9 个修复（模式 5）**。commit `3dcc30097` 名义上是"同步 GitHub main 重构"，实际 GitHub main 滞后于 Gitee，把当天 9 个已合入的修复整体覆盖、净删 1236 行——用户侧表现为已修 bug 集体复活（"点击任务卡片无法查看详情""三列宽度又不一致"），其中投标专员标讯可见性回退无人测出、隐藏最深。根因：双向同步流程无 diff 审计，多个修复没有防回退测试，被回退时 CI 不响。教训：多远端同步只走 cherry-pick 增量，禁止"同步"名义的整体覆盖；"恢复被回退的代码默认 cherry-pick、禁止手工重写"要第一天立为纪律；给关键 bug 修复配防回退契约测试。

**案例 10｜`!429` 假保存：路径不一致，数据从未写入（模式 3）**。前端 `getTasks`/`createTask` 调 `/api/projects/{id}/tasks`，后端实际注册的是 `/api/tasks/project/{id}` 与 `POST /api/tasks`——任务"创建成功"但刷新后消失，数据从未写入。根因：前后端由不同 agent 实现，路径各写各的；前端错误处理把 404 吞掉或让错误提示与成功提示并存。教训：每个写操作必须有"写入后回读验证"的测试（集成或 E2E），假保存类 bug 无法靠单测发现；前端 API 模块的路径常量应与后端 `@RequestMapping` 做静态比对。

**案例 11｜`!598` 六层映射链：表单显示"男"，DB 存 NULL（模式 3）**。人员证书的性别/入职日期/手机/备注保存后详情页全是"-"：三个零号病人分别是前端 `buildPayload` 漏 2 字段、`normalizePersonnel` 漏 2 字段、后端 `toEntity` 漏 3 个 setter——表单显示"男"→DB 存 NULL 的必然性链完整无缺。根因：前后端 5+ 层手工映射链，AI 新增字段只改当前上下文可见的层，其余层静默丢字段，整条链没有任何一环报错。教训：round-trip 集成测试（写入随机值→回读→逐字段断言）是这类 bug 的银弹；新字段六层 checklist 写进 PR 模板；中期用 MapStruct 类生成器替代人肉 builder 链。

**案例 12｜`!1467` `new Blob([res])` 六连：同根因存续一周（模式 4/元模式）**。axios 拦截器对 blob 响应返回完整 response 对象（合理设计），但各模块 agent 手写下载时反复犯同一个错：`new Blob([res])` 把 response 字符串化成 `[object Object]`——"导出 Excel 空白/ZIP 报格式错误/模板下载损坏/PDF 预览失败"，在业绩、CA、平台账户、人员、项目档案至少 6 处被独立重写、独立修复（`!1414`/`!1415`/`!1433`/`!1465`/`!1483`/`!1679`）。根因：没有统一下载 helper；修第一个时没全仓排查，同根因在仓库里存续了整整一周。教训：全局唯一 `downloadBlob` helper + ESLint 禁 `new Blob(` 是根本解；E2E 加下载文件 magic number 校验（PK/%PDF）一条用例拦整类；同根因修到第二个时必须全仓 grep 一次肃清——这条纪律在本案能省掉至少 5 个 PR。

**案例 13｜`!1511` 8472 用户误停用：三轮"合理但非根因"（模式 2/元模式）**。8472 个 OSS 同步用户被误标为"停用"。历经 `!1397`（调 status 优先级）、`!1475`（字符串类型兼容）、`!1495`（改字段名 `activationStatus`）三轮"合理但非根因"的修复后，第四轮靠在测试服务器直连 OSS 抓包 + DB 实证才发现真根因：`handleUnmappedUser` 对角色未匹配用户强制 `setEnabled(false)`，覆盖了正确的在职判定。根因：同步层把"角色未匹配"与"离职/停用"两个语义混为一谈；前三轮没拿生产证据，靠读代码猜根因，猜的都是真实存在但非致病的缺陷。教训：集成类 bug 第一动作是拿生产样本（抓包/DB 直查），禁止"读代码猜根因"式修复——猜对缺陷也治不了病。

**案例 14｜`!1812` 误删 fastjson：生产 crash-loop（模式 5/11）**。一个 agent 把 fastjson 判定为"幽灵依赖"删除，生产启动直接 crash-loop：grep 本仓源码看不到外部 jar（eventlibrary clientsdk）内部对 fastjson 的引用，`mvn dependency:tree` 也未展示该传递依赖，且本地 dev profile 不加载该 SDK 配置类——`mvn test` 全绿给了虚假信心。同族：`!1533` 只引 sentry starter 却在 logback.xml 手动声明类导致第 34 次部署 crash-loop 10 分钟，且部署健康检查把 crash-loop 间隙的短暂响应误判成功。教训：删依赖必须三态验证（源码 grep + jdeps 字节码扫描 + prod profile 真实启动冒烟）；"测试全绿"永远不能替代"生产形态能启动"，prod profile 启动冒烟应纳入合并门禁。

**案例 15｜`!245` 零号病人在 DB：按钮修 4 次（模式 3/元模式）**。"查看项目"按钮始终提示未创建项目，连续 3 个 PR 修复无效：`!227` 给 TenderDTO 补 projectId 字段（但 DB 里本就是 null）、`!243` 给 Controller 加 `/bid` 端点（与已有路径冲突，是弯路）、`!244` 才碰到真因，`!245` 回退弯路并根治。根因：零号病人在 `TenderEvaluationService.proceedToBid()`——项目创建成功后忘了 `tender.setProjectId()` + `save()`，`project_id` 永远为 null，前端无论怎么改都读不到。教训：修 bug 先验证数据链路的最底层（DB 里到底有没有值），再逐层向上；对"已修过 N 次仍复发"的问题强制做零号病人分析，禁止继续在同层打补丁。

## 5. Bug 模式 Top 5 速查表

| 模式 | 信号（看到这些就该警觉） | 第一道防线 |
|---|---|---|
| 权限语义分散 | 用户逐端点报 403/越权；"按钮显示了但点了 403"；同一权限点被反复修、反向修 | 权限矩阵单源机读 + ArchUnit 强制类级 `@PreAuthorize` + "角色 × 端点"契约测试；未知角色一律空权限集 |
| 契约无单源（前后端 + 外部） | "保存成功但刷新没了"；字段名/枚举值两边各写一份；联调才暴露；互反修复 | 契约单一源生成 + 每个写操作"写入后回读"测试 + 外部接口生产抓包样本做 contract test |
| 文件链路断裂 | 上传/下载 404/403；文件损坏、空白、42 字节残包；toast 成功但内容不对 | 统一上传/下载封装（lint 禁裸写）+ "上传→存储→回显→下载→删除"全链路验收 + E2E magic number 校验 |
| 并行合并病 | "任何人拉最新 main 都会编译错误"；已修 bug 集体复活；冲突标记/截断文件进 main | pre-push 编译双绿 + 冲突标记扫描 + rebase 后 `range-diff` 核对；main 定时巡检；回退恢复只走 cherry-pick |
| 修症状不修根因（元模式） | 同一 issue 第 3 轮修复；修复方向互反；报错没了但数据不对 | 二次复发强制根因分析 + 日志/DB 铁证先行 + 修复即配防回退契约测试 |

## 6. 怎么用这章

- 立项第一周：把 13 个模式的"第一道防线"逐项对照进项目骨架——ArchUnit 规则、契约测试模板、迁移取号脚本、统一上传/下载封装、门禁 fail-closed 自检，这些在本项目都是事后补的，下个项目的机会是把它们前置到第一天。
- 给 agent 的上下文里注入两份东西：本章的模式清单（让它知道"同类问题全景"）和元模式的四条纪律（让它知道什么时候该停下来）。
- 复盘时反向使用：新 bug 先对照总览表归类，同类复发直接触发第 3 节的根因流程，而不是再开一个修复 PR。
