# 第 2 章 多 Agent 并行协作：10 个 AI Agent 如何不互相踩死

> 本章回答一个问题：当约 10 个 AI Agent 在同一代码库上并行开发时，需要一套什么样的协作体系才能不散架。
> 全部结论来自西域数智化投标管理平台的真实 PR 数据（2026-06-08 ~ 2026-07-13，1601 个 git merge commit；Gitee 全量已合并 PR 2059 个），每条经验都附 PR 号或 commit 证据。

## 2.1 TL;DR 与协作规模

- 约 5 周内，约 10 个 AI Agent 并行合入 1601 个 PR（中位改动 3 个文件/PR），其中 fix+hotfix 占 59%。**修复占六成不是质量事故，而是并行模式本身的结构性成本**——除 integrator 外的 8 个 agent，fix 占比惊人一致地落在 59%~66% 区间。
- 协作体系的主线不是"分工表"，而是**把冲突成本左移**：把集中在 PR 合入时点的大爆炸，摊平成每个 agent 每次开工时的小口慢痛（强制 rebase + 本地门禁 + 文件锁）。
- 协调信号用 git 事实（哪些分支在该路径有未合 commit），不用静态目录所有权表——表会过时，分支不会说谎；但配套纪律（每日 push WIP）不落实，事实源就失效。
- 最大的两条元教训：**摩擦成本定律**（协调机制用起来太贵，会被集体无视而非被遵守）和 **janitor 定律**（锁、分支、worktree 的泄漏是常态，必须配自动化清理，别指望 agent 自觉）。
- 下个项目第一天的配置清单见 §2.6。分支协议、开工 rebase 脚本、per-task 文件锁、全局序号双保险、一套开发环境、integrator 角色，都该在并行规模上来之前就位——本项目 git 可见历史的第一个 commit（601a2e877）就是修 Bean 冲突，说明设施是事故后补的，代价已经发生过。

**60% fix 占比的结构性含义**，三条推论都有数据支撑：

1. **它不是某个 agent 的问题**。8 个角色各异的 agent，fix 占比全部落在 59%~66%，方差极小。个位数差异来自角色分工（zcode 偏修复、cursor 偏 feat），不构成质差。
2. **它是"并行汇合"的成本**。fix 的区域分布为 backend 635、frontend 466——并行改动在 main 汇合处产生的集成缺陷（Bean 冲突、迁移撞号、冲突选错边）是修复工作的重要来源，这类"汇合病"在单兵开发中根本不存在。
3. **做计划时要给它留预算**。别拿单兵开发的 feat:fix 比例估算产能。并行模式下，六成容量消耗在修复与汇合上是常态；同时设一个 fix 占比天然偏低的 integrator 角色（trae 的 50% + docs 20% + revert 最多）专门承担集成、发布、文档，是有效且必要的安排。

## 2.2 最终协作模式全景

本节描述演进终点上的体系怎么运转。它是事故驱动演进出来的，不代表第一天就长这样——哪些该第一天就有，见 §2.3 的评估。

### 2.2.1 Worktree 布局：持久 worktree + 锚点分支

- 每个 agent 占一个**持久 worktree**（`/Users/user/xiyu/worktrees/<name>`），锚定在受保护的 `agent/<name>-init` 分支上——该分支**禁止直接开发、禁止删除**，只作为身份锚点和任务分支的落点。
- 每个原子任务用 `scripts/agent-start-task.sh --in-place` 在持久 worktree 内切出 `agent/<name>/<task>` 分支。**不要一任务一临时 worktree**：该方案 2026-06-22 被正式废弃（commit 82a181efa），原因是 worktree 膨胀与资源泄漏（!1703 显示残留多到需要专门的 housekeeping 脚本清理）。
- `agent-worktree-guard.sh` 负责身份识别，禁止 agent 在基准区（main 检出）上直接改代码。
- **开发环境全项目只有一套**：自 2026-06-21 起收敛到主工作区 trae（前端 1323 / 后端 18089 / Sidecar 8009 / DB xiyu_bid_main），其余 worktree 只编辑代码，`start-frontend.sh` 等启动脚本内置守卫直接拒绝在非主工作区执行。此前 9 套 per-agent 端口/数据库/Redis DB 映射表被整体废弃（详见 §2.4 环境漂移）。

### 2.2.2 一个任务的完整生命周期

1. **领任务**：需求侧走 Linear CO-XXX。agent 开场强制三步：凭证自检 → 查 issue 拿标题/描述/状态 → 查 team 状态机（写入 AGENTS.md，不依赖口头上下文）。
2. **早操 SOP**：`scripts/sync-env.sh` 一行完成 自动 stash → fetch → rebase origin/main → pop，把冲突暴露提前到开工时。**任务之间也要重跑**，不只是在 session 开头跑（CLAUDE.md §5.0 专门补了这条，否则后续任务在过期 base 上累积工作）。
3. **开分支**：`agent-start-task.sh <agent名> <任务> origin/main --in-place`，任务分支天然从最新 main 衍伸，不积累陈旧。
4. **协调自查**：改动前跑 `who-touches.sh <路径>`，看哪些 agent 分支在该路径有未合 commit；碰到 hot-paths.yml 列出的高危路径（Flyway 迁移 / entity / application.yml / router / Login.vue / CI / hooks），必须先持有 per-task 文件锁（`.agent-locks/<task-slug>.yml`）。
5. **开发与提交**：原子提交（中位 3 文件/PR），15+ 项 pre-commit 检查把守，含 Flyway 自动编号。
6. **push**：14 道 pre-push 本地门禁（编译、ArchUnit、冲突标记扫描、锁检查、Flyway 双向撞号验证等）。`--no-verify` 被 scripts/git 包装器 + git alias 双防线系统级拦截。**每日至少 push 一次 WIP**——这是 who-touches 准确性的前提。
7. **PR 与合入**：PR 走 Gitee（主仓）；GitHub 是 AI 工具入口的单向镜像。1 个 required review 后自动合并，合入后自动清理远端分支。
8. **收尾 SOP**：`agent-finish-task.sh` 用 `git branch -r --merged` + `git cherry` + Gitee API 三重确认代码已合入 main，然后一站式清理本地/远端分支、任务锁、遗留临时 worktree，并切回锚点分支拉齐 main。支持 `--dry-run` 预览。

整条链路的冲突暴露时点设计可以画成一条左移的时间轴：

```
传统模式:   开发 ──────────────► PR 合入时集中爆炸（integrator 买单）
本体系:     开工rebase → 写前查重/拿锁 → commit门禁 → push门禁 → PR确认（各自买单）
            └─ 冲突在最小、最新、责任最清晰的时点暴露 ─┘
```

三个设计意图：冲突暴露得**早**（开工时而非合入时）、**小**（每天几口而非积压数周）、**归责清晰**（谁的陈旧谁解决，而不是 integrator 替所有人解决）。

### 2.2.3 协调协议：git 事实，而非所有权表

体系刻意**不维护静态目录所有权表**——任务一推进表就过时。协调靠三个活信号：

- `who-touches.sh`：以"哪些 agent 分支在目标路径有未合 commit"为唯一事实源，退出码可直接接 hook。该工具在 CO-438（多 agent 并行修同一 bug 互相冲突）之后固化为开工前必跑。
- 每日 push WIP 纪律：本地 commit 对其他 agent 不可见，不 push 的事实源就是瞎的。
- hot-paths.yml + per-task 文件锁：对真正的高危路径做显式预订。hot-paths.yml 的注释直接引用真实事故 #218（Flyway V117 撞）、#220（共享 DB）、#224（root commit 覆盖 Login.vue）作为强制锁依据。

局限性要承认：10 个 agent 里只有 Gemini 有 plan.md 任务声明机制，其余只能靠 commit message + push 频率推断意图（CLAUDE.md §5.3 原文承认）。这套协议是"低摩擦及格线"，不是完备方案。

### 2.2.4 需求交接与追溯

- 582/1601 PR（36%）带 CO 引用，新 agent 凭 CO 号即可重建任务现场，交接不依赖口头上下文。
- 复杂任务走 Spec Kit 流程门禁：specify → plan → tasks 之后才许编码，否则 CI 门禁拒绝。
- 执行不均要正视：各 agent 的 CO 引用率从 27% 到 48% 不等，说明纯文档纪律天然衰减，需要门禁或 review 兜底。
- 被回退的代码一律 cherry-pick 恢复、禁止手工重写（CO-338 教训，见 §2.4 与 §2.5）。

## 2.3 基础设施逐项评估：Day-1 照搬、视规模补、还是别建

11 项基础设施按"引入背景 → 解决了什么 → 二阶成本 → 下个项目 verdict"逐项评估。结论先行：

| # | 设施 | Verdict |
|---|---|---|
| 1 | 持久 worktree + --in-place 任务分支 | **Day-1 照搬** |
| 2 | 早操 SOP（sync-env.sh） | **Day-1 照搬** |
| 3 | per-task 文件锁 + hot-paths | **Day-1 照搬**（直接跳过单文件锁阶段） |
| 4 | who-touches.sh + 每日 push 纪律 | 规模到 5+ agent 再补，但 push 纪律 Day-1 就要立 |
| 5 | 本地门禁双防线（pre-commit/pre-push + 防绕过） | **Day-1 照搬**（CI 不可靠时尤其是） |
| 6 | agent-finish-task.sh 收尾 SOP | **Day-1 照搬** |
| 7 | 开发环境统一主工作区 | **Day-1 照搬**（直接一套，跳过映射表阶段） |
| 8 | Flyway 版本治理（预约 + 双向撞号检测） | **Day-1 照搬**（凡有全局唯一序号都适用） |
| 9 | 双远程 + 单向镜像同步 | 仅当有 AI 工具入口分离的硬需求才建 |
| 10 | 回退恢复 cherry-pick 纪律 | **Day-1 照搬**（成本为零） |
| 11 | Linear CO 交接 + Spec Kit 门禁 | CO 引用约定 Day-1；Spec Kit 只给复杂任务 |

**1. 持久 worktree + --in-place 任务分支模型**。背景：首个可见 commit（2026-06-08，601a2e877）已含脚本，2026-06-22（82a181efa）废弃二级临时 worktree。解决了临时 worktree 膨胀、任务分支从陈旧 base 衍伸两类问题；锚点分支 + guard 脚本顺带解决身份识别。二阶成本：同一 worktree 串行切任务，未完成任务的 WIP 全靠每日 push 纪律保命；init 锚点分支曾反复 unpushed 导致锚点漂移（2026-06-10 a449ad926 修）。**直接照搬，但跳过临时 worktree 阶段。**

**2. 早操 SOP**。背景：首个 commit 已含，后补 init 分支同步（a449ad926）与 GitHub 镜像检测（c064ba24e）。把 merge 冲突从 PR 合入时点提前到每次开工时点，小口慢痛代替大爆炸；rebase 失败保留现场并给手动指引。二阶成本：本质是把冲突成本摊给每个 agent 每天承担；Flyway checksum 校验失败时需手动 `rm -rf backend/target`；任务之间不重跑就会在过期 base 上累工作。**直接照搬，这是全套体系里性价比最高的一项。**

**3. per-task 文件锁**。背景：2026-05-12 从共享单文件 `.agent-locks.yml` 改造（早于 git 历史起点），起因是单文件锁信用破产（见 §2.4）。新任务 = 新文件 = 零冲突，janitor 删文件比删行干净；CI agent-locks job 与 pre-push 锁检查双层拦截。二阶成本不低：僵尸锁/孤儿锁持续泄漏，全周期锁清理类 chore commit 约 180 个（!1451 一次清 10 个僵尸锁），被迫补写 `agent-locks-prune.mjs`、`agent-lock-renew.mjs` 和 spec 测试；锁文件还曾被误 track 进 main（2026-07-05 9e2e4e114 补 gitignore）。**照搬，但清理自动化必须与锁机制同天上岗**（见 §2.5 janitor 定律）。

**4. who-touches.sh + 每日 push WIP 纪律**。背景：首个 commit 已含脚本，CO-438 后固化为开工前必跑。用 git 事实替代静态所有权表。二阶成本：准确性完全依赖全员每日 push——10 个 agent 里只要一两个不 push，lease 检测就漏。**agent 少时收益不明显，5+ 并行时值得补；但"每日 push WIP"这条纪律第一天就要立，否则将来补工具时事实源是空的。**

**5. 本地门禁双防线**。背景：2026-06-09（98716f0ba）加固，起因是 GitHub CI 不可用，门禁完全靠本地。`--no-verify` 被系统级拦截（连 `/usr/bin/git` 直调都列为违规），同时留 `Xiyu_ALLOW_GIT_NO_VERIFY=1` + `.runtime/git-bypass/` 审计日志的合规逃生口。二阶成本：14 道 pre-push 在 P0 事故时耗时过长，2026-07-03 标讯中心宕机（lessons §36）后被迫定义 P0 Hotfix 通道（PRE_PUSH_GATE=0、30 分钟 SLA，但 ArchUnit 与 Flyway 检查仍不可跳）；门禁脚本自身也有 bug（!402、!413）；冲突标记能进 main 说明门禁曾缺编译检查（!2012 事故后 !2014 补上）。**照搬，门禁不可绕过是多 agent 信任的底座；但 P0 逃生通道要同步设计，否则紧急时刻人会砸掉整个门禁体系。**

**6. agent-finish-task.sh 收尾 SOP**。背景：2026-06-14 新增（7fbe8b26d），2026-06-17 升级三重合入守卫（482f12f35）。把"收个任务"从易错的手工多步（确认合入→删分支→删锁→清 worktree）变成一条命令，三重确认杜绝误删未合代码。二阶成本：锁文件命名约定漂移导致旧匹配漏删（91f429b91 才修）——约定要先定死。**照搬。**

**7. 开发环境统一主工作区**。背景：2026-06-21 废弃 9 套 per-agent 端口/DB/Redis 映射表。消灭了 9 套环境的数据漂移与维护成本，只有一份 dev 数据、一套 Flyway 状态，联调结果可比。二阶成本：非主工作区的 agent 失去本地联调能力，验证 UI/接口必须排队；多项目共用机器时端口仍是事故源（!1704 固化容器配置防冲突）。**第一天就一套环境，不要经历映射表阶段。** 联调排队是真实代价，但远小于 9 套环境漂移的代价。

**8. Flyway 版本治理体系**。背景：!1348 的脚本注释标注"沉淀自第 18 次部署事故"——两个 PR 各取 V1110 先后合入导致 main 双 V1110（!1345）。pre-commit 自动编号 + pre-push 强验证（worktree 内部 + origin/main 已被污染两种场景）+ 目录/包内守卫 + 强制 U 回滚脚本。二阶成本：预约靠自觉，撞号没有绝迹（见 §2.4 专题分析，全周期撞号相关 commit 15 个）。**照搬，且要把"预约 + 双向检测"一起上；任何全局唯一序号（版本号、单号段）都适用这个模式。**

**9. 双远程仓库与单向镜像**。背景：AI Coding 工具从 GitHub 进出、主仓留在 Gitee（!1036 配置文档，!1123 安全防护体系——分支名 github-sync-round-6，说明同步方案迭代了 6 轮才稳定）。方向性约束写进脚本硬检查：Gitee→GitHub 单向镜像禁反向覆盖，GitHub→Gitee 只许增量 cherry-pick。二阶成本：迁仓后 GitHub Actions auto-merge 体系整体作废，降级为 gitee-pr-helper.sh；两个远程间的改动需人工补同步（c9339153a、19a1248c7），**同步链路本身是新的 bug 源**。**没有硬需求就别建；必须建就单向 + 硬检查，且预算至少数轮迭代。**

**10. 回退恢复 cherry-pick 纪律**。背景：2026-06-26 CO-338 事件——agent 跳过 cherry-pick 手工重写被回退代码，丢失原作者与改动意图；当天 !1133 恢复代码 + !1135 沉淀纪律。多 agent 团队里 git blame/git log 是唯一考古工具，手工重写即毁史。二阶成本：纯文档纪律无工具强制，全周期仍有 25 个 revert 类 PR（git 口径）。**成本为零，第一天写进贡献指南。**

**11. Linear CO 交接 + Spec Kit 流程门禁**。背景：AGENTS.md 强制"执行 co-XXX"开场三步；PLANS.md 规定复杂任务必须 specify→plan→tasks 后才许编码。36% 的 PR 带 CO 引用，需求—代码可追溯。二阶成本：引用率 27%~48% 执行不均；Spec Kit 在 P0 场景同样让位 hotfix 通道。**CO 引用约定第一天就立（写进 commit/PR 标题规范）；Spec Kit 类重型门禁只给复杂任务，别全量铺开。**

## 2.4 九类并行故障模式及治理

九类故障按"发生了两次以上"或"造成过 main/部署级事故"的标准入选。总览：

| 故障模式 | 代表性证据 | 治理后的残余风险 |
|---|---|---|
| Flyway 版本号撞号 | !1345、!1816/!1823/!1824/!1826、b0f114314 | **未绝迹**，降为 hotfix 级小事故 |
| 冲突标记残留进 main | !2012 → !2014 | 门禁补死后未再发生 |
| 多 agent 修同一 bug 方向打架 | CO-438、!1232、!2067、!2095 | 靠查重纪律，仍有漏网 |
| Bean 冲突/汇合后编译失败 | 601a2e877、6d4a61c02、lessons §14 | 编译门禁后可控 |
| 单文件锁自我瘫痪 | CLAUDE.md §5.2 | 已改 per-task，机制消灭 |
| 僵尸锁/孤儿锁泄漏 | !1451、!1403、!1636 等约 180 个清理 commit | **持续发生**，靠 janitor 兜底 |
| 临时 worktree 膨胀泄漏 | 82a181efa、!1703 | 机制消灭（改 in-place） |
| 双远程同步覆盖/镜像漂移 | !1123（round-6）、c9339153a、19a1248c7 | 方向性硬检查后可控 |
| 环境漂移（9 套端口/DB） | CLAUDE.md §2 废弃声明、!1704 | 机制消灭（收敛一套） |

下面展开四个最有迁移价值的。

### 2.4.1 Flyway 撞号：为什么三层治理后仍反复

时间线：!990（V1089 复用，06-23）→ !1345（两 PR 各取 V1110 先后合入，06-29，第 18 次部署事故）→ 建治理体系（!1175 治理机制、!1279 目录守卫、!1348 撞号检测）→ **2026-07-07 一天三连撞**（V1146：CO-464+CO-533；V1148：CO-537+CO-530；V1149：CO-537 重命名，!1816/!1823/!1824/!1826）→ 07-09 又撞 V1160（CO-566/CO-567，b0f114314）。

治理后仍反复的根因是**竞态不在检测覆盖的时点上**：`--reserve` 预约是软约束（靠自觉），撞号检测在 pre-commit/pre-push 才生效。两个 agent 同一天各自开工、各自通过本地检测、各自取同一号，本地看都合法——直到先后合入 main 才暴露。07-07 的三连撞全部是"两组并行任务互撞"，没有一例是单人失误。

治理的真实效果是把**部署级事故降为 hotfix 级小事故**（发现即改号重提，分钟级修复），而不是消灭撞号。迁移价值在于：**全局唯一序号只有两条路——要么中央仲裁（服务端发号），要么接受残余撞号 + 快速修复通道**。本地检测再厚，也拦不住合入时序的竞态。P0 hotfix 通道里 Flyway 检查仍是不可跳过的两项之一，说明团队最终的取舍是"强检测 + 接受残余 + 快速修"。

### 2.4.2 单文件锁的信用破产：协调机制如何被自己的摩擦杀死

原方案是所有 agent 共写一个 `.agent-locks.yml`。后果链：每次 rebase 必撞锁文件冲突 → 解冲突成为日常噪音 → 告警不再被当作信号 → CLAUDE.md §5.2 原文记录 "conditioned everyone to ignore lock warnings"——**锁在名义上存在，在行为上死亡**。

2026-05-12 改为 per-task 文件（新任务 = 新文件 = 零冲突）后约束力才恢复。这个案例的泛化价值远超锁本身：**任何"每次正常使用都会产生成本"的协调机制，都会被集体无视而不是被遵守**。评估一个门禁/锁/登记表能否活下来，先算使用者单次成本；成本不为零，就要把付费动作和使用动作解耦（per-task 文件正是把"写锁"从共享资源上解耦出来）。

### 2.4.3 双远程同步覆盖：自己引入的分布式一致性问题

双远程把"一个仓库"变成"两个需要保持一致的事实源"，同步方案迭代了 6 轮（分支名 github-sync-round-6 是化石证据）。稳定后的约束全部写成脚本内硬检查而非文档约定：Gitee→GitHub 单向镜像且禁反向覆盖；GitHub→Gitee 只许增量 cherry-pick、禁止 merge/覆盖；早操自动检测镜像落后状态。即便如此，同步链路本身仍持续产生 bug（c9339153a、19a1248c7 都是 GitHub→Gitee 的人工补同步）。

教训：**双远程是用持续的运维成本换 AI 工具的接入便利**。下个项目若 AI 工具可以直接对接主仓，就不要建镜像；若必须建，方向性约束第一天就写进脚本，并给同步链路本身预留维护预算。

### 2.4.4 修复方向打架：从"查重"到"根因治理"的两级应对

多 agent 并行时，同一个 bug 常被多个 agent 同时认领，且修复策略互相冲突：CO-438（lessons §30，多个 PR 互相冲突）、!1232（回退 !1230：角色名改成 bid_admin 改错对象，/bidAdmin 才有效）、!2067（撤销 !2066，同样改错对象）、!2095 + e4c0e176b（撤销 !2091 的 locked 修改，并补 5 个语义守护测试防重蹈）。

治理分两级，对应两种病因：

- **一级（信息问题）**：开工前 who-touches.sh 查重 + 指定单一 agent 统一修复。大多数打架是"不知道对方在修"，补信息即可。
- **二级（架构问题）**：反复修不好的，升级为根因治理。OSS 权限问题经历 CO-361 → CO-373 → spec 032 → CO-551 共 10+ 轮反复，根因是共用代码路径的架构决策而非单点 bug——最终用 Spec Kit 流程（spec 032/033）把它收敛为架构方案三选一，而不是继续各自打补丁。**同一个坑修到第三轮还复发，就该停止派单人修，转为架构级立项。**

### 2.4.5 冲突标记残留进 main：门禁缺口的 24 小时进化

!2012（07-10）：早操 stash apply 的冲突标记残留进 WebhookEventListener 等 2 个文件，main 直接编译失败——14 道 pre-push 门禁居然没有一道查编译和冲突标记。同类隐患并非孤例：da472ead0（07-12）是 rebase 冲突修复，!2047 的 resolveForCrmLookup 与 CO-576 的重命名在 main 上打架。

治理是教科书级的"事故驱动门禁进化"：事故发生后 24 小时内，pre-push-gate 新增编译检查 + 冲突标记扫描（!2014 / 4dd914ea2，commit message 直书"修复 PR !2012 事故根因"），此后未再发生。**门禁清单不是设计出来的，是事故长出来的——但编译检查这种底线项，下个项目第一天就该有，不必等自己的 !2012。**

### 2.4.6 Bean 冲突 / 汇合后编译失败：并行改动的"汇合病"代表

git 可见历史的第一个 commit（601a2e877 / !349）就是修 CaseExportAppService Bean 冲突——并行设施还没就位，汇合病的账单就先到了。此后 6d4a61c02（Spring Boot 启动失败：bean 冲突 + Redis 可选依赖）、8fb785dd3、lessons §14（@RequestScope Bean 与 SDK CacheBeanComponent.initCacheBean() 冲突）接连发生。这类故障单人开发里几乎不存在：每个 agent 本地都编译通过，两个合法改动在 main 汇合后才爆炸。

治理：pre-push 编译检查（!2014 后成为硬门禁）+ `npm run ci:local:quick`（编译 + ArchUnit 约 2 分钟）要求 push 前本地全绿——**远程只做确认，不做发现**。这是"冲突成本左移"在编译层的体现。

### 2.4.7 僵尸锁 / 孤儿锁泄漏：协作资源的熵增是常态

任务合入了，锁没删：!1451 一次清 10 个僵尸锁文件（07-01），!1403（CO-409 孤儿锁）、!1662、!1636（清 5 个 stale 锁）、!1701、aeeae8516 / b034d622f（prune stale expired locks）……全周期锁清理类 chore commit 约 **180 个**——在 5 周的 git 可见历史里，相当于每个工作日都有数起。

治理是三件套：agent-finish-task.sh 收尾时按任务 slug 自动删锁（含两种命名约定兼容，91f429b91 修过匹配漂移）；agent-locks-prune.mjs 定期清理 + agent-lock-renew.mjs 续期 + check-agent-locks 带 spec 测试；CI agent-locks job 检测锁冲突。教训不是"锁会泄漏"，而是**一切协作资源（锁、分支、worktree）的泄漏都是常态而非异常**——janitor 自动化必须与资源机制同天上岗（详见 §2.5 janitor 定律）。

### 2.4.8 临时 worktree 膨胀与资源泄漏：被机制消灭的一类

早期"一任务一临时 worktree"方案导致 worktree 只增不删、磁盘与注意力双重泄漏——!1703 里 agent-housekeeping.mjs 扫 worktree 遇到 EACCES，说明残留多到需要专门的 housekeeping 脚本。2026-06-22（82a181efa）正式废弃，PLANS.md 记录理由"避免 worktree 膨胀、简化资源管理"：改为一 agent 一持久 worktree + --in-place 切分支，finish-task 脚本 Step 9 顺带清理遗留临时 worktree。**机制换掉之后，这类故障彻底消失**——这是九类故障里治理最彻底的两类之一，方式都是"换机制"而非"加纪律"。

### 2.4.9 环境漂移：9 套端口/数据库映射表的维护灾难

早期给 9 个 agent 各配独立端口/数据库/Redis DB 号。结果是 9 份 dev 数据互相漂移、9 套 Flyway 状态各自为政、联调结果互不可比，映射表本身还要专人维护。2026-06-21 整体废弃（CLAUDE.md §2 废弃声明）：开发环境物理收敛到主工作区 trae 一套，其他 worktree 的启动脚本内置守卫直接拒绝执行；健康检查聚合到 `npm run agent:health-check`。

残余代价是真实的：非主工作区的 agent 失去本地联调能力，验证 UI/接口要排队；!1704（07-05）还需固化 MySQL/Redis 容器配置防跨项目端口冲突，说明多项目共用机器时端口仍是事故源。但相比 9 套环境的漂移成本，排队是可接受的代价。**下个项目第一天就一套环境，不要经历映射表阶段。**

## 2.5 元经验：从 1601 个 PR 里提炼的协作定律

**1. 摩擦成本定律：门禁摩擦过高，会被绕过而非遵守。** 单文件锁的信用破产是最干净的实验证据（§2.4.2）。逆命题同样成立：把成本降下来（per-task 文件零冲突），约束力自动恢复。设计任何协调机制时，先算使用者的单次成本，再谈规则。

**2. janitor 定律：一切协作资源都必须配清理者。** 锁、分支、worktree 的泄漏是常态而非异常——约 180 个清锁 commit、一次清 10 个僵尸锁的 !1451、需要专门 housekeeping 脚本的残留 worktree，都是证据。收尾脚本内建清理 + 定期 prune 自动化，缺一不可；指望 agent 自觉释放，等于接受泄漏。

**3. 对全局唯一资源，软约束必败，要么中央仲裁要么接受残余。** Flyway 预约靠自觉 → 15 个撞号 commit、一天三连撞。同理，"每日 push WIP"靠自觉 → who-touches 事实源会漏。凡依赖自觉的环节，都要按"必然有一定比例不执行"来设计兜底。

**4. 冲突成本左移，摊平优于爆炸。** 早操 rebase 把合入冲突从 PR 时点提前到开工时点，且任务之间也要重跑（CLAUDE.md §5.0）。左移的本质是让每个 agent 为自己的陈旧买单，而不是让 integrator 在合入时为所有人的陈旧买单。

**5. 协调信号用 git 事实，不用静态文档。** 目录所有权表会过时，分支不会说谎。但 git 事实的鲜度由 push 频率决定——事实源和纪律是同一个系统的两半。

**6. 门禁三原则：系统级防绕过、带审计的逃生口、随事故进化。** 防绕过要到"连 /usr/bin/git 直调都算违规"的强度（98716f0ba）；但必须预留合规逃生通道（Xiyu_ALLOW_GIT_NO_VERIFY=1 + 审计日志、P0 hotfix 通道），否则紧急时刻人会砸掉整个门禁体系。每次事故后反问"哪道门禁本该拦住它"——!2012（冲突标记进 main）发生后 24 小时内 !2014 补上编译检查 + 标记扫描，门禁体系就是这样长全的。

**7. 给并行模式预算 60% 的 fix 容量，并设 integrator 角色。** 8 个 agent 的 fix 占比一致落在 59%~66%，这是结构成本，不会因为你更努力而消失；trae 的分布（fix 50% + docs 20% + revert 最多）证明专设一个承担集成、发布、文档的主工作区角色是有效的安排。

**8. 毁史即毁协作：被回退的代码用 cherry-pick 恢复。** 多 agent 团队里 git blame/git log 是唯一的考古工具。CO-338 中 agent 手工重写被回退代码，原作者与改动意图随之丢失，团队当天用 !1133 + !1135 把纪律固化（只允许三种例外且必须引用原 hash）。历史可追溯性在多 agent 场景下是协作基础设施，不是洁癖。

## 2.6 行动清单：下个项目多 Agent 协作的 Day-1 配置单

**第一天必须就绪**（按搭建顺序）：

- [ ] 分支协议：`agent/<name>-init` 锚点分支（保护 + 禁删 + 禁直接开发）+ `agent/<name>/<task>` 任务分支命名，写进 AGENTS.md。unknown 占 6.7% 的教训：命名约定要有 hook 校验，否则统计与追溯都漏。
- [ ] 每 agent 一个持久 worktree + 开工脚本：一条命令完成 stash → fetch → rebase origin/main → pop → 切任务分支（in-place），任务之间也重跑。
- [ ] per-task 文件锁 + 高危路径清单（迁移 / entity / 全局配置 / 路由 / 入口页面 / CI），直接跳过共享单文件阶段；锁文件加入 .gitignore 的例外规则先想清楚。
- [ ] 全局唯一序号双保险：开工预约 + pre-push 双向撞号检测（本 worktree + 与 main 比）。
- [ ] push 前本地门禁最小集：编译检查 + 冲突标记扫描 + 锁检查（别等自己的 !2012 才补编译检查）；`--no-verify` 系统级拦截 + 带审计日志的逃生口。
- [ ] 收尾脚本：三重合入检查（merged + cherry + PR API）+ 锁/分支/worktree 一站式清理 + 切回锚点。
- [ ] 开发环境只有一套，其他 worktree 的启动脚本内置守卫拒绝执行。
- [ ] 需求号（Linear/Jira）进 commit 与 PR 标题的约定，开场自查步骤写进 AGENTS.md。
- [ ] 回退恢复 cherry-pick 纪律写进贡献指南，列出例外情形。
- [ ] 指定 integrator 角色（集成/发布/文档），产能计划按 60% fix 容量做预算。

**规模到 5+ agent 或出对应事故后再补**：

- [ ] who-touches 类 git 事实协调工具（前提：每日 push WIP 纪律已落实）。
- [ ] P0 hotfix 通道：明确 SLA、可跳过项与**不可跳过项**（本项目是 ArchUnit + Flyway 两项）。
- [ ] Spec Kit 类重型流程门禁，只罩复杂任务。
- [ ] 双远程镜像：仅当 AI 工具入口必须与主仓分离；单向 + 脚本内硬检查 + 预算数轮迭代。

**明确不要做**（本项目已交过学费）：

- 每 agent 独立端口/数据库/Redis 映射表——9 套环境维护不起且数据互相漂移，2026-06-21 整体废弃。
- 一任务一临时 worktree——膨胀与泄漏，2026-06-22 废弃（82a181efa）。
- 任何"每次正常使用都会冲突"的共享协调文件——它会被无视，不会被遵守。
- 静态目录所有权表——它从写完那一刻起就在过时。
