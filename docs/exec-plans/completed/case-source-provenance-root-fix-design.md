# 案例来源标题根因修复设计

## 目标

修复新生成案例大量缺少「原文所在标题」的根因，不减少案例生成数量，不要求大模型逐字复制原文，不把评分项标题或正文首句伪造成来源标题。

## 已证实根因

`CaseAiMatcher` 先从原始 Markdown 生成相关摘录，但只将摘录文本交给大模型，并且只接收模型返回的 `matchedSnippet`。该链路丢弃了摘录在原文中的位置和所属章节。入库前又用不受程序约束的 `matchedSnippet` 去原文做精确连续字符串反查；模型只要修改标点、Markdown/HTML 格式、省略或拼接文本，反查就返回 `null`，来源字段为空。

## 设计

### 1. 摘录阶段确定来源

将「相关摘录」从纯字符串升级为不可变值对象，至少包含：

- 交给大模型的摘录文本；
- 摘录中命中原文段的原始位置；
- 在摘录生成时根据原始 Markdown 确定的章节来源。

章节来源必须由程序根据原文位置计算，不依赖大模型输出。

### 2. AI 只负责选择证据内容

`AiMatchedSlice` 在保留 `matchedSnippet` 和置信度的同时，携带调用前已确定的来源候选。大模型返回内容不得覆盖或生成来源标题。

### 3. 入库优先使用上游来源

`ProjectClosedEventListener` 构建案例时：

1. 优先使用 `AiMatchedSlice` 携带的已证明来源；
2. 为了兼容其他调用者和历史测试，上游未携带来源时，保留现有 `matchedSnippet` 反查作为次级回退；
3. 两种方式都无法定位时，案例仍然正常生成，不改变用户确认的业务契约。

### 4. 纯核心与副作用边界

- 纯核心：摘录位置与章节来源的计算，输入 Markdown/位置，输出不可变来源值。
- 副作用外壳：`CaseAiMatcher` 调用 AI，`ProjectClosedEventListener` 编排和持久化。
- 不新增数据库表或迁移；沿用现有五个来源字段。

## 测试与验收

### RED 根因测试

构造一份含有明确 Markdown 章节的标书，让 AI 返回语义一致但非原文连续子串的 `matchedSnippet`。旧实现下案例会生成但来源标题为空，测试必须失败。

### GREEN 验收

- 同一测试在修复后案例数不变；
- 来源标题和路径来自原始 Markdown 章节；
- AI 改写的 `matchedSnippet` 仍作为案例应答内容保存；
- 原有 AI 解包、空结果、大文件摘录预算和历史反查测试继续通过；
- 后端相关单测、架构门禁和整仓 Maven 测试通过。

## 明确不在本次范围

- 不改变案例的生成、去重、推荐和上下架规则；
- 不因来源定位失败丢弃案例；
- 不在本次代码修复中更新生产数据；
- 不部署、不自动执行生产回填。
