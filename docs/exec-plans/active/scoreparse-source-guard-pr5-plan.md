# PR #5 原文分值与发布门禁执行计划

基准 `8a04569d881e80ca73d5980b22b09e9ebd2d900d`；范围仅为评分解析校验、确定性回补、发布入口及直接测试。真实项目 1386 不在本地合成验证的结论范围内。

1. 固定同一份 100 分原文资产，以缩小声明总分、篡改单项分值、20/80 凑总分三个反例先取得旧代码业务断言失败证据。
2. 纯领域层分别核验模型声明总分、原文方案总分、叶子合计与逐项最高分；保持原有定位、引用、父子、去重规则。
3. 首次与一次紧凑复核共用原文约束；确定性回补也走同一纯校验，不接受默认总分或错误作用域。
4. 把已核验资格带到正式发布入口；`REVIEW_REQUIRED` 只保存任务事实和证据，不触碰既有正式评分项与打分。
5. 验证 100/80 分正向、异常路径、父子及多表、回补正负、旧数据保护，再跑 scoreparse 回归、金标、架构与提交前门禁。
6. 更新 Wiki，独立审查，普通提交并同步 Gitee/GitHub 当前分支；PR 保持打开，不部署、不合并、不清理 worktree。

## 2026-09-21 续修：方案范围与多表发布（起点 `7a581a6c3d66be9343a6fabedf35a5f14a4f79ef`）

- 旧代码失败证据：`OriginalScoreEvidencePolicyTest` 11 项中 4 项业务断言失败；`SchemeScopePublicationTest` 5 项中 4 项业务断言失败。A1 把单表 20 当总分、A2/A3 丢失独立汇总 100、C2 丢失逗号前方案上下文；B1 两张局部完整表 50 分误获 AUTO，B3 跨表完整 100 分误拒。

- 模型首次、一次复核、确定性回补复用这份上下文。局部小计只核验对应表，所有有效叶子再与方案总分闭合；正式发布证明绑定当次事实和候选集。`REVIEW_REQUIRED` 仅保存事实、证据与诊断，不替换旧 `score_item` / `score_result`。

## 2026-09-22 续修：原文证据角色、共用分表小计与标题层级（起点 `919d8e36c19c596de85b91233b72f2f1ae8f1dc9`）

- A：带“评分因素/评分规则/分值”的明细行不是方案总分声明行，规则单元格以“满分10分”开头也只供单项分值核验。正文无方案总分则未知；正文或独立汇总表明确 100 才能闭合。
- B：`OriginalScoreEvidencePolicy` 对模型事实与确定性事实使用同一份原文 `subtotals`，按完整方案事实集合排除父项后核验每表叶子合计。`OriginalSourcePublicationGuard` 删除原来独有的第二套小计比较；诊断带 tableId、原文单元格、expected/actual，并在当前任务 `run_summary.sourceDiagnostics` 保留有限的小计差异。
- C：正文标题按 Markdown 层级识别父方案与子章节。`# 本项目评分办法` 下的两个 `## …评分标准` 不再算三个方案；同级新方案或另一标包仍转人工。
- 新增测试先在本起点获得领域 8 项中 5 项业务失败、真实编排 14 项中 4 项业务失败、JPA 9 项中 1 项业务失败；后续单独发现并修复诊断来源丢失与无空格标题漏检，均先补业务失败测试。真实 1386 仍未验证，不部署或重解析。
- 独立评审补充：稀疏评分明细行仅留一个“满分10分”规则单元格时，旧非空单元格计数仍误判为方案总分；该用例先出现业务失败，再改用表头行位置识别明细角色。B2 真实复核结果进入 JPA 发布保护对照；新增编排场景拆出独立测试类，遵守 300 行限制。
