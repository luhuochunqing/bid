二、规格外决策（Spec 里没有、我拍板的）

D1：种子用户角色一律 MANAGER，绝不 seed 成 admin 角色码。
理由：正向 ADMIN 用例的放行靠的是注解提供的 ROLE_ADMIN authority + 库内用户存在 + 非 OSS（hasAdminAccess 三条件），与 DB 角色字段无关；而负向用例（如 CalendarIntegrationTest 的 BID_TEAM 期望 403）依赖"非管理员走 scope 判定被拒"。若把种子提权为 admin，负向测试会反向翻红。最小权限原则下两者兼得。
D2：种子时机用 beforeTestExecution（@BeforeEach 之后、@Test 之前），而非 beforeTestClass/beforeTestMethod。
理由：DocumentExportIntegrationTest 等非事务测试在 @BeforeEach 里 userRepository.deleteAll()，只有 beforeTestExecution 能保证清理后再补种。注册方式为 spring.factories 全局 TestExecutionListener（注意 key 是单数接口名 org.springframework.test.context.TestExecutionListener——先用注解类复数名踩了一次坑）。
D3：ExpensePaymentControllerIntegrationTest 单独显式补种，不走全局钩子。
理由：该类 @DirtiesContext(AFTER_EACH) 且在 @BeforeEach 内部就调用受守卫接口（setUp→approveExpense），任何全局 listener 相位都早于它。与其改相位不如就地一行 ensureSeeded，显式可读。
D4：簇F选择子类桩而非抽接口重构。
理由：OpenAiScoreAnalyzer 是具体类无接口，抽接口要动 3 个消费方 + application→infrastructure 方向问题；子类桩 5 个 public 方法全覆盖、行为确定性（空候选池 + quoteMissing=true），改动面最小。代价：父类构造器传 null，若未来桩未覆盖新 public 方法会 NPE —— 已在类头维护声明里写明扩展注意事项。
D5：ProjectArchiveControllerDownloadPathTest 改 stub 方法而非改产品代码。
理由：302→500 的 NPE 是因为 spec039 把下载收口到 ObsDirectRedirects.tryRedirect（调 signObsDirect），测试还 stub 旧的 trySign → Mockito 默认返回 null。生产契约是对的，测试漂移。
D6：种子器加 H2-only 守卫（jdbc:h2:mem: 前缀检查）。
理由：第一版全局种子把 user 行写进了 Testcontainers/本地共享 MySQL 容器库，导致 FlywayMysqlContainerTest 的 V1092「role_id NULL 计数」假失败（首轮绿、二轮红的铁证）。守卫后该类恢复 4/4。
D7："admin" 从全局种子清单移除，改由需要的测试类显式 ensureSeededFor("admin")。
理由：种子行跨类持久，TenderCrmLinkIntegrationTest 自 INSERT admin 撞 users.username 唯一键。默认名 "user" 无此冲突（无测试自建同名）。

三、规格外决策（Spec 未写明、我拍板）

D1：报价参数不单拆为独立评分项，一律收敛进“报价评分（100分）”主项 detail。
依据：招标文件报价评分 100 分为单一科目，下浮率/BP%/HP%/L1/L2/RH/RL 均为其计算参数，非独立给分项。拆分为 8 条会使权重合计虚增 80+10+10+3+6+1+0=110 且语义失真。决定：正则层直接跳过参数行（PRICE_PARAM_ROW_PATTERN），LLM 层通过 prompt 硬约束“不得单拆”，合并层把跨 chunk 报价 detail 拼合。
D2：跨页表格合并采用后处理启发式，而非重写 pdfplumber 提表。
重写提表需处理 rowspan/colspan 的几何合并，风险高；后处理仅看相邻 pipe 块的 header 是否含报价参数且无评分头，改动面小、失败时易回滚。已用合成 markdown 回归验证（下浮率/BP%/HP% 连续合并）。
D3：邻近 chunk 扩展仅对含报价参数或含 “|” 的孤立块生效。
若对所有孤立块扩展，会把大量合同纯文本噪声重新拉入 LLM，成本与幻觉回升。限定报价参数/表格特征，既治报价截断又不放宽全文。
D4：报价 detail 拼合采用简单 “\n” 连接，暂不做语义去重。
去重需对齐与子串判定，易误删公式中的重复子句（如“Y基准=Y平均×(1-X)”在两 chunk 均出现时）。先保证不丢，再观察线上 detail 去重需求。

四、风险与后续

R1：LLM 仍可能截断超长 detail。报价 detail 拼合后可达 800-1200 字符，若模型输出截断（max_tokens），后半参数仍可能缺。缓解：已在合并层做硬拼合，未来可把报价表格在喂 LLM 前做“参数表预拼”作为上下文注记，或对 detail 超 800 字做二次回补请求。
R2：权重合计校验对报价单科 100 分敏感。报价单科 100 分时若商务/技术另有 60 分，合计 160 会触发超载剔除/归一化。当前剔除仅针对无 code/无 sourceText 候选，报价主项（有 code 有 sourceText）不会被剔，但合计仍会归一化缩放。需关注多标的“每包 100 分”场景的权重口径（按包归一还是全局归一）。
R3：合成测试未覆盖真实 203 页 PDF 字体 matrix。本次用合成 markdown 验证合并逻辑，真实 pdfplumber 对扫描件/图片型 PDF 的表格识别仍可能失败（low_text_density 警告路径）。后续需用用户提供的原文件在 staging 复测一次完整链路（含 sidecar /convert → chunk → LLM →落库）。
