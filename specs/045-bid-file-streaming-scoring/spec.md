# Feature Specification: 投标文件流式落盘与文本量设限打分

**Feature Branch**: `045-bid-file-streaming-scoring`

**Created**: 2026-08-17

**Status**: Draft

**Input**: User description: "50MB 拒绝是止血方案（防服务 OOM），投标文件天然很大是真实业务矛盾。根治需要流式落盘 + 按提取后文本量设限。"

## 背景与问题陈述

- PR !2314（第 130 次部署）在打分读取侧加了 50MB 硬上限：超过即返回「投标文件超过 50MB，无法完成打分，请压缩后重新上传」。这是防 OOM 的止血，不是业务正确行为。
- 真实业务矛盾：投标文件普遍远超 50MB（测试环境实测 project 226 存在 1.62GB 投标文件）。止血方案等于把大部分真实投标文件挡在打分之外。
- 根因（lessons-learned §120）：`ScoreBidDocumentLookup` 用 `ofByteArray()` 全量加载到 JVM 堆，1.62GB 直接 `Java heap space`。
- 打分真正消费的是**提取后的文本**，不是原始字节。1.62GB 的 PDF（多为扫描图+高分辨率排版）提取出的纯文本通常远小于原文件。**正确的限制对象是提取后文本量，不是原始文件字节数。**

## Clarifications

### Session 2026-08-17（立项时开放问题，specify/clarify 阶段需逐条收敛）

- Q: 提取后文本量上限取多少？ → A: 待定。锚点是 LLM 阶段 2 打分的有效上下文窗口与成本（参考 spec 044 花费守卫），初值候选 2MB 文本（约百万字），clarify 阶段与用户确认。
- Q: 流式落盘的位置与配额？ → A: 待定。候选为服务器本地临时目录（`/opt/xiyu-bid/tmp/` 类）+ 单文件与总量配额 + 用后即删；需确认测试/生产磁盘余量（生产 99G 盘）。
- Q: 文本提取走 sidecar 还是后端内嵌库？ → A: 待定。现有 document-converter sidecar（Python, 8009）能力需评估：能否接受 URL/流输入、能否流式输出文本、大文件超时行为。
- Q: 超过文本量上限后的行为？ → A: 待定。候选 a) 明确拒绝并提示；b) 截断到上限并在结果中标注「基于前 N 字打分」。倾向 a（打分依据不完整会造成误导性得分），clarify 阶段确认。
- Q: 上传侧（PR !2311 已解除 50MB）与读取侧口径如何统一？ → A: 本规格落地后，读取侧 50MB 字节硬限废止，统一为「字节不设限（受磁盘配额约束）+ 文本量设限」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 大文件投标文件能完成打分 (Priority: P0)

投标人员上传 1.62GB 的投标文件后点击实际打分（阶段 2）。系统将文件**流式**下载到服务器磁盘（全程不整包进入 JVM 堆），提取文本后完成打分。用户无需压缩、无需重新上传，得到与中小文件一致的打分体验。

**Why this priority**: 这是本规格存在的理由——止血方案把最典型的真实投标文件（大文件）挡在核心功能之外。

**Independent Test**: 使用 project 226 的 1.62GB 文件触发 `POST /api/projects/226/score-parse/scoring`，任务进入 PROCESSING 并最终 COMPLETED（或因文本量超限走 US3 的明确拒绝），全程后端无 `OutOfMemoryError`，JVM 堆峰值无 1GB 级尖峰。

**Acceptance Scenarios**:
1. **Given** 项目已上传 1.62GB 投标文件且评分项已解析，**When** 用户触发实际打分，**Then** 系统流式落盘该文件（JVM 堆内存占用与文件大小无关），提取文本并执行打分。
2. **Given** 任意大小（≤ 磁盘配额）的投标文件，**When** 打分读取，**Then** 全链路无 `byte[]` 整包持有原始文件内容。
3. **Given** 提取后文本量在上限内，**When** 打分完成，**Then** 结果与得分依据正常落库，体验与 ≤50MB 文件无差异。

---

### User Story 2 - 服务内存与磁盘安全 (Priority: P0)

大文件落盘与文本提取不得以牺牲服务可用性为代价：任意大小文件不得触发 OOM；磁盘临时文件有配额、有清理，不得写满磁盘拖垮同机服务。

**Why this priority**: 修复 OOM 的初衷不能被根治方案重新引入（磁盘版 OOM）。

**Independent Test**: 并发触发 2 个 1.5GB 级文件打分，监控 JVM 堆峰值（无 1GB 级尖峰）与临时目录占用（不超过配额）；任务结束或失败后临时文件被删除。

**Acceptance Scenarios**:
1. **Given** 落盘空间配额为 Q，**When** 单文件超过 Q 或并发落盘总量将超过 Q，**Then** 拒绝下载并返回明确的配额提示（可区分于文本量超限），不留半截文件。
2. **Given** 打分任务完成、失败或超时，**When** 任务进入终态，**Then** 对应临时文件被删除（含异常路径）。
3. **Given** 服务重启，**When** 启动恢复逻辑运行，**Then** 孤儿临时文件（无对应进行中任务）被清理。

---

### User Story 3 - 提取后文本量超限的明确拒绝 (Priority: P1)

文件字节数不大但文本量巨大（如纯文本型超大文档）时，提取后文本超过上限，系统给出与当前 50MB 拒绝同级别的明确提示，说明是「文本量」超限而非「文件大小」超限，且不产生误导性部分打分。

**Why this priority**: 限制对象从字节换成文本后，必须有对应的用户可理解边界，且避免「截断后打分」造成得分误导。

**Independent Test**: 构造文本量超限的文件（如数百 MB 纯 txt/doc），触发打分，返回超限提示；`score_parse_task` 落 FAILED 且原因可查；不产生部分得分结果。

**Acceptance Scenarios**:
1. **Given** 提取后文本量超过上限 T，**When** 打分执行，**Then** 任务失败并提示文本量超限（文案含具体上限值），不输出部分打分结果。
2. **Given** 提取后文本量不超过 T，**When** 打分执行，**Then** 正常完成，与文件原始字节数无关。

---

### User Story 4 - 读取侧限制口径统一 (Priority: P2)

50MB 字节硬限（PR !2314 止血）在本规格落地后废止；前端提示文案、后端异常语义、wiki 文档同步更新，不留双轨口径。

**Why this priority**: 双轨限制（上传不限、读取按 50MB 字节拒）是止血期已知妥协，长期并存会造成排障与用户沟通混乱。

**Independent Test**: 全局 grep 无残留的「投标文件超过 50MB」打分侧文案（招标解析侧 50MB 属 spec 043 管辖，不在本规格范围）；wiki `score-parse-service.md` 更新为文本量口径。

**Acceptance Scenarios**:
1. **Given** 本规格上线，**When** 用户上传超 50MB 投标文件并打分，**Then** 不再出现「投标文件超过 50MB，无法完成打分」提示。
2. **Given** 本规格上线，**When** 排障人员查阅文档，**Then** wiki 与代码注释中的读取限制均为文本量口径，无过期的 50MB 字节表述。

---

### Edge Cases

- 文件字节数超磁盘配额但文本量很小（高压缩比扫描件）：按 US2 配额拒绝，提示与文本量超限区分。
- 文件字节数很小但文本量超限（纯文本文档）：按 US3 文本量拒绝。
- 流式下载中途断开：按读取失败处理，任务 FAILED，临时文件清理，用户可重试。
- 提取器对损坏/加密文件返回空文本：沿用现有「投标文件解析失败」路径，不误报文本量超限。
- 并发打分多个大文件：配额总量控制生效，后到者明确拒绝而非写满磁盘。
- OBS 签名 URL 过期（大文件下载耗时长）：下载前刷新签名或失败重试一次。
- 扫描件（无文本层）：提取文本近空，走现有「解析失败/无正文」语义，不进入打分。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以流式方式将投标文件从 OBS 下载到服务器磁盘临时位置，全程 MUST NOT 以 `byte[]`/堆缓冲整包持有原始文件内容。
- **FR-002**: 系统 MUST 对临时落盘实施配额管理：单文件上限与并发总量上限；超限时 MUST 拒绝并返回区别于文本量超限的明确提示。
- **FR-003**: 系统 MUST 在任务终态（成功/失败/超时）及服务启动恢复时清理临时文件，不得残留孤儿文件。
- **FR-004**: 系统 MUST 在文本提取完成后按提取后文本量设上限 T；超限时任务 FAILED 并提示文本量超限（含 T 值），MUST NOT 产生部分打分结果。
- **FR-005**: 文本量上限 T 的取值 MUST 在 clarify 阶段与用户确认，锚定 LLM 上下文与成本；落地后 MUST 以配置项（非硬编码）存在。
- **FR-006**: 打分侧 50MB 字节硬限（PR !2314 的 `capSize`/`OversizedBidFileException` 字节语义）MUST 废止或改为仅作「免落盘快路径」优化（小文件直接内存处理），拒绝语义统一为文本量口径。
- **FR-007**: 前端提示、异常语义、wiki 文档 MUST 同步文本量口径，MUST NOT 残留打分侧 50MB 字节文案。
- **FR-008**: 流式链路 MUST 复用既有下载设施（`BoundedHttpDownloader` 的连接复用范式），MUST NOT 每次新建无管理会话。
- **FR-009**: 权限守卫（`assertCurrentUserCanAccessProject`）与任务状态机（PENDING→PROCESSING→COMPLETED/FAILED）MUST 与现网一致，本规格不改变权限与状态语义。

### Key Entities

- **投标文件原始字节**: OBS 对象的原始内容；仅流经网络与磁盘，不进 JVM 堆。
- **临时落盘文件**: 流式下载的磁盘副本；有配额、有生命周期（任务终态即删）。
- **提取后文本**: 打分真正消费的正文；限制对象（上限 T）。
- **磁盘配额**: 单文件与并发总量的落盘上限；超限属资源类拒绝，与文本量超限（业务类拒绝）语义区分。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: project 226 的 1.62GB 投标文件触发打分：无 `OutOfMemoryError`，JVM 堆峰值无 1GB 级尖峰（监控证据），任务到达终态（COMPLETED 或文本量超限 FAILED）。
- **SC-002**: 全链路代码审查确认：原始文件内容无 `byte[]` 整包持有点（`ofByteArray` 类模式为 0）。
- **SC-003**: 任务终态后 60 秒内临时文件被删除；服务重启后孤儿文件清理率 100%。
- **SC-004**: 文本量超限场景返回含 T 值的明确提示，无部分打分结果落库。
- **SC-005**: 全局 grep 打分侧「超过 50MB」文案命中数为 0（排除 spec 043 管辖的招标解析侧与上传侧历史文档）。
- **SC-006**: ≤50MB 小文件打分耗时与现网相当（快路径优化不劣化常规体验）。

## Assumptions

- OBS 侧无单对象大小限制问题（PR !2311 已解除上传侧 50MB；华为云 OBS 单对象上限 5GB，远超业务文件）。
- 测试/生产服务器磁盘余量足以支撑配额设计（生产 99G 盘当前余量需在 plan 阶段实测确认）。
- 文本提取能力（后端内嵌库或 sidecar）可接受磁盘文件路径输入并输出纯文本；若 sidecar 不支持大文件，plan 阶段评估后端流式提取库（如 PDFBox 逐页）。
- 招标解析侧（spec 043）的 50MB 读取上限不在本规格范围；两侧行为差异（招标拒大文件、投标支持大文件）符合业务预期——招标文件多数项目有立项底稿兜底，投标文件无替代来源。
- LLM 阶段 2 打分本身的上下文截断策略（spec 044 花费守卫）与本规格的文本量上限是两层限制：本规格管「入场的文本总量」，spec 044 管「单次 LLM 调用的花费」；两层并存不冲突。
- 本规格不改变打分结果的存储结构（`score_result`）与前端展示组件。
