# 评分解析质量修复：幽灵项过滤与编号排序（fix-score-parse-ghost）

## 概述

测试环境 project 212 暴露两类解析质量问题：
1. **幽灵评分项**：招标文件评分表的表头/汇总行（如"得分"列名 + 总分 100）被 LLM 全文召回当成真实评分项落库，导致权重合计 200、与真实"投标报价"项编号撞号。
2. **编号与顺序失真**：落库顺序按"候选池首次出现顺序"而非评分表真实编号序（6/7 跑到 1 前面）；空编号被自动补成行号假编号（"1"），与真实编号重复；LLM chunk 提取失败被静默跳过且无任何可见痕迹。

本 feature 修复以上解析质量问题，使落库评分项与招标文件评分表一一对应、权重合计可闭环、异常可见。

## 背景

- 四路召回（正则/结构/语义/LLM 全文）产出候选池 → 合并去重 → 权重闭环校验（≠100 触发补漏）→ 落库。
- 现状缺陷链（project 212 task 13 实测）：
  - 表头幽灵候选无编号，去重键独立（dim+detail 指纹），四路去重对它无效；
  - 权重校验发现 200≠100 只会**补漏**，不会**剔除**多余项，方向反了；
  - 警告不阻断，幽灵项照样落库；
  - 落库时空编号自动补 itemIndex（"1"），制造假编号重复；
  - 落库顺序 = 召回首现序，与评分表编号序不一致；
  - LLM chunk 失败（如 chunk 7/15）静默跳过，该段评分项整块丢失且用户不可见。

## 需求

### FR-001 幽灵候选过滤（P0）

召回合并后、权重校验前，过滤非条款幽灵候选。判定规则（纯函数，可单测）：
- 候选 dim 与 detail 归一化后相同（trim+去空白）且长度 ≤ 4 字（如"得分"）；**或**
- 候选无来源文本（sourceText 为空/空白）**且**无编号（code 为空）。

被过滤候选记日志（INFO，含 dim/detail/weight），不阻断流程。四路召回本身的正则路（lane1/2/3）若产出同类幽灵同样被过滤（过滤位置在 merge 之后统一生效）。

### FR-002 权重超载剔除（P0）

权重闭环校验发现合计 > 100（容差 +0.5）时，走"嫌疑剔除"分支而非仅补漏：
- 优先剔除无编号候选；若剔除后合计仍 > 100，再剔除无来源文本候选；
- 每轮剔除后重算合计，回到 100（容差内）即停；
- 剔除动作记日志（WARN，含被剔除项摘要与剔除轮次）；
- 合计 < 100 时维持现有补漏逻辑（recheckGaps）不变；
- 剔尽嫌疑后仍 > 100：保留剩余全部候选，照常落库并带 weightWarning（现有语义）。

### FR-003 编号序落库（P1）

落库前按评分项编号排序：
- 编号可解析为数值的按数值排（1,2,3,4-1,4-2,5,6,7：主段数值 + 子段数值）；
- 不可解析编号的候选保持相对顺序，排在可解析编号之后；
- itemIndex 按排序后顺序重新编号（1..n）；
- code 字段保留原文编号，不改动。

### FR-004 空编号不再补假编号（P1）

落库时编号为空的候选，code 落空串（或保持空），**不得**用行号补位（消除与真实编号撞号）。展示层显示"—"由前端处理，本 feature 不改前端。

### FR-005 LLM chunk 失败可见（P1）

召回四 LLM 提取的单 chunk 失败：先重试 1 次，仍失败再跳过；解析任务的 items 元数据中输出"跳过 chunk 计数"（skippedChunks ≥ 1 时前端可见）。不改变现有"单 chunk 失败不阻断整体"语义。

### FR-006 不变量：真实项零损失（P0 约束）

FR-001/FR-002 的过滤与剔除**不得**误删真实评分项：有编号或有实质条款文本（sourceText 非空）的候选只能因 FR-002 的超载剔除被移除，且移除顺序必须"无编号 → 无来源文本"从弱到强。

## 非目标（Out of Scope）

- 不改前端展示组件（"—" 占位除外的前端逻辑）；
- 不动 markitdown 转换质量（表格转 markdown 的保真度是 sidecar 课题）；
- 不重构四路召回本身（lane1-4 的召回策略不变）；
- 不处理合计 < 100 的补漏逻辑（维持现状）。

## 用户场景与验收

### 场景 1：表头幽灵（project 212 复现）

解析含"得分 | 100"表头的评分表：
- 落库项数 = 真实项数（9 → 8，无幽灵）；
- 权重合计 = 100；
- 无 dim=detail="得分"的行；
- 真实"投标报价"编号 1 唯一。

### 场景 2：编号排序

同一解析结果：
- itemIndex 顺序 = 1,2,3,4-1,4-2,5,6,7（投标报价→商务→技术→质量→售后）；
- code 与原文编号一致。

### 场景 3：LLM chunk 失败

模拟某 chunk 提取连续失败 2 次：
- 整体解析仍完成（不阻断）；
- items meta 含 skippedChunks ≥ 1；
- 重试发生且仅 1 次。

### 场景 4：真实项保护

有编号 + 有条款文本的候选，在合计 ≤ 100 或剔除后已达标的任何分支中均不被删除。

## 成功标准

- 幽灵候选（dim==detail≤4字 或 无code无source）过滤命中率 100%（单测断言）；
- 权重 >100 场景经剔除后合计回到 100 容差内（单测断言）；
- 落库 itemIndex 与编号数值序一致（单测断言）；
- 真实项（有编号或有条款文本）在全部场景零误删（单测断言）；
- 现有 scoreparse 相关测试全部保持绿；
- ArchitectureTest / FPJavaArchitectureTest 全绿（新策略类为纯核心）。

## 假设与依赖

- 幽灵判定阈值（≤4 字、无 code+无 sourceText）基于 project 212 实测样本；后续可用 spec 042 验收集回归。
- FR-005 的 skippedChunks 通过现有 items meta 通道（ScoreParseItemsMetaBuilder）透出，前端消费另行任务。
- 依赖现有 WeightSumCheck / ScoreItemMergePolicy / ScoreItemPersistenceService 结构，不引入新表、零 DB 迁移。
