# Feature Specification: 商机预测实时收件人与历史补发

**Feature Branch**: `agent/codex/opportunity-reminder-live-recipients`

**Created**: 2026-09-15

**Status**: Ready for planning

**Input**: User description: "修复生产环境商机预测提醒的收件人判断，并将上线日前已经到期但未完整提醒的历史项目安全补发一次。接收人是项目经理、投标管理员、投标组长；离职项目经理不发。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 实时解析正确收件人 (Priority: P1)

作为商机预测提醒的业务负责人，我希望每次扫描都依据当前组织架构确认项目经理是否在职，并识别一个人拥有的全部投标角色，从而把提醒发给仍在职的项目经理、投标管理员和投标组长。

**Why this priority**: 当前每日扫描虽然正常执行，但错误的本地单角色缓存导致核心角色接收人数长期为零，是历史和未来提醒持续漏发的直接原因。

**Independent Test**: 准备本地角色成员数为零、实时组织数据中包含一名投标管理员和一名同时拥有投标组长角色的人员，执行一次到期项目扫描；两名核心角色和在职经理均收到一次提醒，离职经理不收到。

**Acceptance Scenarios**:

1. **Given** 本地角色缓存没有投标管理员或投标组长成员，实时组织数据存在在职目标角色人员，**When** 扫描到一个已到预测日期的项目，**Then** 所有实时目标角色人员都在接收人中。
2. **Given** 项目经理在本地仍有关联但实时组织数据标记为离职或已不存在，**When** 项目到达提醒日期，**Then** 不向该项目经理发送提醒。
3. **Given** 同一人员既是项目经理又拥有目标角色，**When** 生成提醒，**Then** 该人员只收到一份通知。

---

### User Story 2 - 补发上线日前历史项目 (Priority: P1)

作为项目经理、投标管理员或投标组长，我希望上线日前已经到达预测日期、但系统当时没有完整发送的历史项目被补发一次，以便不会因为历史导入时间早于功能上线而遗漏商机。

**Why this priority**: 历史项目已经过期，不会通过未来日期自然补回；若不执行补发，业务侧永久缺少这些商机信息。

**Independent Test**: 以固定截止日运行历史补发。一个从未提醒的到期项目向完整实时接收人发送；一个已有经理提醒的到期项目只向缺失的目标角色补发；截止日后的项目不处理。

**Acceptance Scenarios**:

1. **Given** 项目预测日期不晚于截止日且从未生成提醒，**When** 执行历史补发，**Then** 按当前实时接收人生成完整提醒并保留每项目一次的提醒日志。
2. **Given** 项目预测日期不晚于截止日且已有经理提醒，但目标角色从未收到，**When** 执行历史补发，**Then** 只向缺失的投标管理员和投标组长发送，不重复通知项目经理。
3. **Given** 项目预测日期晚于截止日，**When** 执行历史补发，**Then** 项目不产生任何通知或日志变化。

---

### User Story 3 - 安全审计并防止重复补发 (Priority: P2)

作为生产运维执行人，我希望补发动作默认只预览范围，只有显式执行时才写入，并且重复执行不会重复发信，从而能先核对数量再安全操作。

**Why this priority**: 补发会向真实业务人员发送外部消息；范围错误或重复执行会造成集中骚扰且难以撤回。

**Independent Test**: 对同一截止日先运行预览、再执行两次。预览不产生写入；第一次执行数量与预览一致；第二次执行新增通知数为零。

**Acceptance Scenarios**:

1. **Given** 未提供显式执行指令，**When** 运行历史补发，**Then** 只输出候选项目、目标角色和预计通知数量，不写入任何数据、不发送消息。
2. **Given** 已确认预览范围并显式执行，**When** 补发完成，**Then** 输出新建、已存在、跳过和失败的准确计数。
3. **Given** 相同截止日的补发已经成功执行，**When** 再次执行，**Then** 不为同一项目和同一接收人创建第二份通知。

### Edge Cases

- 实时组织接口只返回部分工号时，只使用已明确返回且在职的人员；未返回人员不得用本地缓存猜测为在职。
- 实时组织接口完全不可用时，本轮不发送并记录可定位的失败摘要，避免使用过期角色或人员状态误发。
- 用户缺少可查询的工号时，不作为实时角色或在职经理接收人，并计入跳过原因。
- 同一人员有多个目标角色、同一项目经理也有目标角色时，按用户去重。
- 已有提醒日志但事件库投递尚未完成时，历史角色补发不得改变原有事件重试状态。
- 已有通知只覆盖部分目标角色时，只补尚未拥有该项目通知的实时目标角色。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每次商机预测提醒扫描 MUST 以实时组织架构返回的人员状态和全部系统角色作为收件人事实源。
- **FR-002**: 本地人员缓存 MUST 仅用于将组织工号关联到站内通知用户，不得覆盖实时离职状态或实时角色成员关系。
- **FR-003**: 正常提醒的接收人 MUST 是在职项目经理、所有在职投标管理员、所有在职投标组长的去重并集。
- **FR-004**: 实时接口未返回、明确离职、已删除或缺少工号的项目经理 MUST NOT 接收提醒。
- **FR-005**: 实时接口失败或返回不完整时，系统 MUST 失败关闭，且记录请求人数、返回人数与错误摘要；不得回退到本地角色缓存误发。
- **FR-006**: 历史补发 MUST 只处理预测日期不晚于显式截止日的项目，且不得处理未来预测项目。
- **FR-007**: 从未提醒的历史项目 MUST 复用正常扫描的预测、消息、日志和投递链路生成完整提醒。
- **FR-008**: 已有历史提醒的项目 MUST 只向从未收到该项目商机预测提醒的实时目标角色补发，不得重复通知项目经理。
- **FR-009**: 历史补发 MUST NOT 删除、重置或伪造现有提醒日志，也不得改变原有事件投递重试状态。
- **FR-010**: 历史补发 MUST 默认处于预览模式；只有显式执行参数存在且截止日明确时才允许写入和发送。
- **FR-011**: 预览与执行 MUST 输出候选项目数、从未提醒项目数、仅补角色项目数、实时角色人数、预计或实际用户通知数、去重数、跳过数和失败数。
- **FR-012**: 相同项目与相同接收人的历史补发 MUST 幂等；重复执行不得生成第二份通知。
- **FR-013**: 日常扫描的预测算法、每天 09:00 调度、每项目一次提醒日志和事件库语义 MUST 保持不变。

### Key Entities

- **历史候选项目**: 预测日期不晚于执行截止日的当前项目，分为从未提醒与已有提醒两类。
- **实时人员事实**: 由组织架构按工号返回的在职状态、系统角色集合和姓名；缺失响应不表示在职。
- **项目提醒记录**: 证明某项目已经走过完整提醒链路的既有记录，补发不得删除或重建。
- **用户通知关系**: 某条商机预测通知与一个接收人的关联，用于判断该项目对该用户是否已经送达站内消息。
- **补发结果**: 一次预览或执行的范围与计数，用于生产操作前后核对。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在生产预览中，截止 2026-09-15 的范围与基线核对一致：128 个从未提醒项目、114 个需补核心角色的当前历史项目、3 名实时在职目标角色人员；差异必须在执行前解释。
- **SC-002**: 执行后，每个符合条件的项目对每名实时目标角色最多存在一份新补发通知，已有经理提醒的 114 个项目不新增经理重复通知。
- **SC-003**: 实时组织数据中已离职或不存在的项目经理收到的新增历史提醒数量为 0。
- **SC-004**: 对同一截止日再次执行，新增用户通知数量为 0，且既有提醒日志和事件投递状态不变。
- **SC-005**: 日常提醒扫描在生产数据规模下 60 秒内完成，并在日志中给出扫描项目数、实时查询人数、实时返回人数和各结果计数。

## Assumptions

- 生产执行截止日为 2026-09-15，包含该日；执行前以 dry-run 再确认实际基线。
- 当前用户表已缓存需要映射的 OSS 工号；若实时人员不在本地缓存中，无法建立站内接收人，必须跳过并报告而不是临时创建账号。
- 企微投递继续使用现有通知异步任务；站内通知创建成功不等于企微必然成功，企微失败数需在执行后单独核对。
- 本次不修复历史上缺少工号或企微绑定导致的 30 条经理外发失败，它们作为独立运维问题报告。
- 不新增数据库结构；现有项目提醒记录和用户通知唯一关系足以完成幂等判断。
