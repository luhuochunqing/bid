# Feature Specification: 基于真实数据底座的历史案例精准推荐

**Feature Branch**: `agent/antigravity/061-accurate-historical-case-recommendation`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "围绕第一性原理：在AI 智能案例推荐能准确地推荐相似的历史案例。先梳理 70 个项目的特征抽取脚本，再谈模型推荐，基于真实数据底座重写方案。"

## 背景与第一性原理

在投标编制过程中，编制人员打开“AI 智能案例推荐”抽屉的核心诉求是：**针对当前评分项（如“7×24小时应急售后”或“系统接口对接”），立刻准确找出历史最相似、高质量、可直接复用的真实标书应答案例与原文。**

### 当前现状与核心痛点
1. **数据覆盖严重不足（300 条样本断层）**：服务器 OBS 存储了 70 个历史项目投标文件，包含 8144+ 章节切片，但目前入库到前台推荐唯一只读表 `knowledge_case` 的仅有 300 条样本切片，导致大量细分技术项（如接口集成、特定应急、质保检测）召回结果为 0 条。
2. **特征颗粒度过粗且缺乏业务子主题**：原有提取脚本仅按粗略的“技术/商务”大类划分，缺乏“系统架构”、“售后 SLA”、“应急预案”、“系统对接”、“安全合规”、“物流仓储”等关键细分主题标记，推荐时极易被长文本中的通用招投标停用词（“方案、保障、管理、实施”）带偏。
3. **跨大类渗透与碎片切词偶发**：历史上虽设立了实体抽取与互斥门禁，但在缺乏细粒度子主题的情况下，跨大类软加分或长文本停用词仍存在冲淡核心业务匹配的风险。

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 评分项精准匹配与智能推荐 (Priority: P1)

投标专员在项目投标方案编制阶段打开“AI 智能案例推荐”抽屉，选择某个特定评分项（如“系统接口集成方案”），系统实时分析评分项标题与评分规则，准确推荐出高度匹配的历史案例，并展示高纯度业务关键词与清晰推荐理由（如“命中专属客户(建设银行)”、“同类主题(系统对接与数据集成)”）。

**Why this priority**: 这是特性的核心价值所在。让编制人员一眼看到高度契合的案例，直接解决“找素材难、匹配不准”的根本痛点。

**Independent Test**: 选择真实评分项（如“应急保障措施与售后服务承诺”），调用推荐接口，验证排在第一梯队的均为“售后保障/应急预案”类案例；若当前项目为“三峡集团”，验证三峡历史同类案例以断层优势稳居第一。

**Acceptance Scenarios**:

1. **Given** 当前项目客户主体包含专名“三峡”，**When** 用户请求推荐任意技术评分项，**Then** 若历史案例库存在该专名的同大类案例，该专属客户案例以断层高分稳居推荐列表首位。
2. **Given** 用户选择技术类评分项（如“技术架构与系统安全性”），**When** 系统执行案例推荐，**Then** 纯商务、财务、资质类历史案例被强互斥门禁拦截（得分 0），绝不上浮至前台。
3. **Given** 用户选择的评分项属于“售后保障与SLA服务”，**When** 系统执行推荐，**Then** 具有同类子主题（`SLA_SERVICE`）的历史案例获得明确加分，优先于泛化的总体方案。
4. **Given** 推荐结果展示，**When** 用户查看“命中关键词”与“推荐理由”，**Then** 关键词均为高纯度实体词（如“双活灾备”、“专线对接”），不包含任何机械 2-gram 碎片（如“的标”、“不可”、“双的”）。

### User Story 2 - 70 个历史项目特征深度抽取与全量数据入库 (Priority: P1)

系统后台执行特征抽取与清洗流水线，对服务器上 70 个历史项目完整目录与 8144+ 章节切片进行结构化提炼：自动识别归一化客户专名、项目类型、10 大业务子主题、清洗过滤无价值样板段落，萃取生成 1000 条以上高质量案例并全量写入 `knowledge_case`，每条记录 100% 绑定可直链下载的 OBS 原文路径。

**Why this priority**: 真实数据底座是推荐引擎的基石。没有充足覆盖且具备细粒度标签的数据源，算法优化就是无源之水。必须先做特征抽取脚本，扩充案例库容量与质量。

**Independent Test**: 执行特征抽取脚本自测与全量入库，验证 `knowledge_case` 表历史案例总量达到 1000 条以上，且 100% 带有合法的 `obs_bid_file_key` 和已识别的业务子主题。

**Acceptance Scenarios**:

1. **Given** OBS 目录中的 70 个历史项目 docx 文件与 JSONL 切片，**When** 执行特征抽取脚本，**Then** 脚本输出清洗后的高质量结构化数据集，成功过滤纯目录、纯表格、少于 120 字的无效片段。
2. **Given** 抽取出的切片，**When** 识别其所属项目与客户专名，**Then** 准确剥离“2026.01.20--”、“中国”等前缀，正确提炼出核心企业专名（如“建设银行”、“三峡”）。
3. **Given** 章节标题包含“售后服务”、“应急预案”、“接口规范”等，**When** 执行子主题分类，**Then** 正确打上对应的枚举标签（`SLA_SERVICE` / `EMERGENCY_PLAN` / `INTEGRATION` 等），准确率 $\ge 90\%$。
4. **Given** 数据全量入库后，**When** 统计 `knowledge_case` 表，**Then** 历史案例条数 $\ge 1000$ 条，`obs_bid_file_key` 字段 100% 非空且符合桶路径规范。

---

### User Story 3 - 案例详情查阅与原版标书一键下载 (Priority: P2)

编制人员在推荐抽屉中浏览推荐案例，点击卡片可展开查看完整段落原文，并可一键将内容复制到当前标书，或点击“标书原文”直接下载原版 Word 投标文件查看排版和上下文。

**Why this priority**: 完成从“找到相似案例”到“复用案例并验证上下文”的工作流闭环。

**Independent Test**: 点击任一推荐出来的历史案例卡片，验证其正文排版清晰，点击“标书原文”能在 3 秒内直接触发浏览器下载原版 docx。

**Acceptance Scenarios**:

1. **Given** 推荐结果列表，**When** 用户点击任一卡片“查看详情”，**Then** 抽屉右侧展开完整应答正文与段落结构。
2. **Given** 用户点击卡片上的“标书原文”，**When** 系统校验该案例来源，**Then** 签发 300 秒有效期的 OBS 预签名直链，浏览器立即启动下载。

---

### Edge Cases

- **冷启动评分项（评分规则文本极短或仅有编号）**：评分项标题带有标号（如 `2.2.4(3)`）且无详细描述时，算法自动剥离前缀编号，基于核心业务词（如“系统对接”）进行主题推断与案例召回，不报 400 且不返回空列表。
- **无历史同客户案例的项目**：当前投标项目为全新客户（无历史投标记录）时，系统自动平滑降级，依托业务子主题（Sub-Topic）和行业类型进行高相关度案例推荐，并在推荐理由中提示“同类业务最佳实践”。
- **异常项目名称输入**：当项目名包含非常规字符、口语化文本（如“朱双双的标讯不可编辑”）时，标点分层抽取器配合招投标停用词库进行清洗，绝不产生非法切片或错误推荐理由。
- **原版标书在 OBS 缺失或重命名**：若用户点击“标书原文”但底层文件不存在，系统给出清晰友好的提示“原版标书正在同步中”，不下载空文件，不抛出系统内部 500 异常。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供 70 个历史项目的特征抽取脚本（`scripts/extract-historical-case-features.py`），具备以下自动化提炼能力：
  - 核心企业专名抽取（剥离年份、日期、地域、行政前缀）；
  - 招投标细分业务子主题（Sub-Topic）确定性规则分类；
  - 段落内容充实度与质量评分（0~100）；
  - 完整原版文件 OBS 对象键（`obs_bid_file_key`）有效性校验。
- **FR-002**: 特征抽取流水线必须包含质量过滤门禁，物理过滤字数少于 120 字、纯声明、纯发票资质清单等无实际应答复用价值的样板段落。
- **FR-003**: 数据库 `knowledge_case` 表必须扩展支持存储业务子主题（`sub_topic`，VARCHAR(50)）与质量评分（`quality_score`，INT），并通过幂等导入脚本将有效历史案例扩充至 1000 条以上。
- **FR-004**: 评分项案例匹配策略（`ScoreItemCaseMatchPolicy`）必须设立宏观大类强互斥门禁（Hard Gate）：技术类评分项与纯商务/财务案例冲突时一票否决（最终得分为 0）。
- **FR-005**: 推荐算法必须支持“项目专属客户实体匹配”（满分 25 分）：当候选案例所属项目或客户实体命中当前项目的专属专名时，赋予断层式优先加分。
- **FR-006**: 推荐算法必须支持“业务子主题（Sub-Topic）精准匹配”（满分 25 分）：当评分项推断主题与案例标注主题一致时赋予高权重加分。
- **FR-007**: 推荐算法必须前置过滤招投标通用停用词，采用标点分层实体抽取器提取并列高价值特征词，严禁在前台展示任何机械 2-gram 切词碎片。
- **FR-008**: 推荐接口必须保持纯无状态与纯核心（Pure Core）架构规范，单次推荐请求响应耗时在 P95 下必须小于 300ms。
- **FR-009**: 推荐卡片必须联动已有原文下载服务，支持点击“标书原文”按需签发预签名直链下载原版 docx 文件。

### Key Entities

- **历史案例（KnowledgeCase）**: 案例库中的单条应答单元，包含来源项目名、所属客户专名、评分项标题、应答正文预览与全文、业务大类（技术/商务）、业务子主题（`sub_topic`）、质量分（`quality_score`）及原版标书 OBS 对象键（`obs_bid_file_key`）。
- **业务子主题（Sub-Topic）**: 招投标应答案例的细分业务分类，包括但不限于：
  - `SYS_ARCH`（系统架构与设计）
  - `SLA_SERVICE`（售后服务与SLA保障）
  - `EMERGENCY_PLAN`（应急预案与突发事件响应）
  - `INTEGRATION`（系统对接与数据集成）
  - `SECURITY_COMPLIANCE`（网络安全与等保合规）
  - `DELIVERY_PROGRESS`（项目进度与实施计划）
  - `LOGISTICS_WAREHOUSE`（仓储管理与物流配送）
  - `QUALITY_CONTROL`（质量保证与验收标准）
  - `ORG_STAFF`（团队组织与人员配置）
  - `COMMERCIAL_TERMS`（商务条款与偏离响应）
- **推荐评分上下文（RecommendationCriteria）**: 推荐输入上下文，包含当前项目名称、所属客户专名、行业类型、当前评分项标题、评分规则文本及推断的业务子主题。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 案例库中具备细粒度标签的有效历史案例数从 300 条扩充至 1000 条以上，覆盖率提升 3 倍以上。
- **SC-002**: 在专属客户测试用例（如三峡集团、中国建设银行）中，同客户历史案例在推荐列表前 3 位的命中率达到 100%。
- **SC-003**: 跨大类误推荐（技术项推荐财务案例）的发生率为 0%（一票否决门禁 100% 拦截）。
- **SC-004**: 推荐结果展示的“命中关键词”中，无语义的 2-gram 字符碎末（如“的标”、“不可”、“双的”）出现率为 0%。
- **SC-005**: 推荐抽屉调用接口 `POST /api/projects/{id}/cases/recommend` 的单次计算响应时间 P95 小于 300ms。
- **SC-006**: 全量入库的历史案例中，“标书原文”下载链接签发有效率为 100%。

---

## Assumptions

- 历史投标文件存放在服务器 OBS 目录 `/data/obs_winbid/2026年（投标文件）/`，源文件格式均为 Word（.docx）且可正常读取。
- 推荐计算不引入重型外部向量数据库组件，依托 MySQL 8.0 存储元数据与纯核心算法进行实时内存算分，遵循现有 Constitution 与“Boring Proven Patterns”。
- 策略算法实现严格遵守 FP-Java 规范：纯核心逻辑无外部副作用、无 Spring 依赖、入参对象不可变、完全可单测。
