# Feature Specification: 招标文件大文件解析放行

**Feature Branch**: `065-tender-large-file-parse`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "招标文件走 OBS 已支持大文件上传（上限约 512MB），但 AI 评分项解析阶段仍以 50MB 字节硬限拒绝（提示“招标文件超过 50MB，无法解析”）。要求：上传放行后解析也能解（只要文档文本量正常）；极端超大文本明确拒绝且提示可操作动作；前端在上传前明示限制、解析失败有指引。TypeSafe 补强（chunk 相关性重排 + 抽取验证级联）记为 Phase 2 附录。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 大文件招标文件正常解析 (Priority: P1)

投标人员在立项阶段上传超过 50MB 的招标文件（经 OBS 直传，上限以内，如 80MB 扫描版 PDF），随后打开「AI 评分标准解析」抽屉，解析正常完成并产出评分项清单，不再看到「招标文件超过 50MB，无法解析」。

**Why this priority**: 当前上传与解析口径断裂（上传能存、解析拒解），用户上传成功后走进死路（解析阶段无法再传、立项提交后更无法替换），属主流程断裂，必须最先修复。

**Independent Test**: 准备一份 80MB 左右、以扫描图片为主的真实招标 PDF（提取后文本量正常），经 OBS 上传后触发解析，断言解析成功且评分项清单与该文件 50MB 以内压缩版的解析结果一致（项数、总权重一致）。

**Acceptance Scenarios**:

1. **Given** 立项已上传 80MB 招标文件且无历史解析底稿，**When** 用户打开解析抽屉或点击「重新解析」，**Then** 解析成功产出评分项，不报 50MB 超限。
2. **Given** 同一份大文件的 50MB 以内压缩版，**When** 分别解析两版，**Then** 评分项清单一致（项数相同、总权重相同）。
3. **Given** 解析进行中，**When** 观察服务进程内存，**Then** 不发生内存溢出失败（堆占用不随文件字节数等比增长）。

---

### User Story 2 - 极端超大文本明确拒绝 (Priority: P1)

投标人员误传极端文档（如上千万字文字版巨兽、文本量超过约 500 万字），解析任务失败并给出可操作提示（检查是否误传或拆分文档），不输出残缺的、误导性的部分评分项。

**Why this priority**: 放开字节限制后必须有新护栏，否则超大文本会导致解析耗时失控、费用失控或后半部分评分项静默丢失；明确拒绝比“解出一半”更正确。

**Independent Test**: 构造文本量超过上限的文档触发解析，断言任务失败、提示文案含上限说明与建议动作，且评分项清单不被残缺结果覆盖。

**Acceptance Scenarios**:

1. **Given** 招标文件提取后文本量超过上限，**When** 发起解析，**Then** 任务失败并提示文本量超限（含上限值与“检查误传/拆分文档”建议），不落库部分评分项。
2. **Given** 文本量刚好在上限内的大文件，**When** 发起解析，**Then** 正常完成。

---

### User Story 3 - 超限指引可操作 (Priority: P2)

用户在上传前即知道解析口径的限制；解析失败时知道下一步做什么（压缩/拆分/未提交前回立项替换/已提交联系管理员），而不是对着「重试」按钮反复失败。

**Why this priority**: 与主流程断裂同源的体验问题；文案改动小、风险低，但能消除“传上去解不出、解不出换不掉”的困惑。

**Independent Test**: 分别走查立项上传区提示文案、超限拦截提示、解析抽屉失败态文案，断言三处口径一致且动作指引正确。

**Acceptance Scenarios**:

1. **Given** 用户在立项阶段准备上传招标文件，**When** 查看上传区，**Then** 看到上传上限与解析口径说明（解析按文本量，上限约 500 万字；扫描大 PDF 压缩后一般可过）。
2. **Given** 用户选择超过上传配额的文件，**When** 确认上传，**Then** 上传前即被拒绝并提示压缩后重传，不会“存上了解不出”。
3. **Given** 解析因文本量超限失败，**When** 查看抽屉失败态，**Then** 看到超限原因 + 下一步动作（回立项替换/已提交联系管理员），「重新解析」按钮文案统一。

---

### Edge Cases

- 文件大小刚好 50MB：视为允许（现行“含 50MB”口径保持）。
- 扫描图 PDF（字节大、文本小）：放行并正常解析，不因字节数拒绝。
- 超大文件但有可用历史解析底稿：沿用现行回退底稿行为，不报错（spec 043 语义保持）。
- OBS 直传失败回退传统上传路径：仍受 50MB 上传限制约束，提示上传侧文案（与解析侧文案区分）。
- 立项已提交/已通过（锁态）：用户无法自行替换招标文件，失败态指引必须导向联系管理员，而非让其回立项操作。
- 解析中途服务重启/超时：任务失败原因可区分（超限 vs 超时 vs 读失败），不混用同一文案。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 解析侧 MUST 不再以 50MB 文件字节数作为拒绝依据；字节数只用于上传配额与下载配额判断。
- **FR-002**: 系统 MUST 在解析前以提取后文本量作为是否可解的判定口径；上限默认约 500 万字，以配置项存在（非硬编码），可在不改代码的前提下按环境调整。
- **FR-003**: 系统 MUST 以流式方式读取与转换大文件，解析过程的内存占用 MUST NOT 随文件字节数等比增长（大文件不得整包载入内存）。
- **FR-004**: 文本量超限时系统 MUST 明确拒绝并提示上限值与建议动作（检查是否误传或拆分文档），MUST NOT 输出部分评分项或覆盖已有可用结果。
- **FR-005**: 上传入口 MUST 在上传前按上传配额做前置拦截（超配额直接拒，提示压缩后重传），不得出现“上传成功但注定解析失败”的文件。
- **FR-006**: 立项上传区提示文案 MUST 同时说明上传上限与解析口径（解析按文本量），扫描大 PDF 给出一句话压缩指引；解析抽屉失败态 MUST 给出下一步动作指引（含锁态导向管理员），「重试」按钮文案统一为「重新解析」。
- **FR-007**: 既有行为 MUST 保持：无文件时提示回立项上传；超大且有可用历史底稿时回退底稿；50MB 以内常规文件解析行为零变化。

### Key Entities

- **TenderIntake（取正文结果）**: 有源则含正文来源；无源则含失败原因，失败原因 MUST 区分“无文件”“文本量超限”“读取失败”三类，不可混用同一文案。
- **Parse Task（解析任务）**: 失败时 MUST 记录可区分的原因（供抽屉展示与重跑决策）；文本量超限失败 MUST NOT 覆盖已有可用评分项。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 80MB 扫描版招标 PDF（文本量正常）从上传到解析产出评分项一次通过，失败率与 50MB 以内版本无差异。
- **SC-002**: 文本量超上限的文档 100% 被明确拒绝且提示含上限值与建议动作，零残缺结果落库。
- **SC-003**: 大文件解析全程无内存溢出失败；相同文本量的大小字节文件耗时差异在合理范围内（字节数只影响传输，不决定成败）。
- **SC-004**: 用户走查三处文案（上传区、上传拦截、解析失败态）一次看懂下一步动作，因“超限不知怎么办”产生的重复重试降为零。

## Assumptions

- 生产环境 OBS 直传已启用；上传配额默认单文件 512MB（沿用打分链路现行配额口径）。
- 文本量上限默认约 500 万字（沿用打分链路 spec 045 现行口径，极宽松，几乎只拦误传）。
- 复用 sidecar 现有流式转换端点，不新增解析库依赖；不改分块大小（4k）与模型选型。
- TypeSafe 外部 verifier 接入需另过安全评审（招标文件为敏感数据，且当前无 API 密钥做过实测），故列为 Phase 2，不在本期范围。
- 后端 `ScoreParseAppService` 现 295 行、硬上限 300 行，实现阶段必须拆分纯函数以腾出行预算（plan 阶段定案）。

## Appendix A - Phase 2：TypeSafe 补强（本期不做，附录立项）

> 来源：TypeSafe 技能评审（live docs：how-to-build-with-system-one、sde_cascade、rerank、citation_check）。前提：完成安全评审并取得 API 密钥后实施；阈值须在自有标书上重测校准，不得照搬 cookbook 示例值。

- **A1. chunk 相关性重排**：现行 `filterRelevantChunks` 为关键词正则，大文档易漏后半部分评分表。Phase 2 对每 chunk 增加一个 Noul 判断（“本块是否含评分规则？”），按得分排序截取 Top-N 再进生成抽取；独立问题单次批量并行。预期：召回完整性提升，生成调用量下降。
- **A2. 抽取验证级联（SDE cascade）**：现行生成式 JSON 直接信任。Phase 2 增加：cheap 抽取 → Jev per-field 验证电池（hallucinated / off_target / unreasonable，坏=TRUE）→ `max` 门（任一超阈即升级）→ 仅被 flag 的 chunk 走强模型/人工。Citation check（supports / contradicts / says_nothing + 置信度门）接入现有 `AUTO_APPROVED / REVIEW_REQUIRED` 复核流。预期：把超大文档“全量贵调用”变为“便宜全量 + 贵只付被 flag 的”，幻觉检出率提升。
- **A3. 增量评估**：新增 1 个纯核心验证器类 + 2 个阈值配置；先在现有模型通道内做同构 verifier 原型验证收益，再决定是否引入外部 Jev 依赖。
