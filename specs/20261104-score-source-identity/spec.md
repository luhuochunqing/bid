# Feature Specification: 同来源评分身份与 OCR 失败可见性

**Feature Branch**: `agent/gemini/diagnose-score43-119`  
**Created**: 2026-11-04  
**Status**: Approved for implementation — 用户在诊断结果后明确“立刻修复”。

## User Scenarios & Testing

### US1 同一评分单元只计一次 (P1)
用户重新解析同一文件，分块交叠或定向重试改变编号/名称时，同一原文评分单元仍只出现一次。project43 的服务5、整体方案10、项目团队4不再重复。
**Independent Test**: 对两个合并入口回放别名变化，并通过真实 handler 运行完整评分章节结构；11个评分单元合计100且规则非空。
**Acceptance Scenarios**: 同来源同规则不同编号只计一次；同格不同原文子项保留；不同方案/文档/来源保留；父项别名合并后子项仍指向保留父项；不同权重不得靠丢弃凑总分。

### US2 OCR 配置与失败原因一致 (P1)
评分解析在没有专用覆盖时使用已配置的通用百度OCR凭证；显式专用环境覆盖仍有效。认证失败、业务错误、全部页面失败仍保留诊断，让任务进入可解释的人工复核状态。
**Independent Test**: 真正加载 application.yml 的属性绑定测试；本地故障客户端经 enricher → acquisition → handler 验证错误透传。
**Acceptance Scenarios**: 共享凭证一致；专用覆盖优先；全失败保留原artifact与失败页；部分失败保留成功页与诊断；正常关闭OCR不产生失败诊断。

## Requirements
- FR-001 来源身份必须包含方案、文档/表/单元格和原文规则边界，不能用模型编号、名称或总分判断重复。
- FR-002 去重不得丢失完整原文、原来源定位和父子关系；无法证明同一单元的候选保留待核验。
- FR-003 重试只替换被选中的失败来源，正常候选和其他来源保持完整。
- FR-004 OCR失败进入任务诊断，不得仅写日志或以零表直接吞掉。
- FR-005 不引入任何明文新凭证；配置引用统一来源且支持既有覆盖。
- FR-006 不直接修改生产候选或正式评分；代码验证与上线业务验收分开记录。

## Success Criteria
- SC-001 已保存的同源重复用例在基线失败，修复后两个入口均通过。
- SC-002 真实评分结构11项分别为30/5/10/10/10/5/10/4/4/6/6，总分100；不以单独总分断言作为验收。
- SC-003 OCR401/业务错误/中断均有可识别诊断；配置默认解析不再落入失效的专用凭证。
- SC-004 同格多子项、跨文件/方案、父子关系、差异权重边界均保留；完整影响域测试与独立审查有证据。

## Scope
无数据库结构变化，无全局解析重构，无生产强制采纳。原PDF及运行快照仅本地忽略目录，不提交客户原件。
