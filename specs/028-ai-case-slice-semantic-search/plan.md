# Implementation Plan: AI 案例切片语义检索

**Branch**: `agent/claude/ai-case-slice-semantic-search` | **Date**: 2026-07-04 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/028-ai-case-slice-semantic-search/spec.md`

## Summary

为西域数智化投标管理平台新增"AI 案例切片语义检索"能力：把服务器上 70 个历史投标文件抽取出的 8144 个章节切片导入数据库，生成语义向量，并基于向量相似度 + 业务规则精排，向当前项目的评分项推荐最相关的历史应答片段。本阶段不修改现有 `knowledge_case` 表，而是新建独立的 `bid_case_slice` 表作为"历史投标文件参考素材库"。

## Technical Context

**Language/Version**: Java 21 + Spring Boot 3.2

**Primary Dependencies**: Spring Data JPA, Flyway, MySQL 8.0 Connector/J, OpenAI Java SDK 4.32.0

**Storage**: MySQL 8.0（`bid_case_slice` 表），向量以 `MEDIUMBLOB` 存储；应用启动时加载到内存 `ConcurrentHashMap` 做相似度计算。

**Testing**: JUnit 5 + Mockito（后端单元测试），ArchUnit（架构门禁），mvn test 全量验证。

**Target Platform**: Linux/macOS 服务器，Spring Boot 后端服务。

**Project Type**: Web service backend feature.

**Performance Goals**: 推荐接口 p95 < 5s（在向量化完成前提下）；Top-20 推荐计算 < 200ms。

**Constraints**:
- 必须使用真实 API，禁止 Mock（Constitution II）。
- 纯核心与命令式外壳分离，Application Service 只做编排（Constitution I）。
- 单 Java 文件软上限 200 行，硬上限 300 行（Constitution IV）。
- 新增 `@PreAuthorize` 只允许 `isAuthenticated()` 或 `hasAuthority('<permissionKey>')`（Constitution VI）。
- 涉及 `projectId` 的接口 MUST 通过 `ProjectAccessScopeService` 校验（Constitution Security & Access Control）。
- `Collectors.toMap` 必须提供 merge function（Constitution VII）。

**Scale/Scope**: 8144 条切片，1024 维 float 向量，约 33MB 内存占用。

## Constitution Check

| Principle | Status | Notes |
|---|---|---|
| I. FP-Java Architecture | PASS | 精排策略 `BidCaseSliceMatchPolicy` 作为纯核心；Application Service 仅编排；Repository 仅数据访问；DTO 转换由独立 assembler/policy 负责。 |
| II. Real-API Only | PASS | Embedding 调用走真实 provider（通义千问/OpenAI/豆包）；不引入 Mock embedding client。 |
| III. TDD | PASS | 每个纯核心类与编排服务先写测试；新增 ArchUnit 规则防止 `Collectors.toMap` 2 参数版本。 |
| IV. Split-First & Simplicity | PASS | 每个类职责单一，单文件不超过 300 行；`BidCaseSliceMatchPolicy` / `BidCaseSliceRecommendAppService` / `BidCaseSliceVectorCache` / `EmbeddingClient` 分离。 |
| V. OSS Integration | N/A | 本功能不涉及 OSS 集成。 |
| VI. Authorization Unification | PASS | Controller 使用 `isAuthenticated()`，资源权限下沉到 Service 层 `ProjectAccessScopeService.assertCurrentUserCanAccessProject`。 |
| VII. Defensive Collection & Graceful Degradation | PASS | `Collectors.toMap` 使用 3 参数版本；embedding 服务不可用时返回降级提示；异常 handler 打印堆栈 + Sentry。 |
| VIII. Boring Proven Patterns | PASS | 使用 MySQL BLOB + 内存余弦，不引入新向量数据库；复用现有 `RoutingAiProvider` 与 `ProjectAccessScopeService`。 |

## Phase Breakdown

### Phase 0: Research (Completed)

- 已确认 `RoutingAiProvider` 不支持 embedding，需要扩展接口与配置。
- 已确认项目无向量数据库，采用 MySQL BLOB + 内存余弦。
- 已确认 74 个项目中 59 个有招标文件，但本阶段仅使用已抽取的 8144 条切片。
- 已确定默认 embedding provider 为通义千问 text-embedding-v3（1024 维）。

### Phase 1: Design (Completed)

- 数据模型：`bid_case_slice` 表结构见 [data-model.md](data-model.md)。
- API 契约：见 [contracts/api.md](contracts/api.md)。
- 召回 + 精排架构：向量余弦召回 Top-50 → `BidCaseSliceMatchPolicy` 精排 → Top-20。
- 权限：复用 `ProjectAccessScopeService.assertCurrentUserCanAccessProject`。

## Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| DeepSeek 默认 provider 不支持 embedding | 功能无法使用 | 默认使用通义千问；在配置中明确说明 DeepSeek 不可选；提供 NoopEmbeddingClient 兜底 |
| 通义千问 API key 未购买 | 无法生成向量 | 代码先完成，等用户购买 key 后执行批量向量化 |
| 8144 条切片向量化耗时过长 | 阻塞上线 | 限速 10 QPS、断点续跑、后台任务 |
| 向量缓存占用内存过大 | 启动慢 / OOM | 8144×1024×4≈33MB，可控；未来规模增长后迁移到 Redis Stack |
| 推荐结果语义不相关 | 用户不满意 | 精排策略结合标题匹配、文件类别、正文充实度；上线后人工抽检调优 |
