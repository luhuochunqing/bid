# Feature Specification: 根治评分项权重合计缺口

**Feature Branch**: `agent/trae/047-fix-score-weight-gap`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "totalWeight 90≠100 属解析质量缺口（weightWarning 透明提示），必须根治"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 评分项权重合计必须恒等于 100 (Priority: P1)

用户在项目详情页"评分对标"看到每个投标文件的评分项结果时，应当看到权重合计**恒等于 100**，
而不是 90 或其它非 100 值。当前 spec/046 仅在没有幽灵项、超载被剔除后透出一个
`weightWarning` 提示（合计=90），用户仍会看到权重大约缺 10 分的异常结果。

**Why this priority**: 权重合计 = 100 是评分的根本不变量。合计 ≠ 100 会让"实际得分/预计得分"
等派生值语义失真（如权重占比、总分换算），用户看到不完整的评分项会误判投标文件质量。
这是数据正确性缺陷，优先于其它改进。

**Independent Test**: 对一个权重合计 ≠ 100 的候选集，系统无需依赖 LLM 二次回补即可将
合计稳定到 100。可单测验证：任意候选权重集合在结果集输出中合计恒为 100。

**Acceptance Scenarios**:

1. **Given** LLM 提取的候选评分项权重合计为 90（缺 10 分），**When** 解析完成落库，
   **Then** 结果集中各项权重按"补齐后合计=100"归一，合计恰为 100，且结果带"原合计 90 已补齐"信号。
2. **Given** LLM 提取合计为 200（超载，超 100），**When** 解析完成落库，
   **Then** 结果集合计被归一/修剪到 100，不出现合计 >100 的越界结果。
3. **Given** 合计恰好 = 100，**When** 解析完成落库，**Then** 各项权重保持原值，不做任何变更。

---

### User Story 2 - 归一化不扭曲相对权重结构 (Priority: P2)

系统在对合计做归一化到 100 时，必须保持各评分项之间的相对权重比例不变；同时采用确定性
规则分配因四舍五入产生的余数，避免同一输入在不同运行时产生不同的权重结果。

**Why this priority**: 若归一化采用"把差额随意塞给某一项"的简单补足，会扭曲真实评分结构，
产生看似正确实则错误的权重。确定性保证结果可复现、可测试。

**Independent Test**: 给定同一组候选权重，连续调用两次归一化，输出权重集合逐位一致；
相对占比与原权重占比一致（在单精度误差内）。

**Acceptance Scenarios**:

1. **Given** 候选权重 [10, 20, 70] 合计 100，**When** 归一化，**Then** 输出仍为 [10, 20, 70]，
   不因归一化路径而变。
2. **Given** 候选权重合计 ≠ 100，**When** 归一化，**Then** 各项相对比例缩放后合计恰为 100，
   余数按确定性规则（如最大余数法）分配，结果可复现。
3. **Given** 候选权重合计 = 0（全部无法解析），**When** 归一化，**Then** 不产生除零/空权重，
   维持原候选语义（保留 weightWarning 兜底，不强行捏造权重）。

---

### User Story 3 - 缺口来源对用户可见 (Priority: P3)

当归一化发生时（即原始 LLM 提取合计 ≠ 100），系统应当让用户知道"这是经权重补齐后的结果"，
而不能静默修正，避免用户误以为系统能 100% 还原招标文件的每个评分项。

**Why this priority**: 归一化是数据修正手段，不是真实的提取完整性。若完全静默，用户会把
补齐后的权重当作招标文件原文，属误导性呈现。保留轻量可见性并合并到 weightWarning 语义即可。

**Independent Test**: 归一化发生后通过状态字段暴露"原合计≠100"信号，前端可据此决定是否
呈现提示；未归一化时该信号为空。

**Acceptance Scenarios**:

1. **Given** 原合计 = 90 触发归一化，**When** 解析落库，**Then** 结果带标记"原合计 90，已补齐到 100"。
2. **Given** 原合计 = 100 未归一化，**When** 解析落库，**Then** 不产生该标记。

---

### Edge Cases

- **合计恰好 = 100**：不做任何变更，原值透传（US1 场景 3）。
- **合计 = 0**（所有项权重无法解析）：不能除零捏造权重，保留 weightWarning，不强行归一。
- **合计 > 100（超载，如 200）**：必须修剪/归一到 100，不能保留越界结果。
- **整数权重归一化产生小数**：需确定性舍入（如最大余数法）保证合计恰为 100 且结果可复现。
- **单一项权重为 100**：归一化后仍应为 100（不溢出）。
- **空候选集**：与 spec/046 ItemCountCheck 的"0 项失败"逻辑一致，归一化不改变失败终态判定。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在评分项权重合计 ≠ 100（超出容差 ±0.5）时，对候选集执行权重归一化，
  使落库合计恒等于 100，替代当前"仅透出 weightWarning"的提示式处理。
- **FR-002**: 归一化 MUST 采用**按比例缩放 + 确定性余数分配**策略，保持各项相对权重比例，
  同一输入产生确定一致输出。
- **FR-003**: 归一化 MUST 处理合计 >100（超载）与 <100（缺口）两种情形，均收敛到 100。
- **FR-004**: 归一化 MUST NOT 处理合计 = 0 的候选集（避免除零/捏造权重），此类场景保留现有
  weightWarning 兜底语义。
- **FR-005**: 当归一化实际发生时，结果 MUST 携带"原始合计"信号（缺省 null），供前端决定是否
  呈现"原合计 X，已补齐到 100"的轻量提示。此信号并入现有 weightWarning 语义，不新增独立告警。
- **FR-006**: 归一化逻辑 MUST 作为纯核心（Pure Core）实现，不依赖 Spring/框架，可独立单测
  （呼应 constitution Principle I FP-Java）。

- **FR-007**: 前端是否展示"原合计 X 已补齐"的提示条，由前端根据 FR-005 信号自行决定；
  展示文案由设计/产品侧确认后再定，此为交互呈现影响，不阻塞核心归一化实现。

### Key Entities

- **评分项候选 (ScoreCandidate)**: 单个评分项，含 `code / dim / detail / weight / sourceText`。
  归一化仅改写 `weight`，其余字段保持不变。
- **权重合计信号**: 归一化输出携带的原始合计快照（如 `90`），用于 FR-005 可见性。
  缺省 `null` 表示未归一化（原合计即 100）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的解析结果（不含"0项失败"终态），其权重合计恒等于 100，
  不再出现 totalWeight=90 之类的缺口结果。
- **SC-002**: 归一化逻辑被纯单测覆盖 ≥ 10 个用例，覆盖缺口/超载/恰好100/合计0/单100/整数舍入等
  全部分支；归一化后的方案总分列表不再产生越界分数。
- **SC-003**: 归一化结果可复现——同一候选输入在不同运行时输出权重集合完全一致。
- **SC-004**: project 212 复测：原始合计 90 的场景，落库后合计=100，评分项数量不变，
  weightWarning 保留"原 90 已补齐"信号。

## Assumptions

- "根治"定义为：落库的权重合计 MUST 恒等于 100，而非仅提示。提示（weightWarning）保留并升级为
  携带原合计信号，不删除。
- 归一化会改变单项权重的原始数值（尤其产生小数），此为本 feature 的目标行为；如需保留招标文件
  原文整数权重用于展示原文，属前端展示层职责，不在本 spec 范围。
- spec/046 的幽灵过滤、超载剔除（>100.5）、编号排序、@Async 事务、chunk 可见性均视为已完成基线，
  本 feature 只在其结果之上增加权重归一化收敛，不改动这些已实现逻辑。
- 前端静态展示文案（FR-007）由产品/设计确认，不阻塞后端核心归一化实现。
- 归一化仅在"候选集权重可解析且合计>0"时生效；合计=0 遵循既有失败/兜底语义。
