**验收审查结论背景**: 2026-08-16 对已合并的 PR !2292（AI 评分标准解析 V3 双阶段抽屉）做了 PRD（飞书 D6fUdxPpJojW5Tx6cW5cyHcAnCe）× 原型（docs/prototypes/AI评分标准解析-V3.html）× 代码三方审查，判定 FAIL：1 项 P0（后端编译失败）、1 项 P1（待确认项显示为 0 分）、5 项 P2 偏差、若干流程与文档失实。其中 P0（OpenAiScoreAnalyzer 缺失 import）已由 PR !2298（043 分支）顺手修复，本 feature 基于 043 分支开工，收敛剩余整改项。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 待确认项不再误显示为 0 分 (Priority: P1)

投标负责人打开「AI 评分标准解析」抽屉查看阶段 1 预计得分。当某个客观项因知识库无对应数据或单项计算失败而处于"待确认"（无预判得分）时，表格得分列必须显示"待确认"文字，不得显示红色"0 分"——否则负责人会误以为该资质已被判定不满足而放弃投标或错误投入资源。PRD 1.3 明文："知识库中无对应数据的客观项，预计得分显示'待确认'"。

**Why this priority**: 错误的 0 分直接误导投标决策，且当前实现中同一行的状态列显示"待确认"、得分列显示红色 0 分，自相矛盾，属于核心计分展示错误。

**Independent Test**: 构造一个客观项（后端返回无预判得分 + 待确认状态），打开抽屉，断言得分列渲染"待确认"样式而非 0 分红色样式；同场景下合计行不把它计入 0 分求和口径变化。

**Acceptance Scenarios**:

1. **Given** 阶段 1 某客观项预判得分为空（待人工确认），**When** 用户打开抽屉查看评分标准表，**Then** 该项得分列显示灰色"待确认"，不显示数字 0，不带零分红色样式
2. **Given** 阶段 1 某客观项预判得分为空，**When** 用户点击该项「详情」按钮，**Then** 弹窗"预计得分"一栏显示"待确认"，与表格口径一致
3. **Given** 阶段 1 某客观项知识库完全未匹配（预判 0 分、状态不满足），**When** 用户查看表格，**Then** 该项显示红色 0 分（真实零分不受本次修复影响）
4. **Given** 主观项（无预判得分、待确认），**When** 用户查看表格与详情，**Then** 显示"待确认"（回归验证，现有行为不得劣化）

---

### User Story 2 - 详情弹窗长内容可读 (Priority: P2)

评标协作人员查看某不满足评分项详情时，弹窗同时包含评分依据、标书引用、缺失说明、修改建议四段长文本。弹窗整体高度不得超过视口的 70%，超出部分在弹窗内容区内部滚动，保证关闭按钮与标题始终可见（PRD 6.4）。

**Why this priority**: 纯 UI 可用性问题，不阻断流程，但影响验收演示时的专业观感。

**Independent Test**: 构造含全部四段长文本的详情数据，打开弹窗，断言弹窗高度受限于视口 70% 且内容区可滚动。

**Acceptance Scenarios**:

1. **Given** 某阶段 2 评分项详情含超长引用与建议文本，**When** 用户打开详情弹窗，**Then** 弹窗不超出视口高度的 70%，超出内容在弹窗内滚动

---

### User Story 3 - 状态视觉与文案对齐产品规范 (Priority: P2)

用户查看评分表时，"待确认"状态的文字应为灰色并保留蓝色圆点前缀（PRD 6.5：满足=绿 / 不满足=红 / 待确认=灰字+蓝点）；上传投标文件超过 50MB 时提示文案应为"文件大小超过限制（50MB），请压缩后重新上传"（PRD 5.3）。

**Why this priority**: 与 PRD 明文的视觉/文案规范不一致，属验收偏差，改动小、风险低。

**Independent Test**: 视觉走查待确认行（灰字+蓝点）；构造 >50MB 投标文件上传，断言提示文案逐字符合 PRD 5.3。

**Acceptance Scenarios**:

1. **Given** 表格中存在"待确认"状态行，**When** 用户查看，**Then** 状态文字为灰色、圆点为蓝色
2. **Given** 用户上传超过 50MB 的投标文件，**When** 后端拒绝，**Then** 用户看到"文件大小超过限制（50MB），请压缩后重新上传"

---

### User Story 4 - 验收记录与工程纪律真实性 (Priority: P3)

后续维护者查阅 specs/042 验收清单与验收交接文档时，看到的声明必须与实现一致：042 T03 声称的"打开抽屉自动打分"实际未实现（实现为 PRD 1.1 的用户手动点击触发，符合 PRD），必须更正声明而非补自动打分行为；同时沉淀"PR 合并前 CI（含后端编译）必须绿"的工程纪律，防止 main 再次合入不可构建代码。

**Why this priority**: 不改产品行为，只修正文档失实与流程漏洞；但若不修，下一次验收仍会被不实声明误导（本次 P0 正是在"测试全通过"声明下合入 main 的）。

**Independent Test**: 通读 042 任务清单与交接文档，无与实现相反的声明；工程纪律文档包含合并前置 CI 规则条目。

**Acceptance Scenarios**:

1. **Given** 维护者阅读 specs/042 任务清单 T03，**When** 对照实现，**Then** 声明描述与实际行为（手动触发打分）一致
2. **Given** 工程纪律文档，**When** 维护者查阅 PR 合并流程，**Then** 存在"合并前 CI 含后端编译必须通过"的强制规则

### Edge Cases

- 客观项预判得分为空且权重合计 ≠ 100 同时出现：得分列"待确认"、合计行保留实际总分与警告标注，两者互不干扰
- 预判得分为空项的详情弹窗：得分行"待确认"，评分依据显示后端待确认依据文案
- 阶段 2 回归：实际得分为空的客观项（解析失败兜底路径）已显示"待确认"，本次修复不得改变阶段 2 行为
- >50MB 提示与格式不支持提示同时存在场景：文件先超限则提示大小文案，格式非法则提示格式文案，二者不叠加

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 阶段 1 评分标准表中，预判得分为空的客观项 MUST 在"预计得分"列显示"待确认"（灰色主观样式），MUST NOT 显示数字 0 或零分红色样式
- **FR-002**: 评分项详情弹窗（预计模式）中，预判得分为空的客观项 MUST 显示"待确认"，与表格口径一致
- **FR-003**: 得分列渲染逻辑 MUST 区分三种空值语义：真实零分（数字 0，红色）、待确认（空值，灰字"待确认"）、主观项（"待确认"）
- **FR-004**: 评分项详情弹窗整体高度 MUST 不超过视口高度的 70%，超出时内容区内部滚动
- **FR-005**: 表格"满足状态"列中"待确认"的文字 MUST 为灰色，前缀圆点 MUST 为蓝色
- **FR-006**: 投标文件上传超过 50MB 时，面向用户的提示文案 MUST 为"文件大小超过限制（50MB），请压缩后重新上传"
- **FR-007**: specs/042 任务清单中关于"打开抽屉自动执行打分"的声明 MUST 更正为"用户点击「AI 实际打分」按钮触发（PRD 1.1），打开抽屉仅展示已有结果"
- **FR-008**: 工程纪律文档 MUST 沉淀规则：PR 合并前 CI 必须通过且必须包含后端编译检查；自验收文档中的"测试通过"结论 MUST 附可复现命令与结果

### Key Entities

本 feature 为缺陷修复性质，不引入新数据实体；涉及既有实体展示口径：评分项（预计得分、满足状态）、打分结果（实际得分）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: PRD 1.3 复验通过——构造"知识库无对应数据的客观项"用例，预计得分显示"待确认"的比例为 100%（含表格与详情弹窗两处）
- **SC-002**: 本 feature 涉及的前端测试套件全部通过，且后端整体编译通过（基线为 043 分支之上的完整代码）
- **SC-003**: 文档一致性抽查通过——042 清单与验收交接文档中不存在与实现相反的行为声明
- **SC-004**: 阶段 2 展示行为零回归——既有阶段 2 相关测试全部原样通过

## Assumptions

- 基线为 PR !2298（043 分支）：P0 编译缺陷（OpenAiScoreAnalyzer 缺失 import）已在该分支修复，本 feature 不重复处理，仅在验证环节确认编译通过
- 「导入到评分草稿」「导出报告」两个超出 PRD 的工具按钮的去留属产品决策，不在本 feature 范围
- PRD 内部矛盾（1.3 仓库类"无记录→待确认" vs 3.4"未匹配=0 分"）维持现实现（按 3.4 公式），待产品澄清后另行处理
- 投标文件通用上传入口的格式校验宽度（允许 xlsx/图片）属既有业务行为，本 feature 仅对齐 50MB 提示文案，不收紧通用上传格式（打分链路已有解析失败闭环兜底）
