# Feature Specification: 评分解析生产风险收口

**Feature Branch**: `043-harden-score-parse-intake`

**Created**: 2026-08-16

**Status**: Implemented

**Input**: User description: "修复生产风险审查对 PR #2296 指出的六项：失败后不再自动重打解析、招标文件读取设大小上限、立项读失败回退已有快照、下载连接复用、去掉初稿残留文案、上线说明写清初稿入口下线是产品决定。"

## Clarifications

### Session 2026-08-16

- Q: 打开评分抽屉时，什么情况下系统可以自动开始解析（不必先点「重新解析」）？ → A: 仅当该项目从未有过解析任务、且还没有评分项时自动**新建**一次；已失败、成功都不自动新建。进行中不算「自动开始」：只跟随已有任务（复用并轮询），不另开并行任务。
- Q: 立项招标文件超过 50MB 时，解析是失败还是回退底稿？ → A: 超大文件不得整包载入。有可用历史底稿则回退底稿继续解析；无底稿则失败，并向用户说明文件过大。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 解析失败后不再悄悄重打 (Priority: P1)

投标人员打开「AI 评分标准解析」抽屉。仅当该项目**从未有过任何解析任务**、且还没有评分项时，打开抽屉可以自动**新建**一次解析。已成功或失败后再打开，不得再自动新建；失败时展示原因，要再跑必须点「重新解析」。若已有进行中的任务，打开抽屉只跟随该任务等到终态，不另开一轮。

**Why this priority**: 失败后每次打开都自动再跑，会重复消耗解析配额、拖慢其他项目的解析，也让用户误以为系统在死循环。

**Independent Test**: 构造一次解析失败后的项目，连续打开抽屉两次，第二次不得再自动发起解析；点「重新解析」后才发起。

**Acceptance Scenarios**:

1. **Given** 项目立项已上传招标文件、尚无评分项、且从未有过任何解析任务，**When** 用户打开评分抽屉，**Then** 系统自动开始一次解析。
2. **Given** 该项目最近一次解析已结束（成功或失败）且当前无评分项，**When** 用户再次打开评分抽屉，**Then** 系统不自动新建解析；若最近一次失败则展示失败原因；用户可点「重新解析」。
3. **Given** 抽屉已展示失败态，**When** 用户点击「重新解析」，**Then** 系统发起新的解析任务。
4. **Given** 已有进行中的解析任务，**When** 用户打开抽屉或点击「重新解析」，**Then** 系统跟随并等待该任务，不另开并行任务（跟随不是新建）。

---

### User Story 2 - 超大招标文件被拒绝，服务保持可用 (Priority: P1)

投标人员使用立项阶段已上传的招标文件做评分解析。文件超过业务允许的大小上限（与立项/项目文档一致：50MB）时，系统拒绝把整份文件读入解析，并给出可理解的失败说明。不超过上限的常规招标文件仍能正常解析。

**Why this priority**: 无上限整包读入会拖垮服务进程，影响同一环境上的所有用户。

**Independent Test**: 超过 50MB 且无底稿 → 失败并说明过大；超过 50MB 且有底稿 → 不整包载入、改用底稿；不超过 50MB 的可读文件可进入解析。

**Acceptance Scenarios**:

1. **Given** 立项招标文件不超过 50MB 且可提取正文，**When** 用户发起或自动触发解析，**Then** 系统读取该文件并继续评分项提取。
2. **Given** 立项招标文件超过 50MB 且没有可用历史底稿，**When** 解析尝试读取该文件，**Then** 该文件不得整包载入，解析失败并提示文件过大。
3. **Given** 远程存储返回的文件没有可靠的大小声明，**When** 实际读取量达到 50MB 仍未结束，**Then** 系统停止读取该来源；无底稿则按过大失败，有底稿则回退底稿。
4. **Given** 立项招标文件超过 50MB 且存在可用历史底稿，**When** 发起解析，**Then** 不整包载入超大文件，改用该底稿完成解析。

---

### User Story 3 - 立项文件读失败时用已有解析底稿 (Priority: P1)

项目可能同时有「立项上传的招标文件」和「历史解析留下的正文底稿」。立项文件优先。若立项文件读不出（损坏、扫面件无字、存储暂时不可用），系统改用已有底稿继续解析，而不是直接失败。只有立项文件和底稿都不可用时，才要求用户先在立项阶段重新上传招标文件。

**Why this priority**: 「有没有可用正文」必须前后一致；否则会出现“系统认为有文件、一跑就失败、好底稿用不上”。

**Independent Test**: 立项文件故意不可读但存在可用历史底稿时，解析应使用底稿；两者都没有时，明确提示去立项上传。

**Acceptance Scenarios**:

1. **Given** 立项招标文件可读，**When** 发起解析，**Then** 使用该立项文件正文，不使用更旧的底稿。
2. **Given** 立项招标文件存在但读失败或抽不出正文，且存在可用历史底稿，**When** 发起解析，**Then** 使用该底稿完成解析，不把任务判为“没有招标文件”。
3. **Given** 立项文件与历史底稿都不可用，**When** 用户打开抽屉或发起解析，**Then** 无文件时提示「请先在立项阶段上传招标文件」，超大无底稿时提示文件过大；留下 FAILED 记录，再次打开不自动新建。
4. **Given** 判断“能不能解析”的入口，**When** 与真正取正文的入口面对同一项目，**Then** 两者对“是否有可用正文”的结论一致。

---

### User Story 4 - 文案与上线说明对齐产品决定 (Priority: P2)

产品已决定不再通过「启动 AI 生成初稿」做评分。界面残留的“用于生成初稿”说法会误导用户走回头路。上线说明需写明：这是产品下线入口，不是事故回滚。

**Why this priority**: 不修会让一线按旧路径操作，验收和培训对不上。

**Independent Test**: 招标拆解相关界面不再出现“可用于 AI 生成初稿”的引导；发布说明含初稿入口下线原因。

**Acceptance Scenarios**:

1. **Given** 用户打开招标拆解相关说明，**When** 阅读上传提示，**Then** 文案只服务拆解/评分解析，不再引导去生成初稿。
2. **Given** 本变更随版本发布，**When** 实施或验收阅读上线说明，**Then** 能看到：初稿入口下线是产品决定；评分路径为立项上传招标 → 评分抽屉 → 编制上传投标后实际打分。

---

### Edge Cases

- 用户在解析进行中反复打开抽屉：只跟随进行中的任务，不叠加新任务。
- 解析失败后用户更换了立项招标文件再打开抽屉：不自动解析；必须点「重新解析」才用新文件。
- 解析成功后又变成空清单（被覆盖清理或数据被删）：打开抽屉不自动再跑，须点「重新解析」。
- 解析失败后用户更换了立项招标文件再点「重新解析」：使用新文件，不因曾经失败而拒绝手动重试。
- 文件大小刚好 50MB：视为不超过上限，允许读取。
- 历史底稿有正文但立项文件是空壳记录（无有效存储地址）：视为立项读失败，回退底稿。
- 远程下载中途断开：按读取失败处理；有底稿则回退，无底稿则提示重新上传。
- 用户无项目权限：行为与现网一致，不得因本次修复放宽或绕过权限。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 仅在「尚无评分项、且该项目从未有过任何解析任务」时，才允许打开抽屉时自动**新建**一次解析。
- **FR-002**: 系统 MUST 在最近一次解析已结束（成功或失败）时，禁止因再次打开抽屉而自动新建解析；最近一次失败时 MUST 展示失败原因；用户 MUST 能通过「重新解析」手动重试。进行中的任务按 FR-008 跟随，不算新建。
- **FR-003**: 系统 MUST 拒绝把超过 50MB 的招标文件整份载入内存。无可用底稿时 MUST 向用户说明文件过大；有可用底稿时按 FR-005 回退，不把超大文件当解析正文。
- **FR-004**: 系统 MUST 在读取招标文件时限制实际读取量不超过 50MB；达到上限仍未读完则放弃该来源（有底稿则回退，无底稿则按过大失败）。
- **FR-005**: 系统 MUST 优先使用立项招标文件正文；当立项文件读取或抽正文失败且存在可用历史底稿时，MUST 改用该底稿。
- **FR-006**: 系统判断“是否具备可解析正文”与真正取正文 MUST 使用同一套成功条件，避免“以为有文件、一跑就失败”。
- **FR-007**: 系统 MUST 在立项与底稿都不可用时返回失败并留下 FAILED 任务，不得因 `lastParseStatus` 仍为 null 而每次打开抽屉再自动 POST。无文件时提示先在立项阶段上传招标文件；仅超大导致无源时用 FR-003 的过大说明。
- **FR-008**: 系统 MUST 在同一项目已有进行中的解析时复用该任务，不并行再开一轮。
- **FR-009**: 招标拆解相关界面 MUST 删除“可用于 AI 生成初稿”类引导，改为与拆解或评分解析一致的说明。
- **FR-010**: 本变更的上线说明 MUST 写明：初稿入口下线是产品决定；现行评分路径为立项招标 → 评分抽屉 → 编制投标后实际打分。
- **FR-011**: 读取远程招标文件时，系统 MUST 稳定、可重复地完成下载，不得因每次新建无管理的下载会话而泄漏资源或放大故障面。

### Key Entities

- **评分解析任务**: 一次针对某项目的解析运行，状态包括进行中、成功、失败；失败后仍可查询原因。
- **立项招标文件**: 立项阶段上传的招标原件，是评分抽取的首选正文来源。
- **历史解析底稿**: 项目上已保存的招标正文备份，仅在立项文件不可用时使用。
- **评分项清单**: 解析成功后的结构化评分要求；为空表示尚未成功解析。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 最近一次解析已结束（含失败或成功后清单为空）的项目，连续打开评分抽屉 3 次，自动**新建**的解析次数为 0；用户点 1 次「重新解析」恰好新建 1 次。进行中打开抽屉只跟随已有任务。
- **SC-002**: 超过 50MB 的立项文件不得整包进入内存；无底稿时解析失败且提示过大；有底稿时使用底稿、不把超大文件当正文。
- **SC-003**: 立项文件不可读但有可用底稿时，解析使用底稿，而不是报「没有招标文件」。
- **SC-004**: 同一项目同一时刻，「能不能解析」与实际取正文的结论一致（无互相矛盾的提示）。
- **SC-005**: 招标拆解界面中“生成初稿”引导出现次数为 0；验收人员阅读上线说明即可独立说出新评分路径，无需再问“初稿按钮去哪了”。
- **SC-006**: 投标人员在立项已传招标、且该项目从未有过解析任务时，首次打开评分抽屉仍能在一次操作内进入解析，不增加额外步骤。

## Assumptions

- 立项招标读上限与现网立项/项目文档约定一致，为 50MB（含等于 50MB）。这与宪法「通用附件上传 20MB / PDF·JPG·PNG」不是同一条规则：本特性读的是立项招标（含 Word），不把通用附件上限套到招标正文。
- 「打开抽屉自动**新建**解析」只服务从未有过任何 PARSE 任务的第一次打开。之后成功/失败都须点「重新解析」。进行中只跟随已有任务，不算新建。
- 无可用正文时 `POST /parse` 仍返回 400，但须留下一条 FAILED 任务，避免 `lastParseStatus` 仍为 null 导致每次打开抽屉再自动 POST。
- 历史解析底稿若存在非空正文，即视为可用；不在本规格内重新校验底稿是否过期。
- 不恢复「启动 AI 生成初稿」作为评分入口；后端初稿能力可保留但不在本规格实现范围内。
- 权限、阶段 2 实际打分、四路抽取算法本身不在本规格修改范围内。
- 本规格在 PR #2296「评分解析改走立项招标文件」之上收口风险，不回退该产品方向。
- 上线说明写入本仓库实施说明或发布说明即可，不另建对外营销页。
