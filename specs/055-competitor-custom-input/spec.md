# Feature Specification: 竞品公司自定义输入与竞争对手库治理 (055)

## 业务背景与问题定义

项目详情"结果确认"阶段的「竞争对手情况」表格，竞品公司名称下拉选项目前是前端硬编码的
24 个公司常量（`src/constants/competitors.js` 的 `COMPETITOR_COMPANY_OPTIONS`）。

问题：
1. **静态写死**：新竞品出现需改代码发版，无法快速响应业务；且各模块（结果登记、项目立项、
   竞争情报、数据报表）数据源不统一。
2. **无自由输入**：下拉不支持输入不存在的公司名，业务员遇到新竞品被阻断。
3. **无治理闭环**：后端已有 `competitors` 全局字典表（`competitionintel` 模块），但缺少
   改名、合并、停用等治理能力，且创建接口限 ADMIN/MANAGER，录入端无法自动入库。

本需求落地文档《竞品公司自定义输入》的方案 **B1**：录入端零门槛（动态下拉 + 输入即建），
治理端兜底（管理员后台改名/合并/停用）。

## 用户故事与使用场景

### User Story 1: 结果确认页动态选择并输入即建竞品 (P1)
**作为** 投标专员（以及投标组长、投标项目负责人、投标管理员等可操作结果确认页的投标业务角色），
**我希望** 竞品公司名称下拉框从后端全局竞品库动态加载、支持搜索过滤，且输入不存在的名字时
自动进入全局竞品库，
**以便于** 遇到新竞品时不被阻断，登记流程丝滑完成。

### User Story 2: 管理员维护竞争对手库 (P1)
**作为** 投标管理员 / 投标系统管理员 / 投标组长 / 本地超级管理员，
**我希望** 在系统管理区有一个「竞争对手库」列表，能查看竞品、修改名称、将相似项合并到规范项、停用错误项，
**以便于** 治理录入端产生的同名异写/错别字，保持全局竞品字典与后续报表的规范。

### User Story 3: 停用竞品不影响历史快照与报表 (P2)
**作为** 所有查看历史项目结果的人员，
**我希望** 某个竞品被改名/合并/停用后，已登记的项目结果快照仍保持登记当时的原样，
**以便于** 审计与历史还原的真实性不受字典治理影响。

## 功能需求 (Functional Requirements)

- **FR-01 (动态下拉数据源)**：系统提供竞品全局字典查询接口，返回"启用中"的竞品列表，作为结果确认页竞品下拉的数据源。
- **FR-02 (输入即建)**：投标业务角色（`bid-Team`、`bid-TeamLeader`、`bid-projectLeader`、`/bidAdmin`、`bid-SystemAdmin`、`admin`）在结果确认页输入不存在的竞品名时，系统自动创建全局竞品条目，无需离开登记流程。
- **FR-03 (名称唯一 + 并发幂等)**：竞品名称全局唯一；并发输入同名竞品只产生一条记录（唯一约束 + 按名查重兜底）。
- **FR-04 (快照只存 name)**：结果确认保存竞品快照时仅存名称文本，不引用竞品字典主键；历史快照不受后续字典变动影响。
- **FR-05 (治理权限)**：仅治理角色（`admin`、`/bidAdmin`、`bid-SystemAdmin`、`bid-TeamLeader`）可执行改名、合并、停用。
- **FR-06 (改名)**：治理角色可修改竞品名称；新录入使用新名称，历史快照保持原名。
- **FR-07 (合并)**：治理角色可将某竞品合并到另一竞品（如"上海震坤行"→"震坤行"）；合并后原竞品停用，其竞争分析（`competition_analyses`）关联迁移到目标竞品；历史项目结果快照的 name 保持不变。
- **FR-08 (停用)**：治理角色可停用竞品（软删除）；停用后不再出现在录入下拉，但历史快照与已有关联不受影响。
- **FR-09 (权限统一)**：权限遵循 Constitution VI——竞品创建与治理的权限键 MUST 在 `RoleProfileCatalog` 注册，并经 Flyway 迁移同步到对应角色；Controller 用 `hasAuthority`/`isAuthenticated`，禁止 `hasAnyRole` 角色白名单。
- **FR-10 (初始数据迁移)**：现有 24 个硬编码竞品经 Flyway 迁移 seed 进竞品字典，保证录入体验不退化。
- **FR-11 (审计可追溯)**：竞品创建、改名、合并、停用操作可被审计追踪。

## 非功能需求 (NFR)

- **NFR-01 (纯核心可测)**：竞品查重、合并引用迁移、停用过滤等核心判定为纯函数/可独立单测，不依赖 Spring/IO。
- **NFR-02 (前端字段对齐)**：前端竞品 API 归一化字段与后端 DTO 对齐（消除现有 `normalizeCompetitor` 字段错位）。
- **NFR-03 (无 N+1)**：竞品列表、合并引用迁移采用批量操作。
- **NFR-04 (装饰性降级)**：下拉加载竞品失败时降级为允许自由输入，不阻断结果登记主流程。

## 边界与权衡

- **历史快照不修复**：合并/改名不回溯改写 `project_result_competitor` 历史 name。理由为审计真实性
  （文档问题 3 明确"已登记结果不受字典变动影响"），而非技术复杂度。
- **报表只对合并后新数据规范**：竞争对手分析报表按快照 name 分组，历史错别字仍按原 name 计入；
  合并治理只保证"合并后录入"的数据规范，接受此取舍。
- **停用即软删除**：竞品字典不物理删除，用状态字段标记停用，防止已有关联悬空。
- **B1 而非 B2**：不引入"标准库 vs 临时录入"双态，录入端零门槛，治理端兜底。

## 验收条件与成功指标

1. **动态下拉**：结果确认页竞品下拉从后端动态加载，不再依赖前端硬编码常量。
2. **输入即建**：投标业务角色输入新竞品名，失焦/提交后竞品即时进入全局字典，无需离开页面。
3. **幂等**：并发输入同名竞品不产生重复条目（唯一约束 + 查重兜底）。
4. **治理生效**：治理角色改名/合并/停用竞品后，后续录入下拉只看到规范名/启用项；
   历史项目结果快照 name 保持原样。
5. **权限边界**：非投标业务角色不能创建竞品，非治理角色不能改名/合并/停用。
6. **无回归**：后端全量测试通过，前端 build 与既有测试通过。
