# Feature Specification: 投标关键节点企微通知

**Feature Branch**: `agent/kimi/enterprise-wecom-notifications`

**Created**: 2026-07-12

**Status**: Implemented

**Input**: User description: "新增两个企业微信通知触点：1）投标管理员在已评估的标讯，点击立即投标。要给项目负责人发送待立项的企微通知。2）项目详情，投标负责人将项目复盘阶段推进至项目结项阶段。要给项目负责人发送待结项申请的通知。要求按 FP-Java Profile + Split-First Rule 实现：纯核心负责业务决策，应用服务只做编排；任何类不得同时承担规则计算、数据访问、DTO 转换、状态写入三类以上职责；单文件超过 300 行前必须拆分。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 立即投标触发待立项通知 (Priority: P1)

投标管理员在已评估标讯页面确认标讯具备投标条件后，点击"立即投标"按钮。系统在完成投标状态转换的同时，向该标讯对应项目的项目负责人发送一条企业微信通知，提醒其有待立项的项目需要处理。

**Why this priority**: 这是投标流程从"评估"进入"立项"的关键转换点，通知项目负责人及时处理立项是保障投标流程不被阻塞的核心环节。

**Independent Test**: 可通过在已评估标讯页面点击"立即投标"按钮验证：主流程完成后，项目负责人收到一条内容准确的待立项企微通知。

**Acceptance Scenarios**:

1. **Given** 标讯状态为"已评估"且当前用户有投标管理员权限，**When** 用户点击"立即投标"，**Then** 系统完成投标状态转换，并向项目负责人发送待立项企微通知。
2. **Given** 标讯状态不是"已评估"，**When** 用户点击"立即投标"，**Then** 系统拒绝操作，不发送任何通知。
3. **Given** 项目负责人未绑定企微账号，**When** 用户点击"立即投标"，**Then** 主流程仍成功完成，通知发送失败被记录但不阻塞业务。

---

### User Story 2 - 项目结项推进触发待结项申请通知 (Priority: P1)

投标负责人在项目详情页将项目从"复盘阶段"推进至"项目结项阶段"。系统在完成阶段转换的同时，向该项目的项目负责人发送一条企业微信通知，提醒其有待结项申请需要处理。

**Why this priority**: 项目从复盘到结项是项目生命周期的收尾关键节点，及时通知项目负责人提交结项申请可避免项目长期挂账。

**Independent Test**: 可通过在项目详情页将项目阶段从"复盘"推进至"项目结项"验证：阶段转换完成后，项目负责人收到一条内容准确的待结项申请企微通知。

**Acceptance Scenarios**:

1. **Given** 项目当前阶段为"复盘阶段"且当前用户有投标负责人权限，**When** 用户将项目推进至"项目结项阶段"，**Then** 系统完成阶段转换，并向项目负责人发送待结项申请企微通知。
2. **Given** 项目当前阶段不是"复盘阶段"，**When** 用户尝试推进至"项目结项阶段"，**Then** 系统拒绝操作，不发送任何通知。
3. **Given** 项目负责人与当前操作用户为同一人，**When** 用户推进项目结项，**Then** 系统仍按规则发送通知（或按产品配置决定是否发送）。

---

### Edge Cases

- 项目负责人不存在或为空时，通知发送逻辑应如何兜底？
- 通知服务暂时不可用（企微 API 超时/失败）时，是否允许主流程失败？
- 同一操作被重复提交时，是否会导致重复发送通知？
- 当前用户没有操作权限时，状态转换和通知都不得执行。
- 通知内容中的项目名称、标讯名称等关键信息缺失时，是否允许发送简化模板通知？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在投标管理员点击"立即投标"且状态转换成功后，向项目负责人发送待立项企微通知。
- **FR-002**: 系统必须在投标负责人将项目从"复盘阶段"推进至"项目结项阶段"且阶段转换成功后，向项目负责人发送待结项申请企微通知。
- **FR-003**: 系统必须在发送通知前校验当前用户具备对应操作权限。
- **FR-004**: 系统必须确保通知发送失败不影响主业务流程的提交成功。
- **FR-005**: 系统必须支持通过项目负责人标识查询其企微通知接收账号。
- **FR-006**: 系统必须记录通知发送的关键上下文（触发动作、接收人、发送结果），便于后续审计与排查。
- **FR-007**: 系统必须避免同一业务动作在短时间内因重复提交而发送重复通知（具备幂等或去重机制）。

### Key Entities *(include if feature involves data)*

- **Tender/标讯**: 投标业务对象，包含状态、关联项目、评估结果等信息。
- **Project/项目**: 项目业务对象，包含当前阶段、项目负责人等信息。
- **Project Owner/项目负责人**: 接收企微通知的目标用户，需关联其企微账号标识。
- **Notification Request/通知请求**: 包含模板标识、接收人、模板变量（项目名称、标讯名称、操作链接等）的通知发送请求。
- **Notification Result/通知结果**: 记录通知发送是否成功、失败原因等结果信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在已评估标讯页面点击"立即投标"后，项目负责人在 1 分钟内收到待立项企微通知的成功率达到 99% 以上（企微服务可用时）。
- **SC-002**: 将项目从复盘阶段推进至结项阶段后，项目负责人在 1 分钟内收到待结项申请企微通知的成功率达到 99% 以上（企微服务可用时）。
- **SC-003**: 通知发送失败时，主业务流程的成功率保持 100%，不出现因通知失败导致的回滚或报错。
- **SC-004**: 同一业务动作在 5 分钟内重复提交，项目负责人最多收到 1 条通知（幂等去重）。
- **SC-005**: 所有新增代码通过项目 ArchUnit 架构门禁，符合 FP-Java Profile 与 Split-First Rule 要求。

## Assumptions

- 企业微信通知服务已在项目中存在，可通过内部网关或 SDK 发送消息，本次需求复用现有能力。
- 项目负责人信息已存储在项目实体或关联的用户信息表中，可通过现有查询获取。
- 通知模板（待立项、待结项申请）可由业务方配置或已存在于企微应用后台，本需求负责按模板填充变量并触发发送。
- 通知发送为"尽力而为"的附加操作，不要求强一致性，允许异步或独立事务处理。
- 当前用户的权限校验已在对应的应用服务或控制器层完成，纯核心只负责业务规则计算。
