# Feature Specification: 评分解析与打分的花费守卫

**Feature Branch**: `044-score-llm-spend-guard`

**Created**: 2026-08-16

**Status**: Draft

**Input**: User description: "另起新任务。P0 事件监听和抽屉同一套门闩、失败熔断；P0 投标文件哈希未变则跳过打分；P1 按脏章节只重打相关评分项；P2 手动选择重打范围。明确不做项目级 Token 预算/扣费。"

## 背景

043 已挡住「打开评分抽屉失败后自动重打」。仍有两条花费漏洞：招标文档保存事件会在已解析过的项目上再开一轮解析；投标文件只改了一点也会对全部评分项整份再打。本特性在 043 之上补齐守卫，并给出增量重打。不做扣费或项目级额度。

本特性**不改**评分公式、四路抽取规则、权限模型。

## Clarifications

### Session 2026-08-16

- Q: 投标文件内容和上次成功打分时完全一样，用户仍点了「重新打分」，要不要再跑一轮智能评估？ → A: 没变就跳过（手点也跳过），只提示沿用上次结果。本版不提供「强制重打」。
- Q: 项目当日额度按任务次数还是按 Token 扣费？ → A: 不用管扣费。本版不做项目级额度、Token 账本或超额确认。
- Q: 用户后来换了一份立项招标文件，要不要自动再解析一次评分标准？ → A: 不自动，必须点「重新解析」。和抽屉门闩一致。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自动路径不再偷偷连打 (Priority: P1)

投标人员或系统在保存招标相关文档后，不应仅仅因为「又存了一次」就再跑一轮评分标准解析。自动发起解析的条件必须与打开评分抽屉时一致：只有该项目从未有过解析任务、且还没有评分项时，才允许自动新建。若短时间内自动路径连续失败，系统停止自动再打，并告诉用户需要先检查文件、再手点「重新解析」。

**Why this priority**: 这是仍在烧配额的漏洞。文档导入或保存抖动一次，就可能再打一整份招标。

**Independent Test**: 已有解析任务（成功或失败）的项目再保存招标文档，不得出现新的自动解析；连续自动失败两次后，第三次自动请求不得再发起。

**Acceptance Scenarios**:

1. **Given** 项目从未有过解析任务且无评分项，**When** 招标文档保存完成或用户打开评分抽屉，**Then** 系统可以自动新建一次解析。
2. **Given** 项目已有过解析任务（进行中、成功或失败），**When** 招标文档再次保存，或用户换成一份新的立项招标文件，**Then** 系统不自动新建解析；进行中则跟随已有任务；要用新文件必须点「重新解析」。
3. **Given** 同一项目在 30 分钟内自动路径已失败 2 次，**When** 再次出现会触发自动解析或自动打分的事件，**Then** 系统不再自动发起，并向有权限的用户展示熔断说明。
4. **Given** 系统已熔断，**When** 用户点击「重新解析」或「重新打分」，**Then** 仍允许手动发起（熔断只挡自动路径）。

---

### User Story 2 - 投标文件没变就不要再打 (Priority: P1)

投标人员再次触发实际打分时，若投标文件内容与上次完成打分时完全相同，系统直接沿用上次结果，不再消耗智能调用。用户能看出「本次跳过，文件未变化」。

**Why this priority**: 大文件全文重打是当前最大浪费；文件没变却整表重跑，没有产品价值。

**Independent Test**: 同一份投标文件连续打分两次，第二次不得产生新的智能评估，结果与第一次终态一致；换一份内容不同的投标文件后再打，必须重新评估。

**Acceptance Scenarios**:

1. **Given** 项目已有一次成功打分，且投标文件内容未变，**When** 用户再次点「重新打分」（或系统自动触发打分），**Then** 系统跳过智能评估，沿用上次各项结果，并提示文件未变化。本版没有「强制重打」。
2. **Given** 投标文件内容已变化，**When** 用户发起打分，**Then** 系统按后续故事做全量或增量重打，不得静默沿用旧结果。
3. **Given** 上次打分失败或没有可沿用的结果，**When** 用户发起打分，**Then** 即使文件哈希与某次失败尝试相同，也不得当作「成功结果」复用。

---

### User Story 3 - 只改一章时只重打相关项 (Priority: P2)

投标人员只改了投标文件中的部分章节后再打分。系统识别哪些章节变了，只对证据落在这些章节、或明显对应这些章节的评分项重新评估；其余项保留上次得分和引用，并告知「本次重评了多少项、因为哪些章节有改动」。

**Why this priority**: 改一章却重打全部几十项，时间和配额都不可接受。本故事依赖「已有一次成功打分」和「能区分章节」，可在哈希跳过之后独立交付。

**Independent Test**: 构造「仅一章内容变化、其余章不变」的第二次打分，被重新评估的项必须少于全部项，且变化章对应的项被重评。

**Acceptance Scenarios**:

1. **Given** 已有成功打分，且仅部分章节内容变化，**When** 用户发起打分，**Then** 系统只重评与脏章节相关的评分项，其余沿用上次结果。
2. **Given** 无法可靠切出章节或无法把评分项对应到章节，**When** 用户发起打分，**Then** 系统退回为全量重打，并说明原因（不静默少打）。
3. **Given** 增量重打完成，**When** 用户查看结果，**Then** 能区分「本次重评」与「沿用上次」的项。

---

### User Story 4 - 人选重打范围 (Priority: P3)

投标人员发起重新打分时，可以选择：全部项、仅当前不满足的项、或勾选的若干项。本版不设项目额度，也不做扣费。

**Why this priority**: 人指定范围能避免「只想重看几项却整表重跑」。额度/扣费已明确不做。

**Independent Test**: 只勾选 3 项再打分，只有这 3 项结果更新。

**Acceptance Scenarios**:

1. **Given** 项目已有评分项，**When** 用户选择「仅不满足项」或勾选若干项后发起打分，**Then** 只有所选范围内的项被重新评估。
2. **Given** 用户选择「全部」，**When** 发起打分，**Then** 按文件是否变化走跳过、增量或全量，不因额度拦截。

---

### Edge Cases

- 进行中的解析或打分任务：新的自动触发只跟随，不另开并行；熔断期间也不取消已在跑的任务。
- 熔断窗口过后：自动路径恢复，失败计数按窗口重新计算。
- 用户手点「重新解析」：不受「从未解析才自动」限制，也不受熔断限制；本版无额度拦截。
- 用户手点「重新打分」但投标文件相对上次成功打分未变化：跳过智能评估，提示沿用上次；本版不提供强制重打。
- 投标文件被删除或换了一份完全不同的文件：不得沿用旧打分；按全量重打。
- 章节切分失败：增量降级为全量，不得假装增量成功。
- 哈希相同但评分项清单已变（又重新解析过标准）：不得沿用旧打分，须按新清单评估。
- 无项目权限：行为与现网一致，不得因本特性放宽。
- 043 已约定的抽屉门闩继续有效：失败后再打开抽屉仍不自动新建解析。
- 立项招标被替换成新文件：不自动解析，必须点「重新解析」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有自动新建解析的入口（含打开抽屉、招标文档保存完成、立项招标被替换等）MUST 使用同一套条件：仅当该项目从未有过解析任务且尚无评分项时，才允许自动新建。已有解析历史后换招标文件 MUST NOT 自动再解析，须用户点「重新解析」。
- **FR-002**: 已有进行中的解析或打分时，自动入口 MUST 跟随已有任务，不得另开并行任务。
- **FR-003**: 同一项目在 30 分钟内自动路径失败达到 2 次后，系统 MUST 熔断自动解析和自动打分，直到窗口结束或用户成功完成一次手动任务。
- **FR-004**: 熔断 MUST 只阻挡自动路径；用户手动「重新解析 / 重新打分」MUST 仍可用，并看到熔断说明。
- **FR-005**: 系统 MUST 能判断当前投标文件内容是否与上次**成功**打分时相同；相同时 MUST 跳过智能评估并沿用上次结果（含用户手动点「重新打分」）。本版 MUST NOT 提供绕过该跳过的「强制重打」。
- **FR-006**: 投标文件内容变化、或评分项清单已变化、或没有可沿用的成功结果时，系统 MUST NOT 跳过评估。
- **FR-007**: 在已有成功打分且仅部分章节变化时，系统 MUST 只重新评估与脏章节相关的评分项，其余 MUST 沿用上次结果。
- **FR-008**: 无法可靠识别章节或无法把评分项对应到章节时，系统 MUST 改为全量重打并告知用户。
- **FR-009**: 用户 MUST 能在重新打分时选择范围：全部、仅不满足、或指定若干项。
- **FR-010**: 本版 MUST NOT 做项目级额度、Token 扣费或超额确认。
- **FR-011**: 用户 MUST 能看到本次是跳过、增量还是全量，以及重评了多少项（若为增量）。

### Key Entities

- **自动发起记录**: 某次由系统而非用户按钮触发的解析或打分，用于熔断计数（不计费）。
- **投标文件指纹**: 用于判断投标内容是否相对上次成功打分发生变化。
- **章节变更集**: 相对上次成功打分，内容有变化的章节。
- **打分沿用结果**: 某评分项上次成功评估的得分与引用，可在文件未变或章节未变时复用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 已有解析历史的项目，招标文档再保存 3 次或替换立项招标文件，自动新建的解析次数为 0。
- **SC-002**: 同一项目 30 分钟内自动失败 2 次后，窗口内第 3 次自动触发不会再发起智能调用。
- **SC-003**: 投标文件内容未变时再次打分（含手点「重新打分」），智能评估次数为 0，且各项结果与上次成功打分一致。
- **SC-004**: 仅一章变化时，被重新评估的评分项数量小于全部项，且用户能说出本次重评了哪些章。
- **SC-005**: 用户勾选部分项打分后，未勾选项的结果保持不变。

## Assumptions

- 依赖 043：抽屉侧「从未解析才自动新建、失败展示原因、进行中跟随」已是产品事实。换招标文件也不打破这条门闩。
- 熔断默认：30 分钟窗口、自动失败 2 次。只挡自动，不挡手点。
- 不做项目级额度、Token 账本、扣费或超额确认。花费控制靠门闩、熔断、哈希跳过和增量重打。
- 跳过打分只认「上次成功打分」的投标内容指纹；失败尝试不产生可沿用结果。手点「重新打分」在文件未变时同样跳过，本版不做强制重打。
- 章节按投标文件既有标题/章节结构划分；切不出结构则全量重打。
- 「与脏章节相关」：该项上次引用落在脏章节，或该项名称/维度与脏章节标题明显对应。不确定则宁可重评该项，不可漏评。
- 不恢复「启动 AI 生成初稿」。不改阶段 1 抽取算法和阶段 2 计分公式。
- 句子级 diff 打分不在范围内。
- 权限、项目隔离与现网一致。
